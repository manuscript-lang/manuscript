# Manuscript-only baseline, 2026-10-28

Fresh Manuscript-only numbers for every suite in this directory; the Go, Rust, C and Node comparison runs were skipped, so there are no ratio columns. The "change" column is this run's median over the median in [`baseline-2026-10-27.md`](baseline-2026-10-27.md) (`dcdaee5d`); below 1.00x is faster. Compare only on the same machine.

- Revision: `87d92d70` (main, 2026-10-28), `ms` 0.1.0 Release build (`make build`, `cargo build --release --locked -p ms-cli`, LLVM backend). Every benchmark program was built by that binary; no Debug or Cranelift build was used.
- Machine: Intel Xeon @ 2.10GHz, 4 vCPUs, 15 GB RAM, Linux 6.18 (shared cloud VM), the same class of machine as the 2026-10-27 page.
- Method: median of 7 runs (5 for workers and JSON, one run of 5 s rounds x 2 for web), run alone on the machine. "min" and "max" show the spread. `try`, `int_eq` and `read_line` in Programs use 15 runs, because the first 7 were noisy.
- Between the two pages 177 commits landed on main, including the Map, string-append, `Int` division, YAML/TOML/CSV/SSE parser, queue/deque, and compiler-pass perf PRs.

## Regressions since 2026-10-27

Two things got slower in a way that reproduced on rerun; the rest of the flagged cases were noise (see below).

| case | 2026-10-27 | 2026-10-28 | change | likely PR |
|---|---:|---:|---:|---|
| programs `try` (ns/op) | 0.38 | 0.71 | 1.9x slower | [#1704](https://github.com/manuscript-lang/manuscript/pull/1704) "Grow large buffers in place; string append within ~1.1x of Rust" |
| programs `int_eq` (ns/op) | 0.74 | 0.97 | 1.3x slower | not bisected; same loop-shape as `try`, so probably #1704 too |
| workloads `c05-calculator` (wall ms) | 52 | 78-84 | 1.5-1.6x slower | not bisected |

`try` was bisected over the 177 commits between the two baselines (0.36 ns before, 0.67 after `096356aa8`, which is #1704). `int_eq` and `c05-calculator` were rerun alone (c05: 15 runs, median 84 ms) and still show the slowdown, but I did not bisect them. `read_line` was 100 ns in the first 7 runs and 64 ns in 15 later runs against 56 ns before, so it is within noise.

Other flagged cases did not reproduce: in the full stdlib run `path.join_normalize` (687 vs 390), `url.parse` (786 vs 551), `string.replace` (25,218 vs 16,633), `list.contains` (38,509 vs 27,177), `math.sqrt_sin` and `time.parse_timestamp` read 1.3-1.8x slower than on 2026-10-27, but rerunning each alone with `--filter` and 15 samples gave 389, 496, 16,995, 26,471, 8.8 and 30.6, equal to the old numbers. Treat single cases in the stdlib table as +-40% across full runs.

## Big wins

Stdlib: `toml.parse` 0.12x, `yaml.parse` 0.16x, `yaml.roundtrip` 0.16x, `sse.feed` 0.13x, `csv.parse` 0.31x (the parser regressions reported on 2026-10-27 are gone), `tasks.spawn_results_1000` 0.10x, `list.map` 0.13x, `list.chunks` 0.09x, `list.partition` 0.16x, `deque.push_pop_both_ends` about 0.2x, `queue.enqueue_dequeue` about 0.3x, `priority_queue` about 0.4x, `fs.list_200` 0.42x, `json.parse` 0.41x. Programs: `collatz_1M` 0.88x, `set_int_add_contains` 0.74x, `pq_int_enqueue_dequeue` 0.49x. Web `/health` req/s 1.6x.
