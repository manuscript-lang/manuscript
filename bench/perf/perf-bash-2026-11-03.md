# Perf bash, 2026-11-03 (stdlib, data structures, programs)

Same-machine Release `ms` (LLVM) before and after, starting at main `a460b7ef`. Machine: Intel Xeon @ 2.10GHz, 4 vCPUs, Linux 6.18 (shared cloud VM), so compare only within this page.

## Gaps found at `a460b7ef`

Data structures are at or ahead of Go and Rust except `string_build_split_join_replace` (1.21x Rust), `bytes_append` (1.43x) and `pq_int_enqueue_dequeue` (1.16x). Kernels are within 1.0x to 1.4x of Rust (`life` 1.39x, `nbody` 1.27x, `matmul` 1.23x). The largest gaps against Go and Rust:

| case | ms | Go | Rust |
|---|---:|---:|---:|
| programs `read_line` (ns/line) | 204 | 115 | 87 |
| programs `string_append_50k` (ns/op) | 1.97 | 3.39 | 0.97 |
| workloads `c03-csv-group-sum` (ms) | 81.8 | 34.2 | 25.6 |
| workloads `c36-bank-ledger` (ms) | 89.3 | 100.6 | 53.7 |

## Stream reads

Profile: each line pulled from `lines(stdin())` paid for a runtime promise, two closures and a result copy. `for x in s.wait()` now runs the source's step directly (it is the waiter's own stack either way), and `read()` makes one closure instead of two.

| case | before | after |
|---|---:|---:|
| `for line in lines(stdin()).wait()`, 2M lines from a file (ns/line) | 148 to 172 | 115 |
| programs `read_line` (ns/line, median of 7) | 204 | 160 |

## Cells keep their block

`msrt_cells_take` freed the cell's block and `msrt_cells_put` allocated a new one, so each stream read cost an allocation pair under the cells mutex, and `msrt_cells_new` scanned the whole table for a dead cell. A cell now keeps its block from `new` to `drop` (`take` and `put` copy the value out of and into it) and dead cells sit on a free list.

| case | before | after |
|---|---:|---:|
| `for line in lines(stdin()).wait()`, 2M lines from a file (ns/line, three alternating pairs) | 116, 112, 112 | 93, 98, 96 |

`tools/leak-check.ms`: 365 programs swept, 0 leaking.

## Looked at, nothing to fix

- `string_append_50k` (1.97 vs Rust 0.97 ns/op): `msrt_strbuilder_append` already has a one-byte path with no frame; the remaining 1 ns is the call and string-length decode per append. No change worth its code.
- `c03-csv-group-sum` and `c36-bank-ledger`: per-line costs measured alone are 3 to 44 ns each (`replace` 16, `trim().is_empty()` 9, `split` 18, `split`+`parse_int` 44, `Map` add/get_or 42, `contains` 10); the biggest single piece was the stream read (fixed above and in #2463). What is left is spread over string allocation, with no hot spot to remove.

## Lock-free cells

`take` and `put` locked the global cells mutex twice per stream item. Cells now sit in a table of fixed pages and one atomic word per cell packs its generation and state (dead, full, out, putting); `take` and `put` are one compare-and-swap each, and only `new` and `drop` take the mutex that guards the dead-slot list, which is threaded through the dead cells themselves (slot indices only, no memory held).

| case | before | after |
|---|---:|---:|
| bare stream of `Int`, 5M items (ns/item) | 32 | 20 |
| `for line in lines(stdin()).wait()`, 2M lines (ns/line, alternating pairs) | 92-97 | 83-86 |

`tools/leak-check.ms`: 365 programs swept, 0 leaking. New unit tests: a cell gives its value once and takes it back; a cell dropped during a read frees its block and ignores the late `put`.

## After #2463, #2477 and #2485 (main `29a8225f`+)

`workloads.ms -- 3`, min wall ms: `c03-csv-group-sum` 81.8 to 74.8 (Go 34.0, Rust 24.6; 2.20x Go), `c05-calculator` 54.5 to 55.8, `c36-bank-ledger` 89.3 to 80.1 (0.81x Go, 1.57x Rust). c03 is still 2.2x Go. Measured alone, per line: raw chunk scan with `index_of_byte` 15 ns, plus building the line string 31 ns, `lines()` 84 ns (a bare stream item is 20 ns, so the splitter's list append, reverse and pop cost about 33 ns), and the c03 parse work about 120 ns (`split` 18-20, `split`+`parse_int` 44, `Map` add and `get_or` 42). The stream layer has no single piece left to remove without a new list API (`reserve`, or moving an element out by index); the parse work is string allocation spread over many small operations.

## Kernels against Rust: spread, not a gap

`kernels.ms -- kernels 5` after the changes: `life_128x128_50` 3603 us vs Rust 2595 (1.28x with overflow checks), `nbody_200k` 6286 vs 5003, `matmul_200` 6605 vs 5353. Building the same `bench/perf/kernels/rust/main.rs` by hand with `rustc -O` gave `life` 3627 us on this machine, as slow as Manuscript, so the Rust binary itself varies by 40% with build flags and layout; and with the grid dimensions hidden from the optimizer (`black_box`) Rust takes 22,000 us. Manuscript already folds the constants. No codegen change is justified by these numbers.

## Cells without locked instructions

A stream's value has one owner at a time, so `take` and `put` no longer need a compare-and-swap: two locked instructions cost 12 ns per item in a standalone loop, which was most of the 20 ns bare item. They are now a load and a store of the cell's word; `drop` still swaps it, so a cell dropped on another thread after a handoff frees its block once.

| case | before | after |
|---|---:|---:|
| bare stream of `Int`, 5M items (ns/item, three alternating pairs) | 20, 21, 22 | 12, 12, 13 |
| `for line in lines(stdin()).wait()`, 2M lines (ns/line, five alternating pairs) | 82-101 | 84-86 |

The line loop did not move: with the stream item at 12 ns, the splitter and string building are what it measures. `tools/leak-check.ms`: 365 programs swept, 0 leaking.
