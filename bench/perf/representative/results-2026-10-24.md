# Representative performance baseline and local inliner improvement

Baseline: `414d66451b1efe8acde9cd31097dcb456ee62b0b`, fetched from `main` on
2026-10-24 before measurement. Optimization: local commit
`f24a068e88a827e4ae10956b84b3c546a0cc819e` (the local measured source revision,
reconstructible from [the retained patch](evidence-2026-10-24/optimization.patch)).
These are historical results on that exact baseline, not measurements of later main
or of the subsequently rebased publication branch.

The [change](../../../crates/ms-mir/src/opt/inline.rs) indexes constant definitions once per caller during MIR inlining and
adds definitions from newly appended callee blocks. The old implementation scanned
the entire growing caller at every candidate call. Inlining thresholds, growth
budgets, generated operations, ownership rules and runtime code are unchanged.

## Method and scope

- Linux x86-64, AMD EPYC 9V74 virtual machine, 5 visible CPUs, approximately 18 GB RAM.
  Rust 1.99.1 (`58cf8f9c3`), repository-pinned LLVM 23.1.1 bundle, GCC 14 for native
  runtime C dependencies and the RSS measurement helper. Compiler binaries use
  `cargo build --release --locked -p ms-cli`; Manuscript programs use Release
  (`default<O3>`, `llc -O3`) and the same runtime archive.
- Three unchanged real reference applications: CSV grouping with 200,000 rows
  (quoted categories and invalid input); inventory with 300 SKUs, 12,000 three-item
  orders, cancellation/shipping and periodic reports; log analysis with 200,000
  lines, malformed records, 300 paths, aggregation and percentile sorting.
  The expected output comes from each challenge's independent Python oracle.
- Synthetic scalar-rule pipelines at 100/200/400 and 1,000/2,000/4,000 rules isolate
  compiler scaling. They are not evidence of typical application runtime speed.
  Actual CLI `check --json`, `inspect`, and `diagram` exercise source tooling.
- Seven interleaved before/after build trials and nine runtime trials, after an
  excluded warm-up; three interleaved diagnostic-stage and isolated RSS trials.
  All timed runtime executions compare complete stdout to the oracle. CPU work
  from builds/tests/installations did not run alongside timed suites.
- Warm means extraction caches and filesystem pages are warm, but each compiler
  invocation is a new process. Cold means a new empty extraction cache, not flushed
  OS page caches. First toolchain installation and Rust compilation of `ms` are setup,
  not included in Manuscript compile times. No performance threshold is added to CI.
- Actual default-backend `execve` evidence shows embedded `opt`, `llc`, and `lld`.
  Stage runs additionally require an LLVM object and the exact `opt`/`llc` invocation
  pair. The baseline's `.ms-build.json` always says `cranelift`; that field was not
  used to identify the backend. Cached tools are hashed against the pinned downloads.

A diagnostic replay of individual MIR passes on 4,000 rules measured inlining at
0.8722 → 0.1370 s. The first simplification after inlining took 0.6577 s before the
change. This agrees with the source: `inline_into` formerly called `const_values`
for every candidate, while `inline_at` merely moves existing instructions and
appends fresh callee blocks. The new index preserves that definition set without
revisiting the growing continuation. No optimization is disabled.

## Runtime and memory

The before/after optimized MIR and native executables are byte-identical for all
ten programs. There is no generated-runtime speedup claim. The initial baseline
runtime medians were 45.6 ms CSV, 18.3 ms inventory and 74.0 ms logs. In the later
interleaved campaign they were 50.6 → 47.6, 20.3 → 20.1 and 74.6 → 78.3 ms respectively.
Those movements, including the apparent log slowdown, occurred with identical
executable bytes; keep them as shared-host measurement variation, not a code benefit
or evidence of a different backend. Synthetic runtimes below 1 ms are startup-dominated.
The retained focused follow-up (21 interleaved trials) gave 45.01 → 44.87 ms CSV,
18.725 → 18.722 ms inventory, and 71.95 → 71.29 ms logs. It does not reproduce the
apparent log regression; both campaigns remain in the raw evidence.

Separate isolated RSS trials (KiB, median of three):

| Program | Runtime before/after | Build before | Build after |
|---|---:|---:|---:|
| Hello | 164 / 164 | 65,124 | 65,100 |
| CSV | 528 / 528 | 66,160 | 65,708 |
| Inventory | 4,340 / 4,340 | 65,756 | 66,012 |
| Logs | 40,464 / 40,464 | 65,572 | 65,704 |
| 4,000 rules | 528 / 528 | 468,680 | 468,548 |

RSS is Linux's maximum resident size of a single process in the waited tree, not
aggregate concurrent process memory or reserved virtual address space. The ordinary
Python-launched timing samples have an approximately 12 MiB inherited RSS floor;
those raw values are retained but superseded by the separate native-launcher trials.
The optimization does not materially reduce peak build memory because LLVM remains
the largest process.

Empty extraction caches increased baseline hello compilation from approximately
0.048 to 0.552 s and inventory from 0.411 to 0.919 s in the initial campaign. These
are warm-page versus empty-extraction-cache comparisons, not disk-cold measurements.
Separate cold-cache RSS trials put hello at 186,932 KiB (about 183 MiB).

## Checked Rust context

These are independent whole-program implementations with the same input/output
contract, not matched instruction kernels. Both use Rust 1.99.1/LLVM 23.1.1 and static
musl linkage. The Rust references use `-C opt-level=3 -C overflow-checks=on -C
force-frame-pointers=yes -C panic=abort -C codegen-units=1`; Manuscript uses its normal
Release settings. Median of 15 interleaved native-runtime trials; RSS from three
separate isolated trials:

| Application | Manuscript ms | Rust ms | Manuscript RSS KiB | Rust RSS KiB |
|---|---:|---:|---:|---:|
| CSV | 46.85 | 49.60 | 528 | 3,900 |
| Inventory | 20.06 | 46.72 | 4,340 | 4,716 |
| Logs | 76.97 | 67.65 | 40,464 | 14,292 |

There is no blanket language ranking. For example, CSV's Rust implementation reads
all input and uses `BTreeMap<String, u128>`, while Manuscript streams lines and uses
`Map[String, Int]`. Logs use different collection materialization and update idioms:
Rust iterates `str::split` and updates through `HashMap::entry`; Manuscript's source
splits the input into a list and uses `get_or` plus `add`. These source differences
are leads for allocation/call-count profiling, not proof of each operation's share
of elapsed time. No ownership, borrowing or string-lifetime implementation is changed.
The reference source paths and all input/output hashes are pinned by this baseline.

## Tooling and priorities

Baseline CLI medians, seconds, five trials:

| Input | check --json | inspect | diagram |
|---|---:|---:|---:|
| Inventory | 0.0148 | 0.0161 | 0.0153 |
| Logs | 0.0147 | 0.0140 | 0.0142 |
| 1,000 rules | 0.0304 | 0.0487 | 0.0457 |
| 2,000 rules | 0.0553 | 0.0856 | 0.0783 |
| 4,000 rules | 0.1137 | 0.2000 | 0.1627 |

Measured priorities depend on the workflow:

1. LLVM optimization/codegen dominates warm native builds, with `llc` becoming the
   largest scaling cost. The 4,000-rule build still spends about 2.3 s there and
   reaches about 458 MiB RSS. This task makes no LLVM dependency changes.
2. First-use extraction adds approximately 0.5 s. Open PR #1126 already addresses
   tool packaging; no overlapping work or proposed fallback behavior was adopted.
3. Repeated MIR caller scans were the next large local, semantics-preserving target:
   the implemented index removes about 0.74 s of inliner work on 4,000 rules.
4. MIR simplification still has a measurable scaling cost. Its repeated block
   merging/compaction is a follow-up to profile, not another change in this patch.
5. Front-end/tooling latency is smaller on these real programs. The larger source
   cases show tooling scaling worth tracking; this patch does not optimize it.

A fresh instrumented 4,000-rule follow-up after the local change attributed 1.090 s
of `llc` CPU time (45.9%) to Machine Instruction Scheduler, 0.603 s (25.4%) to X86
instruction selection and 0.550 s (23.2%) to the Two-Address instruction pass.
`opt` attributed 0.222 s (34.7%) to InstCombine. These are current diagnostic data,
not the historical f100/f200/f400 figures. Pass timing is one attribution run,
separate from the repeated end-to-end measurements.

Runtime-helper inlining overlaps open PR #1124 and was not duplicated. PR #1130's
runtime symbol table and #1120's counted-loop reservation are already in the pinned
baseline, as are the #1114/#1116/#1117/#1125 refactors and #1119 equality repair.
#1132 is a read-only parity report, not a migration. The open-PR snapshot also
records #1121 and #1133, neither overlapping this change. No excluded lifetime,
borrow-parity, Windows recursion, workflow-dispatch or GraphQL work was attempted.

## Reproduction and validation

See [the harness protocol](README.md), `prepare.py`, `run.py`, `summarize.py`,
`check_outputs.py`, `rss.c`, and `crates/ms-build/examples/perf_stages.rs`.
The `.artifacts/representative/` directory retains binaries, complete stdout/stderr,
inputs and expected outputs, raw campaigns, tool execution logs and environment hashes.
The [retained evidence directory](evidence-2026-10-24/) contains compact measured
samples, input and binary hashes, and the exact historical patch. Its `samples.json`
groups each campaign by `phase/case/label`; arrays align with `trials` and exclude
warm-ups and build-validation executions. Full raw JSONL, stdout/stderr, pass timing
logs and check logs remain local under `.artifacts/representative/`, rather than
adding generated log volume to the repository. The exact backend invocation was
`opt -passes=default<O3>` followed by `llc -filetype=obj -O3`; the environment manifest
records downloaded and executed-cache tool hashes.

Validation results below refer to the measured optimization revision. The added constant-bonus
regression verifies constants on both sides of continuation splits and ensures a
call result does not acquire a literal bonus. The targeted inliner suite passed all
19 tests. All ten optimized MIR/native artifacts match exactly; all 41 ordinary
reference cases pass for baseline Manuscript, candidate Manuscript and checked Rust
(123 executions). Every large runtime trial also checks its entire output.

Completed checks: formatting; workspace/all-target Clippy with warnings denied;
all 842 workspace nextest tests (zero skipped); doc tests; repository invariants;
conformance metadata lint (4,576 fixtures, zero problems); and native Release corpus
replay (2,221 fixtures: 2,219 ordinary passes, zero unexpected failures, one expected
failure and one unexpected pass). Both corpus outliers reproduce on the pinned
baseline: the file-fixture hook case remains an expected failure and the fault-frame
case already passes despite its stale allowlist entry. Those unrelated expectations
were not changed.

The initial workspace test attempt stopped because `llvm-dwarfdump` was absent.
Debian LLVM 19.1.7 inspection tools were extracted locally and selected only through
`LLVM_DWARFDUMP`/`LLVM_SYMBOLIZER`; the complete rerun passed. They were never used
as the benchmark compiler backend. Optional Valgrind instruction-count profiling was
not collected: the package lookup had no candidate; no retry of that lookup was made.

The production optimization is reviewed separately from this harness.
Native macOS and Windows validation and globally cold page-cache trials are outside
this Linux measurement run.
