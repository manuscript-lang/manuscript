# Kernels against C with bounds checks, 2026-11-09

Revision `70f9e479`, `ms` Release build. Machine: Intel Xeon @ 2.10GHz, 4 vCPUs, Linux 6.18 (shared cloud VM), gcc `-O2 -std=c11 -ffp-contract=off`. Compare only against numbers from the same machine.

The 2026-11-05 page compares against C without any checks. Manuscript checks every list index, so this run adds the fairer reference: `bench/perf/kernels/c/ms.c` built with `-DMS_NO_POLL -DMS_NO_OVERFLOW`, which keeps only the bounds checks (`c-bounds`). Minimum of 9 interleaved runs of the three binaries, microseconds, identical checksums.

| kernel | ms us | c-bounds us | c us (unchecked) | ms / c-bounds | ms / c |
|---|---:|---:|---:|---:|---:|
| sieve_5M | 28410 | 28204 | 26836 | 1.01x | 1.06x |
| nbody_200k | 9024 | 8942 | 8906 | 1.01x | 1.01x |
| life_128x128_50 | 4958 | 37967 | 35078 | 0.13x | 0.14x |
| matmul_200 | 9098 | 10188 | 4796 | 0.89x | 1.90x |
| trees_d16_x20 | 25892 | 25855 | 29073 | 1.00x | 0.89x |
| collatz_1M | 244873 | 286587 | 280849 | 0.85x | 0.87x |
| map_count_2M | 17136 | 13002 | 11281 | 1.32x | 1.52x |

Matmul is the case that moves: unchecked C is 1.9x faster than Manuscript, while C with the same bounds checks is within 11% of it. map_count is left out of the public comparison: the C kernel is a specialized int table, not like-for-like with Manuscript's general `Map`.

Reproduce: build `ms.c` with the flags above and `plain.c` with `-O2 -std=c11 -ffp-contract=off`, build `bench/perf/kernels/ms` with `ms build`, run the three alternately and take each kernel's minimum.

## map_count with a single-lookup `Map.update` (revision `3fbb7cfe` plus this change)

Same machine as above, `ms` Release build with LLVM. The kernel now counts with `m.update(k, 0, fn count: count + 1)` instead of `m.add(k, m.get_or(k, 0) + 1)`. `Map.update` is lowered to one probe: an inlined word lookup for `Int` and `String` keys with scalar values, the runtime's `msrt_map_slot_lent` only for an absent key, and the closure inlined into the loop. The compiler-side matcher for `m.add(k, m.get(k).get(0) + 1)` is gone because this path is faster (10.1 ms before).

Minimum of 15 runs of the 2M-count loop, one program per spelling, microseconds:

| spelling | before | after |
|---|---:|---:|
| `m.add(k, m.get_or(k, 0) + 1)` | 13900 | 13900 (unchanged, two lookups) |
| `m.update(k, 0, fn v: v + 1)` | 15000 (two lookups plus an outlined call) | 7600 |
| `m.add(k, m.get(k).get(0) + 1)` (fused matcher) | 10100 | 13900 (matcher removed) |

`bench/tools/kernels.ms` (minimum of 7 rotating runs): map_count_2M is 7679 us for Manuscript, 22958 for Go and 22072 for Rust's `HashMap`. The plain C table runs it in 6.5 to 7.4 ms on this machine.
