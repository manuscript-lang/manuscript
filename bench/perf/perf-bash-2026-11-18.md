# Perf bash, 2026-11-18: workloads and standard library hot paths

Base `main` at the start of this branch, Release `ms` from `make build`, 4 vCPU shared Linux VM. Rust is `rustc -O -C overflow-checks=on`, standard library only. Programs are scratch workloads (not committed); numbers are ms, medians of 3 to 5 runs.

The real gap was the small file read: about 3.7 us per `read_file(..).wait()` against Rust's 1.8 us. Fixed in part below; the rest is promise setup (task spawn, park, context switch, about 60% of the remaining user instructions), which is a scheduler change and not done here.

## Change: TOML stringify no longer deep-copies the document

`emit_table`, `emit_one`, `inline_value`, `section_kind`, `table_items` callers and `datetimes_valid` called `.clone()` on each entry value and key, path and element list before reading them, so every nested table was copied once per level. They now pass the borrowed value.

| 20,000-table document, 1.8 MB | before | after |
| --- | ---: | ---: |
| `stringify` ms (median of 5) | 46 | 24 |
| parse and stringify of a 2,000-table document, instructions | 92.0M | 70.9M |

Output is unchanged (`toml*.ms` conformance fixtures pass). The same clone pattern in `yaml.ms` stringify measured no difference (73 vs 76 ms on 5.4 MB), so it is left alone.

## Change: reading a file opens it and stats it once

`read_file` ran `stat(path)` (to spot a FIFO, which would block `open`), then `open`, then `fstat`. It now opens with `O_NONBLOCK`, does one `fstat`, and switches a non-regular file back to blocking mode, as `open_regular` already did for the pool path. Windows keeps its plain open.

| 60,000 serial `read_file(..).wait()` of 2,000 small files | before | after |
| --- | ---: | ---: |
| system calls per read | 6 | 5 |
| wall seconds (5 alternating runs, median) | 0.225 | 0.190 |
| instructions per read (callgrind) | 8,290 | 7,680 |

## Change: a lone file read runs where it is waited on

`read_file` started a task per call even when nothing else was running, so each `wait` parked, switched to the task, finished and switched back (about 60% of the user instructions). `promise_when_idle` (runtime `msrt_promise_start_idle`) defers the work to the first waiter when the creator is the only live task, and starts a task as before when anything else is running, so reads still overlap. Pure runtime and stdlib, no platform code.

| 60,000 serial `read_file(..).wait()` | after opening once | with deferral |
| --- | ---: | ---: |
| instructions per read (callgrind) | 7,680 | 4,140 |
| wall seconds (5 alternating runs, median) | 0.172 | 0.135 |

Together with the one-stat open the read went from about 3.7 us to 2.2 us (Rust 1.8 us). The web benchmark is unchanged (`/health` 245k, `/io` 1.4k req/s, same as before).

## Change: XML parse matches literals on scalar values

The XML reader kept the document as a `List[String]` of one-scalar strings and, for every `looking_at` and `take_until`, built another list from the literal with `chars()`; `parse` also joined the whole document back into one string to validate it. It now keeps a parallel `List[Int]` of scalar values, compares literals against it, validates while building it, and `name` tests scalars (ASCII first) instead of one-scalar strings.

| 2.86 MB document, 30,000 items | before | after |
| --- | ---: | ---: |
| `parse` ms (3 alternating runs, median) | 188 | 109 |
| instructions, 3,000 items (callgrind) | 175.0M | 77.6M |

The remaining cost is the per-scalar `StringBuilder` for text and the `List[String]` itself; a byte cursor over the original string would remove both and is the next step if XML parse matters. Other formats scanned linearly and were left alone: HTML parses 1.9 MB in 70 ms.
