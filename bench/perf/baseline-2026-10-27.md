# Manuscript-only baseline, 2026-10-27

Fresh Manuscript-only numbers for every suite in this directory; the Go, Rust, C and Node comparison runs were skipped, so there are no ratio columns. Use it as the reference for later Manuscript changes, and compare against it only on the same machine.

- Revision: `dcdaee5d` (main, 2026-10-27), `ms` 0.1.0 Release build (LLVM), `make build`.
- Machine: Intel Xeon @ 2.10GHz, 4 vCPUs, 15 GB RAM, Linux 6.18 (shared cloud VM).
- Method: median of 7 runs (5 for workers, JSON and web), run alone on the machine. Columns "min" and "max" show the spread. Units are in each heading.
- The previous recorded tables (2026-10-25, `c1b81215`) came from a different machine, so the "Change vs 2026-10-25" section is from re-running `c1b81215` on this machine, not from those tables.

## Change vs 2026-10-25 (`c1b81215`, same machine)

I rebuilt `c1b81215` here and reran the suites that exist at both revisions. Differences under 15% are noise on this host and omitted. Stdlib cases whose benchmark source changed between the two revisions (lists, maps, queue, deque, bitset, io, binary, concurrency) are not comparable and omitted.

Faster: `sieve_5M` 0.83x, `string_append_50k` 0.70x, `read_line` 0.49x, `map.int_put_get` 0.73x, `fs.read_file_64k` 0.09x, `string.interpolate` 0.72x.

**Regressions** (same benchmark source at both revisions, confirmed by a second run):

| case | 2026-10-25 | 2026-10-27 | change |
|---|---:|---:|---:|
| `sse.feed` | 930 | 3,926 | 4.2x slower |
| `csv.parse` | 301 | 1,111 | 3.7x slower |
| `toml.parse` | 5,415 | 17,404 | 3.2x slower |
| `yaml.parse` | 8,566 | 24,466 | 2.9x slower |
| `yaml.roundtrip` | 11,140 | 30,336 | 2.7x slower |
| `priority_queue.enqueue_dequeue_100000` | 143 | 227 | 1.6x slower |
| `priority_queue.enqueue_dequeue_400000` | 181 | 274 | 1.5x slower |
| `fs.stat` | 2,296 | 2,953 | 1.3x slower |
| `csv.stringify` | 297 | 358 | 1.2x slower |

The parser-shaped cases (SSE, CSV, TOML, YAML) all slowed by about the same factor, so one shared cause is likely; it is not yet bisected.

JSON throughput was not re-run on `c1b81215` (its JSON bench could not read the corpus here), so it is compared with the recorded 2026-10-25 table, which came from another machine: twitter stringify 851 vs 1,266 MB/s and canada stringify 446 vs 355 MB/s are the largest moves, within what a machine change explains.

The stdlib and web benches did not compile on `dcdaee5d` because of the discarded `Channel.send` check from #1526; main has since fixed them, and the numbers above were taken with equivalent `let _ =` fixes.
