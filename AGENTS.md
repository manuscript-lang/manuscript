# Repository guidance

Manuscript is a statically typed, natively compiled language implemented in C (`src/`). The earlier Rust implementation was deleted; its last commit is `660429d4` and stays in git history. Source `.ms` files are parsed and checked, then compiled to native executables.

## Start each session

- Read [the Manuscript vision](VISION.md) for design direction while respecting current technical contracts. The vision describes aspirations, not evidence of shipped features; verify current behavior against source, tests, and canonical guides.
- Read [architecture](documentation/contributing/architecture.md) and [development checks](documentation/contributing/development.md) for implementation or repository work. Check the relevant source and tests before assuming a documented design is implemented.
- Before implementing or reviewing a change, read [manuscript-change](skills/manuscript-change/SKILL.md), select the workflow skills below, and read the [wiki](design/wiki/index.md) pages it routes to. Read additional skills or checklists if exploration reaches another domain; do not load the whole catalog for every task.
- Apply [language-design](skills/language-design/SKILL.md) (including its taste rules) for language, standard-library, runtime, compiler, or tooling design choices.
- The user's latest explicit direction and current canonical design take precedence over remembered preferences. Historical proposals and assistant completion reports do not establish current behavior. Identify material differences between a newer decision and this checkout.
- Read the [wiki](design/wiki/index.md) for the domains you touch before changing code. When a correction, user decision, or verified failure would change future work, update the wiki in the same change ([protocol](design/wiki/README.md), [record durable lessons](skills/manuscript-change/SKILL.md#record-durable-lessons)): edit the closest page, keep it short, and delete superseded advice.
- Find code and standard-library APIs with `ms search_symbol <name or words>` (project and standard library, fuzzy, bounded output) before reading files or guessing signatures; `ms search_symbol <module>` or `<module>.<Name>` shows a page. `curl -fsSL https://manuscript-lang.github.io/manuscript/install-skill.sh | sh` installs the Manuscript writing skill and concept references for agents (sources: `extensions/agent-skill`).

## Repository layout

- Manuscript is implemented in C in `src/`, layered `base`, `abi`, `runtime`, `compiler/{syntax,project,check,own,lower,mir,opt,emit,link}`, `tooling`, `lsp`, `cli`, `lint`; an include crosses layers only downward, as `src/layers.txt` lists and `ms_lint` enforces. Read [src/README.md](src/README.md) for the build (`make build`, or `cmake --preset ci && cmake --build --preset ci`; clang and Ninja) and the conformance target. Lint caps every C file at 1000 lines. The Rust and Go implementations were removed; fixtures are recorded from the C `ms` (`ms run tools/conform-run.ms -- --record`), and `git show 660429d4:<path>` reads the Rust history.
- Standard-library declarations live in `src/stdlib/` (`*.ms`) and are embedded by the C build. Conformance fixtures live in `tests/conformance/`; `.msversion` holds the release version.
- Performance and agent evidence lives in `bench/perf/` and `bench/agent/`, each suite with its run script. `bench/perf/` commits dated result pages naming the revision and machine, and a speed claim in the README, website, or vision cites one of them; rerun the suite and add a dated section rather than editing old numbers. Agent-benchmark results are not committed. The one agent claim documents may make is that pass rates match Go, Rust and TypeScript; do not quote first-build rates, which measure model familiarity, not language quality.

## Shared guidance and checks

- Standing owner rules (speed as fast as C, general passes, checked-C benchmarks, specific errors, no GPL/LGPL, ask before any dependency, in-process LLVM with child `lld`, auto-merge, stacked PRs, parity, workarounds, Manuscript first, no new dependencies without asking, memory model, glibc floor, thread state): read [standing project rules](design/wiki/repository/standing-project-rules-from-the-owner.md).
- Every PR, however it is opened (including by an agent harness that supplies its own body format): read [create-pr](skills/create-pr/SKILL.md) first, use its four-section body (Problem, Proposed change, Alternatives considered, Testing), open it ready for review, and enable squash auto-merge.
- Before any change that touches large parts of the codebase across multiple packages (for example a new representation, layer, or pass, or a restructure), write a proposal in `design/proposals/` (target 60 to 100 lines) with [author-proposal](skills/author-proposal/SKILL.md) and validate it yourself before implementing: the problem, the concrete benefit with evidence (measurements, or code the change removes), and the alternatives, including doing nothing, after a pass on what can be simplified. Have an independent skeptical reviewer subagent challenge the evidence and the do-nothing case, and build only if the proposal survives. Do not implement first to find out whether it helps. Ship the proposal in the same PR as its implementation, never as a proposal-only PR. Ask the user only when the change alters the language or user-visible behavior; a PR the user has put on hold stays unmerged (disable its auto-merge) until they say otherwise. A perf PR cites a before/after run against the latest dated baseline in `bench/perf/`.
- Perf benchmarks: keep the Manuscript, Rust, Go and C versions of a benchmark as close to each other in design as possible (same algorithm, data layout and concurrency shape), so a gap is the language and not the program. Prefer realistic workloads over pathological ones; a stress test of one primitive (such as 100k one-microsecond tasks) is a probe, not a headline benchmark. Compare speed only with Rust, C or Go; Python is a source of correct answers, never of timings.
- Root-cause fixes only: no special case keyed on a name, an op shape or one benchmark or test. Fix the general layer; if only a hack fits, report it instead of shipping it ([rule](design/wiki/repository/fixes-address-the-root-cause-not-a-name-or-shape.md)).
- Perf measurement: shared VMs are noisy, so use many runs (median) or instruction counts (`valgrind --tool=callgrind`), not one wall-clock run. Perf designs are portable and data-oriented (flat arrays and indices); add a cache only when measurement shows a redesign cannot match it ([wiki](design/wiki/benchmarks-and-performance/perf-work-follows-data-oriented-design-and-removes-caches.md)).
- Issues: add the `in progress` label before fixing one, remove it when the PR merges, and close every issue the fix resolves (verify each is closed) ([fix-issue](skills/fix-issue/SKILL.md)).
- Platform parity: Linux, macOS, and Windows stay at parity. Never skip, gate, or no-op a test on a platform without the user's approval; fix the cause. PR checks run Linux only and `main` runs all six platforms on a schedule, so a platform-sensitive change needs the Windows or macOS CI dispatched on its branch before it is called fixed ([create-pr](skills/create-pr/SKILL.md#merging)).
- Do not consult other models for decisions or reviews; bring choices to the owner. Never special-case a test, fixture or program anywhere.
- Workarounds: a workaround for a bug in Manuscript or a dependency gets an issue that names the removal condition, and is deleted once the fix is on `main` (example: the macOS `-ignore_optimization_hints` lld flag, #1748).
- Prefer Manuscript: put behavior in stdlib `.ms` and derive classifications from declarations, not C name lists. C holds small, general runtime primitives; move tooling and tests into `.ms` where it makes sense.
- Test budget (strict): pull request CI is two jobs, one per Linux arch (`.github/workflows/ci.yml`), each building with `cmake --preset ci` and running `ctest`, `lint`, `dist-smoke`, `repo-check`, `docs-check` and `conform`, under 10 minutes (the `Time budget` job fails a PR whose `linux-*` job passes 600 s). No sharding of the two legs and no per-platform skipping. A new test must fit the budget or something else is cut; cut by removing redundant work, not by shrinking test inputs ([ci-time](skills/ci-time/SKILL.md)). Details: [PR CI budget](design/wiki/repository/pull-request-ci-has-a-ten-minute-budget.md), whose measurements predate the C implementation. Tutorial and stdlib example tests run on PRs only when documentation, stdlib or the example test changes.
- Fewer, larger PRs: combine related stages into one PR rather than a chain of small ones. Search open PRs and issues first so work is not duplicated.
- Fault exit statuses are C-style, from `FaultKind::exit_status` in `ms-rt-abi`: 134 for a fault, 139 for a stack overflow or out of memory, the same on every platform. Never write 67 or any literal status in code, tests or docs; use `ms_rt_abi::EXIT_ABORT` and friends ([wiki](design/wiki/runtime/faults-and-test-failures-reach-the-cli-as-a-record.md)).
- Nested `match` is an anti-pattern. Keep implementation, examples, and diagnostic remedies flat: bind a payload with an early exit, use compatible `?`, or call a small helper. `make repo-check` guards source and Markdown fences; intentional syntax/semantic regressions need a scoped test allowance with a reason. The grammar remains unchanged. See [flat match flow](documentation/core-language/control-flow/pattern-matching.md#keep-match-flow-flat).
- Shared skills live in `skills/`; `.agents/skills/` and `.claude/skills/` link to the same folders for Codex and Claude discovery. Read selected `SKILL.md` files and relevant evidence links. Keep discovery links synchronized when adding, renaming, or removing skills.
- `AGENTS.md` is the sole source of repository guidance. `CLAUDE.md` contains only `@AGENTS.md` so Claude Code, which loads `CLAUDE.md` and not `AGENTS.md`, reads the same file; add no other content to it.
- Skills describe workflows, `design/wiki/` ([index](design/wiki/index.md)) preserves decisions, reasons, and failure modes for agents, and `documentation/` owns exact rules. All standard-library documentation belongs in `src/stdlib/*.ms`, including guide comment blocks; generate disposable book Markdown with `make docs`.
- Keep skills concise and specific to Manuscript. Do not reinstall generic collections during routine setup. [Skill maintenance and history](skills/README.md) records why this catalog exists.
- Run checks appropriate to the changed behavior from the current Makefile; C changes add `ctest --preset ci` and the `lint` target (`cmake --build --preset ci --target lint`); behavior changes add the `conform` target. `make verify` is the routine gate; `make verify-full` adds the conformance corpus, every e2e fixture, book, and distribution checks. Guidance-only edits need reference/discovery validation and license freshness when notices change.
