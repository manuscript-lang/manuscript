    Scope and implementation order#

    Guide index · Chapter index · Design index

    Use this page to see which parts of the design depend on others and which decisions remain open. The implementation order starts with language checking, adds runtime and library behavior, then builds tooling on those checked facts.

    Implementation order#

    1. Parse and check the language, including named calls, exact types, contracts, captures, and sharing.
    2. Implement lexical cleanup and atomic start, cancellation, completion, and close transitions together.
    3. Connect standard imports, data operations, CLI host, streams, and adapters; validate complete programs.
    4. Complete the queue, pool, builder, HTTP, and subprocess APIs using the same lifetime and cancellation rules.
    5. Build source tools, diagrams, traces, and debugging on checked compiler facts and matching runtime metadata.

    Use the semantic tests and complete programs to check that these parts agree. A written acceptance case becomes evidence only when an implementation runs it and records the result.

    Outstanding decisions#

    These gaps still need concrete contracts.

    AreaDetails still neededAuthoritative page
    Test runnerDiscovery, test identity, duplicate names, isolation, authority inputs, expected faults, and build inclusionSemantic tests
    Build distributionExternal adapter/dependency locks and supported debugger distributionReproducibility
    Native adapter ABIGenerated Go declarations, receiver construction, disposer types, and compatibility validationAdapter manifests
    Capability analysisClassification of adapter interfaces, pure contracts, wrappers, and indirect authorityAuthority
    Queue extensionsBlocking channels and wakeup policies beyond the local FIFO contractQueues
    Pool extensionsNative resource factories and additional lease contractsSynchronized values and pools
    Builder extensionsAdditional bulk mutation operations beyond sealed snapshot constructionBuilders
    HTTP and subprocess extensionsAdditional host contracts, interactive subprocess streams, and uniform cross-platform descendant supervision; current HTTP clients, streaming hosts, and WebSockets are covered in package coverageHTTP hosts , streams
    Source toolsRich diagnostic spans, transactional structural edits, and failed-write recoverySource tools
    Diagrams and debuggingStable node identity, diff/trace formats, stepping behavior, value rendering, and supported debugger versionsDeveloper tooling

    For each gap, add exact signatures or data fields, success and failure behavior, an accepted example, and a boundary or rejected example to its concept page. Then add observable conformance expectations. Other guides should link to the rule rather than repeat it.

    Unsupported features#

    Actors, detached tasks, task adoption, racing combinators, inheritance, macros, operator overloading, implicit conversions, and user-defined metaprogramming have no supported forms. More specific syntax exclusions appear on the relevant concept pages.

    Forced task termination is unsupported. Uncooperative work can delay joining indefinitely; host escalation is an incomplete shutdown, not successful cleanup. See cancellation and background shutdown .
