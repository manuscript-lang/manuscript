    Type compatibility and expected types#

    Core language guide · Chapter index · Design index

    The type you provide must match the type required at that position. This applies to variable annotations, assignments, arguments, returns, fields, and collection elements. For example, an Int cannot silently become a Float, and two records do not become interchangeable just because their fields match.

    The exception is an expression of type Never: it cannot produce a value, so it can appear where any expression value is expected. This exception does not make differently declared function types interchangeable.

    Exact and nominal identity#

    Type formIdentity and compatibility
    Built-inFixed compiler or standard identity
    Record or alternativeDefining module, declaration, and ordered type arguments; matching fields or cases do not establish compatibility
    Contract viewNominal contract application, plus whether it is plain or shared; conversions are explicit
    Generic applicationExact declaration and every ordered argument; List[Int] and List[Float] are distinct
    FunctionExact parameter labels, declaration order, parameter types, and result type; no variance or label/order adaptation

    Caller-written argument order affects evaluation without changing function identity. A generic bound grants properties, not subtyping. Shared/plain arguments remain distinct during inference; List[Contract] fails its element bound, while List[Contract & Shareable] may satisfy it.

    Type positions use ordinary name resolution . A value shadowing a type name causes an error, not a second lookup in a hidden namespace. Unqualified cases follow alternative lookup ; expected types cannot override a lexical binding or choose an ambiguous case.

    Shareable, Equal, and Hashable are compiler bounds , not standalone value types. The only value-type refinement is Contract & Shareable; other intersections and refinements are rejected.

    Manuscript
    fn identity(value: Int) -> Int:
    return value

let exact: fn(value: Int) -> Int = identity
# Rejected: amount differs from value.
let relabeled: fn(amount: Int) -> Int = identity

    There are no implicit numeric conversions, optional wrapping/unwrapping, result wrapping, structural record conversions, unions, or nullable references. An integer literal has type Int even under an expected Float; use the explicit conversion API . The type checker does not choose an arbitrary common type for incompatible values.

    Propagating context#

    An expected type comes from the place a value is used: a local annotation, assignment target, return declaration, parameter after generic substitution, record field, or alternative payload.

    That type can guide the expressions inside parentheses, list elements, constructor fields, and case payloads. It can supply missing type arguments for a uniquely identified constructor such as none, ok, or error.

    Context does not resolve an ambiguous unqualified case name or change a type an expression already determines for itself.

    Manuscript
    type Input:
    names: List[Optional[String]]

let input = Input(names: [none, some(value: "Ada")])
let nested: List[List[Int]] = [[], [1]]
let success: Result[Int, String] = ok(value: 1)
let failure: Result[Int, String] = error(cause: "unavailable")
# Rejected: the result error type cannot be inferred from ok's payload.
let incomplete = ok(value: 1)

    The compiler rejects expressions whose type cannot be determined. It does not silently assign a dynamic or unknown type.

    Expression without an annotationWhat can be inferred
    none or []Not enough information to determine the payload or element type.
    ok(value: 1)The success is Int, but the error type is still unknown.
    some(value: 1)The complete type is Optional[Int].
    [none, some(value: 1)]The typed some value supplies enough context for List[Optional[Int]].

    A list is rejected if its independently typed elements disagree.

    Operators and try do not pass an expected result type backward into their operands. Their operands must determine their own types first. For example, knowing that the value unwrapped by try should be Int does not tell the compiler which error type an incomplete Result constructor should have.

    Manuscript
    fn known() -> Result[Int, String]:
    let number: Int = try Result[Int, String].ok(value: 1)
    return ok(value: number)

fn unknown() -> Result[Int, String]:
    # Rejected: the try operand's error type is undetermined.
    let number: Int = try ok(value: 1)
    return ok(value: number)

    Similarly, an expected Bool cannot make [] == [] well typed; neither operand determines a list element type. Explicitly qualify or annotate operands when their types would otherwise be incomplete.

    Never operands use the operator candidate rules . Those rules select a required operand type locally; they do not infer it backward from an expected result.

    Generic function inference uses supplied argument types only, as specified in generics . An expected return type does not infer missing function type arguments. A generic function value must be explicitly specialized before an expected function type can check it. Anonymous functions still require their own explicit parameter/result types.

    Validation boundaries#

    Every declaration’s referenced types must resolve and every application must satisfy arity and bounds. Generic bodies are checked under declared bounds. Public signatures satisfy public type visibility , and recursive concrete layouts satisfy guarded recursion . These checks precede lowering and do not rely on Go’s structural interfaces or implicit assignments.

    Runtime cancellation and resource closed-state errors do not alter static assignability. Their separate contracts remain governed by the existing runtime and reference chapters.
