# Rust and Cranelift implementation: design contract

This describes the Rust and Cranelift implementation. Current ownership rules live in [OWNERSHIP.md](ms-check/OWNERSHIP.md); exact runtime layouts and symbols live in [ABI.md](ms-rt/ABI.md) and `ms-rt-abi`.

## Decisions (taken 2026-10-19, owner direction: keep today's behavior, maximum native speed)

1. **Memory model: the proposal's value semantics, adopted by the owner on 2026-10-19.** Values have one owner and are dropped deterministically at scope end (the `lastuse` MIR pass moves the drop of a plain-memory value, such as a string, list, map or record of those, to its last use, including uses of anything that may point into it; resources, closures and handles keep scope-end drops); no tracing collector and no reference counting for ordinary data. Records, lists, maps, sets, strings, bytes and alternatives are values: plain values (scalars, records of scalars) copy implicitly, strings and everything holding one move (2026-10-22: a borrowed string stored into an owned position needs an explicit `.clone()`, so the copy cost is visible), others move at their last use into a moving position, and `.clone()` duplicates explicitly (the current spelling of planned `.copy()`). `:=` is immutable including contents. Mutation uses **`var`** (kept from today instead of the proposal's `mut`, to limit churn): `var` bindings and `var` parameters (marked at the declaration and at the call, `f(var xs)`) may change, and a `var` argument may not overlap another argument. There is no shared mutable value: concurrent code reads what it captures and sends changes to the owner over a `pipe`. `Weak[T]` and `Arena[T]` with generation-checked `Id[T]` are planned (source using them reports `unknown type`). Borrows are lexical (match/if-let payloads, loop variables, `with` bindings, accessor results): the borrowed root may not be mutated or reassigned while the borrow is live; no lifetimes appear in source. Strings are owned values like lists: one owner, moved at last use, duplicated only by an explicit `.clone()`, and read through immutable borrowed views that keep their source unchanged while they live. String buffers are uniquely owned: a copy allocates and a drop frees (`proposals/two-word-string.md`). The checker implements exclusivity, projections/accessors, mutator results returning Unit, closure escape, and handle classification as described in `crates/ms-check/OWNERSHIP.md`. **Amended 2026-11-01 (`proposals/reference-ownership.md`, owner direction: reference semantics with one owner and no reference counting):** only primitives copy implicitly; a record is a container with one owner like a list, so records of scalars no longer copy. Binding a name to another name borrows it (`:=` shared, `var` exclusive when the source is a `var`), and a `var` binding of a primitive part copies it. A function whose every return path is a part of a parameter or the receiver returns a borrow of that part without a marker (inferred; mixed paths are an error with a `.clone()` remedy; lambdas, interface implementations and resources own their results; a borrowed value converted to an interface on the way out is an owned view of the arguments, `ret_view`); the MIR function carries `ret_borrowed` and callers hold the result as a borrow. Native borrows (`Map.get`, `List.first`, `List.last`) are held as borrows, and `if var x = m.get(k)` changes the entry in place.
2. **Ownership checking.** Ownership/exclusivity is a separate pass on checked HIR. Lowering uses its move, borrow, mutation, and drop facts; standard-library mutators use `var` receivers and return Unit.
3. **Faults** abort the process after running scope-end cleanups in reverse order (a runtime cleanup stack, no frame unwinding in generated code). `ms test` runs each test file in its own promise (`@std/test/runner.ms`); a fault ends that promise, so it fails the running test and ends only its file. Recursive call graphs use a stack-pointer limit check at function entry; non-recursive call graphs omit it.
4. **Promises, no language-level concurrency.** `ms-rt/src/task.rs` runs stackful coroutines parked on descriptors, timers and tokens, with a blocking thread pool (`MS_POOL_THREADS`) for work the kernel cannot wait on: DNS, and file-system calls and regular-file reads and writes. Work is started only through standard-library calls that return a `Promise[T]` and `promise(fn: ...)` in `@std/concurrency/promise.ms`; the language has no `spawn`. A promise reads what it captures, `wait` gives the result, and dropping an unfinished promise cancels it and waits for it to end; a fault ends only that promise. Signal and shutdown cancellation is one global flag checked by runtime calls and I/O, not on loop back edges (atomic relaxed load). The earlier task groups, worker threads, process groups and channels (`proposals/taskgroup.md`, `proposals/channels.md`, `proposals/worker-threads.md`) were removed; history is in git.
5. **Native tool: `ms profile`** replaces the debugger (the debugger and DAP are dropped). It captures sampling profiles of a native program (folded stacks, pprof-compatible output and a `perf` map file) using frame pointers plus a PC-to-source table. `perf record` works on any `ms build` output because the compiler keeps frame pointers and emits a perf map and DWARF line tables.
6. **Linking** runs a pinned static `lld` that `ms` downloads into its cache on first use (released by manuscript-lang/llvm-bundle, pinned by checksum in `toolchain/lld.lock`). Linux links dynamic executables against stubs of glibc 2.28 generated from `toolchain/glibc/<arch>.symbols` (the runtime archive defines `_start`), so they run on glibc 2.28 or newer, or with `--static` static musl executables over the startup files and libc that `crates/ms-clif/build.rs` copies from the Rust toolchain; macOS links against `.tbd` stubs generated from the symbols the program imports. Windows links the mingw-w64 CRT and import libraries from the pinned llvm-mingw release (`toolchain/fetch-mingw.sh`), with the runtime built for `gnullvm` (see `proposals/bundled-linker.md`).

## Pipeline and crates (`crates/`)

```text
.ms -> ms-syntax (lex, parse, AST, format)
    -> ms-check  (resolve, types, generics, contracts, effects, cleanup; typed HIR; diagnostics)
                 (public surface: `ms_check::api` only; every other module is private)
    -> ms-lower  (checked HIR and ownership facts to MIR, native standard calls)
    -> ms-mir    (representation, ownership elaboration, optimizer, verifier, text format, interpreter)
    -> ms-clif   (MIR -> Cranelift -> object file; line tables; perf map)
    -> linker driver + ms-native (ms-rt and the ms-std-* crates in one static library, embedded in ms) -> executable
tools: ms-driver (manifest, aliases and import resolution in `project`; module graph loading, entry rule, checking), ms-build (lowering seam, optimize, codegen and link; the `ms build/run/test/profile` engine in ms-cli sits on it), ms-tooling (lint, inspect, review, diagram; agent guide, `search_symbol` standard-library lookup, docgen), ms-lsp, ms-cli (`ms`), ms-conform (conformance runner)
```

Keep public crate APIs small and documented with rustdoc; cross-crate changes must preserve the shared ownership and runtime ABI contracts.

## Value representation (word-level, 64-bit targets)

- `Int` i64 (checked arithmetic faults on overflow), `Float` f64, `Bool` i8 (0 or 1), `Unit` zero-sized. `Int8`/`Int16`/`Int32`/`Float32` are `i64`/`f64` in registers and 1/2/4/4 bytes in memory (leaves `N8`/`N16`/`N32`/`F32`: sign-extended or promoted on load, reduced or demoted on store); their descriptors are `POD`, and `Float32` uses `msrt_desc_float32`. A record of only `Int`, sized ints and `Bool` with no padding and no `Equal`/`Hashable` methods (a plain key) gets a `POD` descriptor with no `eq`/`hash` glue (`Cx::ensure_glue`), and `ms-rt/src/map.rs` hashes and compares such map keys as one blob of `size` bytes (`BlobKey`). The map's internal hash is not the derived `hash` of the type.
- Generated values are flattened into scalar leaves in registers and naturally aligned slots in memory; see `ms-mir/src/layout.rs`.
- `String` is an owned two-word `{ ptr, tagged }` value whose `ptr` addresses immutable UTF-8 bytes; `tagged` is the byte length with an ownership tag in its top two bits (`00` owned, `01` inline, `10` static, `11` view). Moving transfers the buffer, a copy (`.clone()`) allocates and copies it, and dropping frees it; statics are shared and never freed, and views borrow another string's bytes. A string of at most 15 bytes is stored inline in the two words, so it copies bitwise and never allocates. `String?` reuses the two words with None as `{0, static}`. Lowering hands out views where the source provably outlives the result unchanged (`trim`, `split` lists read in place, map keys and reads out of read-only parameters). Shared objects and closures have reference-counted headers; ordinary owned values do not.
- `List[T]`, `Bytes`, and `StringBuilder` use an owned three-word `{ ptr, len, cap }` value. Elements occupy the monomorphized layout of `T`; generic runtime operations receive an explicit `TypeDesc` with size, alignment, drop, equality, hashing, and copy operations.
- `Map[K, V]` and `Set[T]` use an owned seven-word `MapVal` with ordered slots and a lookup index. Their owner drops elements and frees the buffers.
- Records flatten their fields in declaration order. Alternatives carry a tag and shared payload slots; recursive alternatives are boxed to make their layout finite.
- `T?` uses a nullable pointer for a single-pointer payload, otherwise a presence flag and the payload leaves. Recursive optional layouts use indirection (`ms_mir::ir::Boxing`, shared by lowering and codegen). `Result[T, E]` uses the alternative layout. A container read the checker holds as a borrow (`x := m.get(k)`, `if x := xs.first()`) lowers to the entry's address and `opt.view`, an optional that borrows its payload and is never dropped; a boxed optional cannot be borrowed. A borrow-returning function that wraps its borrowed part (`return ok(self.name)`, `return self.items[0]` as `T?`, `try` of a borrowed error) builds the wrapper with `opt.view` or `alt.view` the same way (`Op::AltView`, `result_mode` Borrow).
- Interfaces use `{ data, vtable }` values: `data` is a heap box of the payload's leaves, `vtable` a pointer to `[drop, methods.., copy]` (8-aligned). The vtable word's low two bits say what the value owns: `0` the box and its payload (`iface.new`, drop calls vtable[0]), `1` only the box (`iface.borrow`: the leaves belong to a value the checker holds borrowed; drop frees the box), except that a borrow whose result reaches only calls (not view returners) and drops keeps its leaves in a stack slot and carries `2`, `2` nothing (`iface.view`, a plain reference handed on by a borrow-returning view function). Dispatch, `iface.is` and the copier mask the bits, and a copy always yields tag `0`. An interface with a `var fn` operation is never borrowed (`contract_mutates`): a method writing into a box of borrowed leaves would free the owner's value. A function returning a view carries `Func.ret_view`: its result is owned (dropped by the caller) and points into its arguments, which `lastuse` and `copyelim` (`Module::result_views`, the view taint) respect. Function values refer to closure objects. Non-escaping closures borrow captures; escaping closures own them, as described in the ownership rules. A `closure.new` whose result only reaches drops, calls, and arguments a callee borrows (and whose callee result is not a view) keeps its object in a stack slot of the creating frame (`framed_closure_objects`): its drop entry is `ClosureDropFramed`, which drops the captures and frees nothing, and a clone always installs the heap drop entry. A closure with a capture closer keeps its heap object.
- Local extensions (an implementation for another module's type) no longer exist in the language; the scoped-descriptor code below predates their removal. They were visible only in their own module. Lowering keys vtables, equality helpers and type descriptors by the module whose implementations they call, but only for types that have an extension (`crates/ms-lower/src/scope.rs`); a generic instance over such a type is separate per caller module. MIR names a scoped descriptor with `Ty::scoped`.
- Generics are monomorphized.

## Runtime ABI rules

- Runtime symbols use `msrt_`; native standard-library symbols use `msstd_`. `stdlib/*.ms` owns public signatures and names its native symbols with `extern fn`.
- Scalars cross the C-layout ABI directly. Aggregates cross by pointer, and constructed aggregates use a trailing output pointer. Fallible calls use status codes and outputs; see [ABI conventions](ms-rt/ABI.md#1-conventions).
- Arguments are borrowed unless documented as consuming; `var` receivers are exclusive mutable pointers. Returned values are owned, while source operations that return a borrow keep the borrow relationship checked by `ms-check`.
- `ms-rt-abi` defines shared layouts and constants; its layout tests keep compiler and runtime assumptions aligned.
- Layering: `ms-rt-abi` < `ms-rt` < `ms-std-*` < `ms-native`. `ms-rt` is the only crate that defines `msrt_*` symbols and also exports the safe helpers the native crates use (`ms_rt::ffi`: the `native!` macro and value marshalling; `ms_rt::glue`: strings, faults, cancellation, task waits and the blocking pool). A native crate calls those as Rust items, so a signature change is a compile error, not a link-time surprise. `ms-native` is the only staticlib; `ms-rt` is an rlib, and its `testing` feature turns faults into panics for tests that drive the natives through the C ABI. `ms-decimal` sits beside them: pure Decimal arithmetic shared by `ms-std-decimal` (C ABI shims) and `ms-lower` (literal folding), so the compiler never depends on a runtime crate other than `ms-rt-abi`.

## Pure and stateful runtime code

Release builds optimize the program with LLVM, which sees the runtime only as opaque calls into `libms_native.a`. The runtime is therefore split by one rule.

- **Pure** helpers live in `ms-rt-hot` and are inlined into the program. A pure function reads only its arguments and the memory they point to and writes only an output argument. It owns no `static`, thread-local, atomic or lock, allocates nothing, faults nothing, calls no descriptor callback that could run user code, and uses no `global_asm!`, `#[link_section]` or other symbol that must exist once. Today: map probes (`get`, `get_ptr`, `contains` for `Int` and `String` keys with word values, `entry_ptrs`, `length`, `slot_count`), string equality, comparison, hashing and ASCII scalar reads (string length is emitted inline by the LLVM emitter, with `msrt_string_length` in `ms-rt` for non-ASCII text). The crate has no dependency except `ms-rt-abi`, and `ms-rt` calls the same functions, so the archive and the inlined copy have one source.
- **Stateful** code stays in `ms-rt` and links as the archive: allocation, strings and lists that build or free, faults and cleanups, I/O, tasks, startup. Duplicating any of it would duplicate its statics (an earlier whole-runtime LTO attempt printed nothing for that reason), so nothing stateful moves into `ms-rt-hot`.
- **Signatures are integers only.** Generated code declares every runtime symbol with `i64`/`i8` types, and LLVM inlines a call only when the callee's type is identical, so exported `ms-rt-hot` functions take and return `usize` (not pointers) and `u8`/`i64`.
- `cargo xtask runtime` also compiles `ms-rt-hot` to LLVM IR for the runtime's target and writes `target/ms-native/ms_rt_hot.ll`: target triple, data layout and `target-cpu`/`target-features` removed (LLVM refuses to inline across a CPU attribute mismatch), every function `alwaysinline`. `ms-clif` embeds it with `llvm-link` (its build script). `ms build --build-type Release` runs `llvm-link --only-needed --internalize` of that IR into the program IR before `opt`, only for programs that call one of its functions, so internalized copies are the only definitions in the program and the exported symbols still come from the archive.
- **Where a new function goes.** `ms-rt-hot` is being retired (`proposals/retire-ms-rt-hot.md`): do not add to it. First, can a stdlib `.ms` body express it (a scan, a compare, a short search)? Then it is Manuscript, not Rust. Check the ownership contract first: the checker treats natives such as `List.first`/`last` as borrows of their receiver, and a `.ms` body returns an owned value (see `wiki/benchmarks-and-performance/hot-string-fast-paths-live-in-ms-rt-hot-with-a-slow-twin.md`), so a native keeps its borrow only while it stays a native declaration: LLVM sees it as ordinary program code. Rust is for what `.ms` cannot express (layout-dependent probes, descriptor-driven access, SIMD or libc calls). For those, ask in order; the first "no" puts it in `ms-rt`.
  1. Is the common case free of allocation, `static`s, locks, descriptor callbacks that run user code, and `global_asm!`? If the cost sits in the rare case, split it: the fast case goes in `ms-rt-hot`, the rest in an `ms-rt` twin named `*_slow` (or `*_long`, `*_far`) that the hot function calls through an `extern` declaration. Faults count as a rare case: the hot function calls the faulting twin.
  2. Is it small and called per element, per line or per probe (a bounds-checked read, a compare, a short scan, a hash)? An operation that spends its time in one large call (a sort, a `memmem` over a long text, a number format) gains nothing from inlining and stays in `ms-rt`: it only grows every program's IR.
  3. Does its fast case need only integers, pointers as `usize` and the layout in `ms-rt-abi`? A function that needs `ms-rt` types or a third-party crate (`memchr`) keeps that part in the twin.
  Stays in `ms-rt` whatever the answers: allocation, building or freeing lists, strings and maps, anything that reads or writes a `static` or thread-local, I/O, tasks, startup, and everything a native `ms-std-*` crate reaches through `ms_rt::ffi` or `ms_rt::glue`. An element copy that may allocate (`String`, list and map elements) is a twin: the hot function inlines only the word-sized `Int`, `Float` and `Bool` slot (`word_slot`).
- **Signature and flag traps** (found by the native-fallbacks audit, `bench/perf/native-fallbacks/README.md`). The hot function's return type must equal the one the call site declares, including an `extern fn` that returns `Result` (that is `i64`, not `u8`): a mismatch silently keeps the call. Check a new function with `MS_KEEP_LL=1 MS_BACKEND=llvm ms build` and look for the call in the IR. A function flagged `pure` gets `memory(read)`, so it must not write an out pointer; flag only functions that return their result.
- `MS_RT_HOT=0` turns the link off (to compare compile and run time); `MS_RT_HOT=<file>` links another helper library.
- Adding a function: it must satisfy the purity rule and the integer-only signature; keep a Rust-side wrapper with pointer types for unit tests in `ms-rt/src/testutil.rs`. Measure instruction counts (`valgrind --tool=callgrind`) and compile time before and after: inlining grows the module, which costs `opt` and `llc` time on map-heavy programs.

## Quality bars

- Every crate: `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test` green; no `unsafe` without a `// SAFETY:` comment; tests beside code.
- Diagnostics (message, position, phase, JSON shape) are pinned by the conformance corpus.
- Performance claims need numbers from `bench/perf` on the same machine.
