# Tests

`make conform` replays the correctness suite against the `ms` just built; `ctest --preset ci` runs the C tests. Programs paired with frozen expectations are the contract for `ms`. `ms` passes the suite apart from fixtures tagged `aliasing`, which the value-semantics migration changes on purpose, and the entries in `expect-fail.txt`.

```sh
make conform                                              # builds ms, then replays the suite with tools/conform-run.ms
ms run tools/conform-run.ms -- --phase check ownership    # one phase, fixtures whose id contains the text
```

## Layout

A fixture id is its path under `tests/` without extension. A `check` fixture states what it expects in its own file: the last lines are `// expect-error: <code> <line>:<col>[-<line>:<col>] <message>` (one per diagnostic, with `// expect-fix: <span> "<replacement>"` after one that offers a fix) and `// expect-exit: <n>` when there is no diagnostic or the exit code is not 1; they follow the program, so their line numbers are the file's own. Other phases use the same trailing block: `run` has `// expect-exit: <n>` and `// expect-stdout: <line>` / `// expect-stderr: <line>` (`-partial` when the output has no final newline); `test` has `// expect-exit:`, `// expect-tests: passed=<n> failed=<n>`; `parse` has diagnostics plus `// expect-format: unchanged|rewritten` (then `// expect-formatted:` lines) or `// expect-format-exit: <n>`. A project directory keeps its lines at the end of `conform.meta`. No fixture has a JSON sidecar (see `design/proposals/readable-conformance-tests.md`).

| directory | contents |
| --- | --- |
| `lang/<feature>/` | Programs that run: `test` blocks and recorded runs, grouped by the feature their first tag names (`ownership`, `lists`, `closures`, `faults`, ...; `misc` when none). |
| `lang/stdlib/` | One program per behavior of a standard-library module, named `<module>-...`; `support/` holds the modules they import. |
| `lang/projects/<name>/` | Multi-file programs, each a directory with `conform.meta` and `ms.toml` (or a loose `*-main.ms` with its siblings). |
| `lang/fuzz/{run,types,syntax}/` | Generated by `ms run tools/conform.ms -- fuzz-gen`; do not edit by hand. |
| `diagnostics/{syntax,names,types,ownership}/` | Rejected programs by the family of their first code (`MS1xxx`, `MS2xxx`, `MS3xxx`), named `<code>-<message words>`. |
| `diagnostics/accepted/` | Programs the checker must accept without a diagnostic. |
| `format/` | Programs `ms fmt` must rewrite or reject. |
| `commands/` | Recorded `ms` command runs (`tools/command-fixtures.ms`). |
| `checks/` | Programs with their own gate: ownership counts, scaling, removed spellings, glibc floor, MIR verify. |
| `lsp/`, `docs/` | Language-server tests and documentation-site tests. |

A header `phase=test,parse` names more than one phase: the first is the recorded one, and each later phase applies its default expectation to the same file (for `parse`, a clean parse that `ms fmt` leaves unchanged), so a formatter check needs no `-fmt` copy of the program. Metadata lives in `// conform: key=value` lines at the top of the file (or in `conform.meta`): `tags`, `phase`, `origin`, `args` (JSON array), `timeout` (seconds), `entry`, `deterministic`. The header is part of the source, so diagnostic positions are those of the file as stored.

## Phases

| phase | command | compared |
| --- | --- | --- |
| `parse` | `ms check --only types --json`, `ms fmt` | parse-phase diagnostics, formatted source |
| `check` | `ms check --only types --json`, `ms check` | diagnostics (code, phase, message, position), terminal text, exit status |
| `run` | `ms run` | stdout, stderr, exit status |
| `test` | `ms test --json` | per-test results, summary, report shape (durations stripped) |

Paths under the work directory print as `<DIR>`.

## Tags

Feature: `lexer layout parser formatter types generics interfaces closures match destructuring try-result optional scope-cleanup faults strings lists maps sets numbers decimal interpolation records alternatives control-flow functions modules projects diagnostics mutation json-protocol docs examples testing cli`; standard library: `stdlib-<module>`; kind: `perf fuzz bench`.

Tier: `tier-core` imports nothing, `tier-stdlib` imports only pure modules, `tier-io` touches files, network, processes, time or randomness.

`aliasing` marks programs whose answer may depend on assignment sharing or `.clone()`. The harvester tags by heuristic (over-tagging is safe); these fixtures are excluded from the gate. Review the tagged set, and tag by hand where the heuristic misses, with `// conform: tags=...,aliasing`.

## Commands

`tools/conform-run.ms` replays the corpus against the `ms` built from this tree and prints `<phase>: passed/total` with one `FAIL <id>` line per difference (`CONFORM_DIFF=1` shows expected and observed output). `--phase`, `--jobs` and fixture id substrings select; `MS` names another binary. `tools/conform.ms` has the other corpus commands: `list` and `stats` (fixtures by phase and tag), `lint` (headers, tags and expectation files; `make conform` runs it, so a fixture with a new tag also adds the tag to `tools/conform/tags.ms`), `retag` (recompute `tier-*` tags from imports), `diff` (two `ms` binaries or build types on the same fixtures), `fuzz-gen` and `fuzz` (deterministic generated programs, written into the corpus or run under `--oracle` and `--ms`, which the oracle's observation decides), and `harvest` (turn repository sources and documentation fences into fixtures; record them with `--record --prune`). The Rust `ms-conform` they replace is at commit `660429d4`.

## Adding and refreshing fixtures

A new behavior test goes in `lang/<feature>/` (or `lang/stdlib/`) as an in-source `test` with `expect_equal` and `phase=test`; a rejected program goes in `diagnostics/<family>/` (`phase=check`, then `--record --inline`), and a multi-file program in `lang/projects/<name>/` with `conform.meta`. Modules that single-file fixtures import live in a `support/` directory beside them (not fixtures). This corpus is the one test runner for `.ms` behavior.

1. Write the `.ms` file with a `// conform:` header, choose tags and phase.
2. `ms run tools/conform-run.ms -- --record --only-missing <slug>` writes the expectation (`--inline` writes the `// expect-` lines); each fixture is observed twice and refused if the answers differ (`deterministic=true` skips this for time- or random-dependent output you have normalized; `--no-stable-check` skips the second run). `--prune` deletes fixtures that cannot be recorded.
3. Review the expectation. It records what the binary does, bugs included; a fixture that pins a bug keeps its expectation and joins `expect-fail.txt` with a reason.
4. Fixtures whose output varies between runs (for example diagnostics emitted in map order) must be deleted, not recorded.

## Hostile fixtures

Programs importing `http`, `net`, `tls`, `websocket`, `sse`, `process`, `terminal`, `system`, `random` or `time` are checked but not run by the harvester, since they bind sockets, wait on signals or depend on the clock. Add run fixtures for them by hand with deterministic output.

Changing a fixture's `// conform:` header shifts byte offsets in its diagnostics, so re-record after editing tags by hand.
