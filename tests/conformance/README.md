# Conformance corpus

Programs paired with frozen expectations, which are the contract for `ms`. `ms` passes the corpus apart from fixtures tagged `aliasing`, which the value-semantics migration changes on purpose, and the entries in `expect-fail.txt`.

```sh
make conform                            # builds ms, then replays the corpus with tools/conform-run.ms
ms run tools/conform-run.ms -- --phase check e2e/reject   # one phase, fixtures whose id contains the text
```

## Layout

A fixture id is its path under `fixtures/` without extension. A `check` fixture states what it expects in its own file: the last lines are `// expect-error: <code> <line>:<col>[-<line>:<col>] <message>` (one per diagnostic, with `// expect-fix: <span> "<replacement>"` after one that offers a fix) and `// expect-exit: <n>` when there is no diagnostic or the exit code is not 1; they follow the program, so their line numbers are the file's own. Parse, run and test fixtures have `<slug>.expected.json` beside the `.ms` file until they are converted (see `design/proposals/readable-conformance-tests.md`). A project fixture is a directory holding `conform.meta`, `ms.toml`, sources and `expected.json`. A `-fmt` suffix marks the parse-phase (formatter) twin of a fixture. Recorded output embeds the file name, so renaming a fixture means re-recording it or editing its expectation.

| directory | contents |
| --- | --- |
| `snippets/<area>/` | Single-file programs harvested from the old per-package unit tests, grouped by the area they exercised: `build checker compiler frontend lexer lower parser syntax tooling`. |
| `snippets/golden/` | Checker diagnostics formerly kept as one Rust-side `golden.txt` (1,084 programs not already in the corpus); the CLI reports every recovered parse error where the old test saw only the first. |
| `snippets/cli/` | CLI behavior programs (`ms check/fmt/lint/test` flags, JSON reports, project discovery). |
| `snippets/e2e-tests/` | Programs harvested from the old end-to-end tests: fault locations, constant diagnostics, CLI projects. |
| `snippets/authored/` | Small hand-written fixtures named by topic (`diag-*`, `foreign-*`, `literal-*`, `sized-*`, ...). Add new single-file fixtures here. |
| `e2e/{accept,reject,stdlib,projects}/` | Programs that must be accepted, rejected, exercise a stdlib module, or are multi-file projects. |
| `examples/`, `bench/` | Harvested from the repository's `examples/` and `bench/` programs. |
| `docs/` | Fences from the documentation; the slug is the page path plus fence number. |
| `repo/` | Manuscript files that live elsewhere in the repository (scripts, test data). |
| `fuzz/{run,types,syntax}/` | Generated by `ms run tools/conform.ms -- fuzz-gen` (then formatted and retagged); do not edit by hand. |

A header `phase=test,parse` names more than one phase: the first is the recorded one, and each later phase applies its default expectation to the same file (for `parse`, a clean parse that `ms fmt` leaves unchanged), so a formatter check needs no `-fmt` copy of the program. Metadata lives in `// conform: key=value` lines at the top of the file (or in `conform.meta`): `tags`, `phase`, `origin`, `args` (JSON array), `timeout` (seconds), `entry`, `deterministic`. The header is part of the source, so diagnostic positions are those of the file as stored.

## Phases

| phase | command | compared |
| --- | --- | --- |
| `parse` | `ms check --json`, `ms fmt` | parse-phase diagnostics, formatted source |
| `check` | `ms check --json`, `ms check` | diagnostics (code, phase, message, position), terminal text, exit status |
| `run` | `ms run` | stdout, stderr, exit status |
| `test` | `ms test --json` | per-test results, summary, report shape (durations stripped) |

Paths under the work directory print as `<DIR>`.

## Tags

Feature: `lexer layout parser formatter types generics interfaces closures match destructuring try-result optional scope-cleanup faults strings lists maps sets numbers decimal interpolation records alternatives control-flow functions modules projects diagnostics mutation json-protocol docs examples testing cli`; standard library: `stdlib-<module>`; kind: `perf fuzz bench`.

Tier: `tier-core` imports nothing, `tier-stdlib` imports only pure modules, `tier-io` touches files, network, processes, time or randomness.

`aliasing` marks programs whose answer may depend on assignment sharing or `.clone()`. The harvester tags by heuristic (over-tagging is safe); these fixtures are excluded from the gate. Review the tagged set, and tag by hand where the heuristic misses, with `// conform: tags=...,aliasing`.

## Commands

`tools/conform-run.ms` replays the corpus against the `ms` built from this tree and prints `<phase>: passed/total` with one `FAIL <id>` line per difference (`CONFORM_DIFF=1` shows expected and observed output). `--phase`, `--jobs` and fixture id substrings select; `MS` names another binary. `tools/conform.ms` has the other corpus commands: `list` and `stats` (fixtures by phase and tag), `lint` (headers, tags and expectation files; `make conform` runs it, so a fixture with a new tag also adds the tag to `tools/conform/tags.ms`), `retag` (recompute `tier-*` tags from imports), `diff` (two `ms` binaries or build types on the same fixtures), `fuzz-gen` and `fuzz` (deterministic generated programs, written into the corpus or run under `--oracle` and `--ms`, which the oracle's observation decides), and `harvest` (turn repository sources and documentation fences into fixtures; record them with `--record --prune`). The Rust `ms-conform` they replace is at commit `660429d4`.

## Adding and refreshing fixtures

A new behavior test goes in `e2e/accept` or `e2e/stdlib` as an in-source `test` with `expect_equal` and `phase=test`; a rejected program goes in `e2e/reject` (`phase=check`), and a multi-file program in `e2e/projects/<name>/` with `conform.meta`. Modules that single-file fixtures import live in a `support/` directory beside them (not fixtures). This corpus is the one test runner for `.ms` behavior.

1. Write the `.ms` file with a `// conform:` header, choose tags and phase.
2. `ms run tools/conform-run.ms -- --record --only-missing <slug>` writes the expectation (`--inline` writes a `check` fixture's as `// expect-` lines); each fixture is observed twice and refused if the answers differ (`deterministic=true` skips this for time- or random-dependent output you have normalized; `--no-stable-check` skips the second run). `--prune` deletes fixtures that cannot be recorded.
3. Review the expectation. It records what the binary does, bugs included; a fixture that pins a bug keeps its expectation and joins `expect-fail.txt` with a reason.
4. Fixtures whose output varies between runs (for example diagnostics emitted in map order) must be deleted, not recorded.

## Hostile fixtures

Programs importing `http`, `net`, `tls`, `websocket`, `sse`, `process`, `terminal`, `system`, `random` or `time` are checked but not run by the harvester, since they bind sockets, wait on signals or depend on the clock. Add run fixtures for them by hand with deterministic output.

Changing a fixture's `// conform:` header shifts byte offsets in its diagnostics, so re-record after editing tags by hand.
