# Function types carry `var` parameters

Decision (2026-11-03): a function type marks the parameters the function changes, `fn(var List[Int]) Unit`, and the marker is part of the type's identity. A named function with `var` parameters is a function value of that type, an anonymous function declares `var` parameters the same way, and a call through the value marks the argument `var` exactly as a direct call does. Before this, a `var` parameter barred a function from being a value and a lambda's `var` parameter was a private copy, so the only ways to change a caller's value through a callback were a closure over the variable or a handle with shared state (the router's pipe-slot `TestState`).

Mechanism: the parser accepts `var` before a parameter type in `typ_inner`; `types::Param` has `mutable`, set by `Checker::params` for declarations and function types alike and by `callback` for lambdas, and compared in `same`, `unify` and `write_type_key`. `call_modes` (`modes.rs`) reads the modes of a call through a function value from the callee's type, so the `var` marker rule in the ownership walk needs no new case. Lowering: `lower_ty` makes a `var` position `MTy::PTR`, so the closure's MIR signature matches the named function's instance and the plain `thunk:` wrapper forwards it; `call_value` passes `var` positions through `var_argument` and `restore_var_arguments` (shared with direct calls in `call.rs`); a lambda binds a `var` parameter with `bind_var_parameter`, the same take-from-slot and put-back-on-return as a named function. A function with both a `var` parameter and a default cannot be a value: the default thunk fills omitted optionals and cannot also pass an address (`exprs.rs`, `callbacks.rs`).

Reassigning a `var` parameter from itself: moving a `var` parameter out is rejected (the caller keeps it), except into the right side of an assignment to that parameter (`exchange = new_tap(exchange, ...)`), which refills it (`self_assign` in `walk.rs`); lowering skips the old-value drop when the right side moved the parameter (`moved_within` in `stmt.rs`). This is what lets router middleware wrap a `var HttpExchange` in place instead of copying it; the exchange state still lives in a pipe slot because a wrapper of another type may come back from the handler.

Reader for `var` (Chinmay, 2026-11-06: "you can go mutable to immutable, but not the other way round"): a function that only reads a parameter may be used where `fn(var T)` is expected, never the reverse. The checker records it in `check_expression` as `Info.function_source` (the expression's type becomes the expected one, as for an interface conversion; `types::reads_where_var_expected` decides) and `unify` accepts a reading actual for a `var` pattern position. Lowering wraps the value in a function adapter (`fit_reader_function`, `FnAdaptJob.reads`) that takes the slot address and `Load`s the value for the held function, which borrows it. `value_ty` returns the source type while the expression is lowered, as for interfaces, so lambdas and named functions are built with their own signature. Identity (`same`) is unchanged. This is what lets one callback type serve both `for_each`-style reads and in-place element updates.

Apply when: changing calling conventions of function values, adding thunk kinds, or designing a stdlib callback that must change its argument (prefer `fn(var T)` over a handle with shared state).
