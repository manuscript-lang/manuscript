# LLVM facts need pointer provenance, and Cranelift alias regions are not markers

The CLIF-to-LLVM translation (`Tr` in `llvm_ir.rs`) is deleted: every release function and glue is written by `mir_llvm` and `glue_llvm`, and a function they cannot write is a build error that lists it. The lowering for Cranelift no longer tags list element accesses with alias regions. History worth keeping: a Cranelift alias region means "disjoint from every other region, untagged accesses included", so a tagged store that no untagged load observes is dead (the `PriorityQueue` test lost a swap); never use a region as a mere marker for Cranelift code. The translation saw every address as an `i64`, so facts reached LLVM only where it kept a `ptr`; the direct emitter keeps `ptr` throughout.

TBAA has two classes only: scalar elements and list/string header elements; other element types stay untagged. A buffer holds one element type, so a number buffer never holds an inner list's `{ptr, len, cap}`; `dp[i][j] = v` no longer reloads and rewrites the row header (LCS grid 41 to 34 ms). Finer classes are unsound: a record field or inner header is also read through borrowed pointers that carry no tag, so only tag accesses through `elem_addr`.

Measured (2026-11-12, same machine): none of this moves the kernels or competence suites beyond noise; `chars_1M` shifted 25% with identical optimized IR (code placement). The real vectorization blocker is checked `Int` arithmetic: `sadd.with.overflow` reductions and the cold fault exits are not vectorized by LLVM 23 (`sumi` 0.6 ns per element, a checked `y[i] += x[i] * 3` 0.78, wrapping `saxpy` 0.25).

Tried without effect (2026-11-12): an entry `llvm.assume` with `dereferenceable(ptr, len * size)` for every list parameter left the LCS grid unchanged (33.7 against 35.3 ms, noise); allocator results are declared `align 16`.

Apply when: adding facts to the direct LLVM emitter.
Evidence: [module and units](../../crates/ms-clif/src/llvm_ir.rs), [direct emitter](../../crates/ms-clif/src/mir_llvm/mod.rs), `make drift-check`.
Verify: `ms-conform diff --a target/release/ms --b target/release/ms --env-b MS_BACKEND=cranelift --phase run,test`.

## Direct MIR emission (stage 1, 2026-11-13)

Chinmay approved emitting LLVM IR directly from MIR (reversing the earlier rule against a second emitter); plan in `proposals/mir-to-llvm-direct.md`. Stage 1 was `crates/ms-clif/src/mir_llvm.rs` behind `MS_LLVM_DIRECT=1`, with per-function fallback to the translation; the flag and the translation are gone (there is `MS_BACKEND=cranelift` for the other backend). Measured before building it: the yaml program is 19k MIR lines and 183k LLVM lines (122k with `MS_VECTORIZE=off`), yet release build time is 2.9 s either way, so line count alone does not predict compile time; judge each stage by time as well. Write source fixtures so the MIR inliner leaves the function out of line (a long body called twice), or the direct path never runs.

IR is written through `crates/ms-clif/src/llvm_build.rs` (typed values, required alignment). A phi names values that later blocks define, so `mir_llvm` names every MIR value before emitting any block; naming at definition crashed on the first loop. Inkwell 0.11 supports LLVM 23 but needs an LLVM development bundle for all six platforms (the pinned archives hold only `opt`, `llc`, `llvm-link`), so it is deferred.

Builder decision (2026-11-13): the emitter writes LLVM text through the in-house `llvm_build.rs`; `inkwell` was tried and dropped (build-time LLVM libraries on six platforms, +4 MB to +54 MB in `ms`). Do not re-propose it without a goal that needs LLVM in process.

Function facts (2026-11-13): `mir_llvm` writes `nounwind nofree nosync memory(none)` (plus `willreturn norecurse` when loop-free and acyclic) on a scalar function whose MIR is pure, and the same on the `declare` at each call site, since a callee in another unit is only a declaration. Recursive functions never qualify yet: `depth.enter` is not a supported op. Not measured as a speedup; it only keeps what LLVM could infer inside one unit when the unit is split. Pointer facts (`noalias`, `readonly`, `dereferenceable`) wait for the record stage.

Check a direct-emitter change with `make drift-check` (corpus output under LLVM against Cranelift) and `make llvm-report` (`tools/llvm-direct-check.ms`: build time under both backends, IR lines, the share of functions emitted directly, `bench/perf` kernel times; one build runs with `MS_LLVM_VERIFY=1`, `opt -verify-each`). CI runs the corpus under both backends against the fixtures' expected output. Hosts that build releases with Cranelift have one backend.

Direct-emitter facts: what is in and what to keep out (2026-11-13). In: `range` on `Bool` (0..2) and on list and bytes length leaves; `!tbaa` scalar-element and header-element on list element accesses, plus `!range` on `Bool` elements and inner list lengths (`Meta`, `load_with`, `store_with`); `nomerge` only on calls that can fault (`call_pure` for callees proven `memory(none)`); pointer parameters `nonnull readonly/noalias nocapture dereferenceable align` and `sret` (`abi_llvm.rs`). Purity is an allow-list: an op no area names in `pure_op` touches memory. Keep out: `noundef` on parameters or returns while enums and optionals pass an unused payload leaf as `undef`, since that would be undefined behavior at the first `none`; record-field TBAA while borrowed pointers carry no tag; `llvm.loop.mustprogress` until the language decides whether a loop with no effect may be deleted. Runtime functions: every `declare` is `nounwind`, faults are also `cold noreturn`, `reads` externs add `willreturn nofree nosync memory(read)` (`runtime_attrs`); fixed-signature ones (`msrt_alloc`, `msrt_free`, ...) are declared only through `mir_llvm/rt.rs`, because the module keeps the first declaration of a symbol and two spellings would drift. Still open: lifetime markers for scratch slots, `nomerge` as opt-in instead of opt-out.
