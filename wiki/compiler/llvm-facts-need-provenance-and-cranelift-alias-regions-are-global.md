# LLVM facts need pointer provenance, and Cranelift alias regions are not markers

Verified: the CLIF-to-LLVM translation sees every address as an `i64`, so facts only reach LLVM where the translation keeps a `ptr`. It now keeps `msrt_alloc`, `msrt_alloc_zeroed` and `msrt_realloc` results (`noalias`), pointer-carrying block parameters (`ptr` phis, found by `find_ptr_params`) and entry parameters used as addresses (one `inttoptr` at entry). List element accesses carry the `REGION_IN_BOUNDS` bit in lowering when they are checked or MIR-proven (`list.get.u`), which becomes `inbounds nuw` addresses and `mul nuw nsw` scaling.

A Cranelift alias region means "disjoint from every other region, untagged accesses included": a tagged store that no untagged load observes is dead (the `PriorityQueue` test lost a swap). Tag only functions LLVM translates (`g.llvm.is_some()`); never use a region as a mere marker for Cranelift code.

TBAA has two classes only: scalar elements (`REGION_SCALAR_ELEM`) and list/string header elements (`REGION_HEADER_ELEM`); other element types stay untagged. A buffer holds one element type, so a number buffer never holds an inner list's `{ptr, len, cap}`; `dp[i][j] = v` no longer reloads and rewrites the row header (LCS grid 41 to 34 ms). Finer classes are unsound: a record field or inner header is also read through borrowed pointers that carry no tag, so only tag accesses through `elem_addr`.

Measured (2026-11-12, same machine): none of this moves the kernels or competence suites beyond noise; `chars_1M` shifted 25% with identical optimized IR (code placement). The real vectorization blocker is checked `Int` arithmetic: `sadd.with.overflow` reductions and the cold fault exits are not vectorized by LLVM 23 (`sumi` 0.6 ns per element, a checked `y[i] += x[i] * 3` 0.78, wrapping `saxpy` 0.25).

Tried without effect (2026-11-12): an entry `llvm.assume` with `dereferenceable(ptr, len * size)` for every list parameter left the LCS grid unchanged (33.7 against 35.3 ms, noise); allocator results are declared `align 16`.

Apply when: adding facts to the LLVM translation, or tagging memory accesses in lowering.
Evidence: [translation](../../crates/ms-clif/src/llvm_ir.rs), [element flags](../../crates/ms-clif/src/lower.rs), `make drift-check`.
Verify: `ms-conform diff --a target/release/ms --b target/release/ms --env-b MS_BACKEND=cranelift --phase run,test`.

## Direct MIR emission (stage 1, 2026-11-13)

Chinmay approved emitting LLVM IR directly from MIR (reversing the earlier rule against a second emitter); plan in `proposals/mir-to-llvm-direct.md`. Stage 1 is `crates/ms-clif/src/mir_llvm.rs` behind `MS_LLVM_DIRECT=1`: scalar-only functions are emitted from MIR, everything else falls back to the translation, and both share the leaf calling convention. Measured before building it: the yaml program is 19k MIR lines and 183k LLVM lines (122k with `MS_VECTORIZE=off`), yet release build time is 2.9 s either way, so line count alone does not predict compile time; judge each stage by time as well. Write source fixtures so the MIR inliner leaves the function out of line (a long body called twice), or the direct path never runs.

IR is written through `crates/ms-clif/src/llvm_build.rs` (typed values, required alignment). A phi names values that later blocks define, so `mir_llvm` names every MIR value before emitting any block; naming at definition crashed on the first loop. Inkwell 0.11 supports LLVM 23 but needs an LLVM development bundle for all six platforms (the pinned archives hold only `opt`, `llc`, `llvm-link`), so it is deferred.

Builder decision (2026-11-13): the emitter writes LLVM text through the in-house `llvm_build.rs`; `inkwell` was tried and dropped (build-time LLVM libraries on six platforms, +4 MB to +54 MB in `ms`). Do not re-propose it without a goal that needs LLVM in process.

Function facts (2026-11-13): `mir_llvm` writes `nounwind nofree nosync memory(none)` (plus `willreturn norecurse` when loop-free and acyclic) on a scalar function whose MIR is pure, and the same on the `declare` at each call site, since a callee in another unit is only a declaration. Recursive functions never qualify yet: `depth.enter` is not a supported op. Not measured as a speedup; it only keeps what LLVM could infer inside one unit when the unit is split. Pointer facts (`noalias`, `readonly`, `dereferenceable`) wait for the record stage.

Check a direct-emitter change with `make llvm-direct-check` (`tools/llvm-direct-check.ms`): `diff` runs the corpus with the flag off and on and compares output, (`opt` verifies its input; `report` also builds once with `MS_LLVM_VERIFY=1`, `opt -verify-each`); `report` prints build time, IR lines, the share of functions emitted directly and `bench/perf` kernel times for both. CI runs both on every platform; hosts that build releases with Cranelift ignore the flag, so there the two sides match by construction.

Direct-emitter facts: what is in and what to keep out (2026-11-13). In: `range` on `Bool` (0..2) and on list and bytes length leaves; `!tbaa` scalar-element and header-element on list element accesses, plus `!range` on `Bool` elements and inner list lengths (`Meta`, `load_with`, `store_with`); `nomerge` only on calls that can fault (`call_pure` for callees proven `memory(none)`); pointer parameters `nonnull readonly/noalias nocapture dereferenceable align` and `sret` (`abi_llvm.rs`). Purity is an allow-list: an op no area names in `pure_op` touches memory. Keep out: `noundef` on parameters or returns while enums and optionals pass an unused payload leaf as `undef`, since that would be undefined behavior at the first `none`; record-field TBAA while borrowed pointers carry no tag; `llvm.loop.mustprogress` until the language decides whether a loop with no effect may be deleted. Runtime functions: every `declare` is `nounwind`, faults are also `cold noreturn`, `reads` externs add `willreturn nofree nosync memory(read)` (`runtime_attrs`); fixed-signature ones (`msrt_alloc`, `msrt_free`, ...) are declared only through `mir_llvm/rt.rs`, because the module keeps the first declaration of a symbol and two spellings would drift. Scratch slots: `llvm_lifetimes.rs` post-processes each function body and brackets every block-confined `alloca` (address only offset, loaded, stored through or passed to calls; first access a write) with `llvm.lifetime.start/end`, so stack coloring overlaps them. Without it direct frames were 2 to 4 times the translation's (YAML `flow_value` 12.6 KB, now 4.2 KB). Still open: `nomerge` as opt-in instead of opt-out.
