# The C build compiles MIR text to an object in C

`ms_build_object` (`compiler/src/build/object.c`, `ms/build_object.h`) is the LLVM half of `ms build`, ported from the Rust `c_backend::compile`: `ms_backend_ir`, pinned `opt` (release only), `llc` to assembly, `ms_backend_tables`, the assembly wrapped as `module asm` lines, `llc` to an object. It takes the LLVM tools directory as an argument; fetching the pinned release stays with the link code. Linux, macOS and Windows (`ms_build_object` and `ms_build_link` run in the `c-pipeline` hello step on all four platform legs).

Prove it with `compiler/tests/build-object-diff.sh`: `ms emit` MIR text, C object, `cc -nostartfiles` against `libms_native.a` (with `--defsym=__dso_handle=0`), and compare output and status with `ms run` on `phase=run` fixtures. Do not compare `.ll` text with the Rust build's `ms-keep.ll`: `ms emit` prints different string-literal bytes from the in-process module, so literal padding differs although the programs behave the same.

`ms_build_link` (`build/link.c`, `ms/build_link.h`) ports the Linux link of `link.rs` and `link/lld.rs`: the pinned `lld` over glibc 2.28 stand-ins (generated once into `<files>/glibc` from `glibc.symbols` as LLVM IR assembled by `llc`, then `lld -shared` with a version script, so no ELF writer is needed), or static musl with `--musl`. The tool directory, `lld` and the linker files directory are arguments. The link is split per host (`link.c` shared, `link_linux.c`, `link_macos.c`): macOS generates the `.tbd` SDK stubs from the Mach-O symbols of the object and inputs (`macho.c`, checked against `nm` on objects `llc` writes for Apple targets) and runs `dsymutil` when a file has `__debug_info`; `link_windows.c` is the mingw lld link (`crt2.o`, the import libraries, `libsynchronization.a`, the compiler-rt builtins); `tool_posix.c`/`tool_windows.c` hold the per-host process and directory helpers. macOS and Windows are proven only by the platform CI legs (`c-pipeline.yml`, `compiler/tests/c-link-hello.sh`). Windows tools build without a system OpenSSL and with `-D_ACRTIMP=` so `ms_mimalloc.h`'s renamed `malloc` is not a dllimport. Fetching and caching the pinned `lld` and LLVM tools is Manuscript, not C: `tools/ms/toolchain.ms` (stdlib fetch, tar/gzip, SHA-256; same `<cache>/ms/<name>/<sha16>/` layout as the Rust link). The linker files directory (`files`) comes from `cmake -DMS_MODE=linker -P cmake/BuildRuntime.cmake` (`cmake/LinkerFiles.cmake`: musl crt/libc and an unwinder on Linux, the mingw crt/libraries and compiler-rt on Windows, nothing on macOS), not from the Rust embed; `c-link-hello.sh` and the `c-pipeline` hello step use it, and both the glibc stand-in link and the static musl link were checked from it. The unwinder is LLVM's `libunwind.a` when the compiler finds one, else GCC's `libgcc_eh.a`. The `--musl` path is untested here (no musl runtime archive in the test); the glibc path is proven by `build-object-diff.sh` (same GLIBC symbol versions as the Rust link).
