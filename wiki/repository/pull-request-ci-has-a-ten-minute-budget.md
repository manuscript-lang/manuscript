# Pull request CI has a ten-minute budget

Decision (Chinmay, 2026-11-14): a pull request's CI must finish in under 10 minutes per job on the current runners (no larger runners), and a new test must fit the budget or something else is cut.

- Two jobs per PR, one per Linux arch (amd64 and arm64), each running its whole suite. No sharding, no extra runners, and no per-arch or per-platform skipping of a test.
- Budget per job: 600 s in total. The conformance corpus takes about 170 s (Cranelift, every phase) and is not trimmed. Rust tests, build, lint and setup share the rest. The earlier 5-minute target was not reachable on 4-core runners without cutting coverage.
- Pull requests build programs with Cranelift. The LLVM suite (LLVM corpus, release gates, the `llvm` Rust tests) runs on `main` every 30 minutes and, on pull requests that touch LLVM-specific code (`crates/ms-mir-llvm`, `crates/ms-mir/src`, `crates/ms-lower` (drop, clone and closure glue is built in MIR, and the LLVM leak sweep found a bug in #4327 that Cranelift CI could not, #4336), `crates/ms-build/src/llvm*`, the LLVM tests, `toolchain/lld.lock`, `toolchain/check-glibc-floor.sh`), in separate `llvm-*` jobs (the whole corpus in one job on amd64 (Chinmay, 2026-11-17: one LLVM job per arch, no shards); the backend tests and gates on arm64) that run beside the two ordinary legs. Decision (Chinmay, 2026-11-14): run LLVM as its own job instead of inside the same job, so no job passes 10 minutes. Putting LLVM inside the legs took them to 924 s and 1,133 s (the LLVM corpus alone is about 400 s). The filter lives in `.github/actions/rust-scope`; the Time budget check covers every `linux-*` and `llvm-*` job.
- Measured on run 44133883442 (2026-11-17, #4426): the two LLVM corpus shards ran 467 s and 628 s with the same fixture count, although local per-fixture times split by position are balanced (968 s vs 948 s), so the gap is runner noise; the gates job took 504 to 623 s over attempts, 113 s of it packaging. Chinmay (2026-11-17): more shards or jobs are not approved; cut redundant work instead and never raise 600 s. Re-running only a failed `Time budget` job re-reads the slow earlier job: re-run the over-budget job itself.
- Slowest tests on a PR run (2026-11-17, linux-amd64, nextest 119 s on 4 cores for 470 CPU-s): one checker test of 30 type doublings took 32 s because `has_variable` walked the type as a tree (2^30 paths); it now shares visited nodes (#4431) and the test keeps 30 doublings at 0.07 s; `doc_examples` 26 s (runs when docs change), `c_smoke` 16 s (rebuilds `ms-native` on its own), LSP reference snapshots 3 to 10 s each. The leak-counting runtime (`use_stats_runtime`) cost about 65 s in each LLVM job that needs it because the warm-caches workflow never built it, so its sccache missed; the workflow now builds it.
- A new Rust test is cheap or it replaces another: no test over 2 s without a reason, no per-position loops over a whole file (sample them), no spawning `ms` for a case an in-process call covers, no work the conformance corpus already does. Measure with the slowest-tests list in the job log.
- Cheapest first fixes found so far: share one checker session instead of rebuilding the standard library per check; cache per-thread test setup; optimize the hot crates of loop-heavy tests with `[profile.dev.package.<crate>]` in the root `Cargo.toml`; cache the native runtime build; profile one `ms test` with `valgrind --tool=callgrind` before guessing (Cranelift's debug assertions were a third of the compile instructions; the dev profile now turns them off for the Cranelift crates, and `main` replays the Cranelift corpus with `--profile checked`, which has them on).
- Rust tests get a strict budget of about 2.5 minutes with only high-value tests; compiler verifiers are never turned off silently, and one `main` job keeps every check on.
- Decision (Chinmay, 2026-11-14): meet the budget by removing redundant work (shared sessions, one build, work another test already does), not by shrinking test inputs or dropping coverage. The Cranelift IR verifier stays on in PR CI. See [ci-time](../../skills/ci-time/SKILL.md).
- Measured on a PR run (4 cores): setup 46 s, test build 166 s, Rust tests 214 s, corpus 189 s, lint 50 s, so the fixed costs alone exceed 300 s on amd64; each `ms run|test` corpus fixture compiles its own program (about 0.5 s), only `check` is batched.
- Cache freshness decides much of the variance (Chinmay's thread, 2026-11-15): the six-platform run of main is hours apart, so a pull request restored an sccache hours old (87 Rust misses, then 35 after a refresh) and never shared the native runtime archives (a pull request cache is visible to that pull request only, so every pull request rebuilt them, 51 to 64 s). The `Warm caches` workflow rebuilds both on Linux after each push to main and pull requests restore them (`native-runtime` action). With a fresh cache the same code went from 563 to 538 s on amd64 and 604 to 508 s on arm64.
- CI reports it: the `Time budget` job in `cicd.yml` fails a pull request whose Linux job ran over 600 s, and `Platform checks` requires it, so an over-budget PR cannot merge until a test or step is cut.
- A `${{ cond && '' || x }}` expression always yields `x`, because an empty string is falsy: the runtime build step passed `--alloc-profile` on pull requests (about 50 s more per leg whenever a runtime source changed). Write `${{ !cond && x || '' }}`.
- Leak counting stays on `main` (measured 2026-11-15, linux legs, `CONFORM_LEAKS=1` on the PR Cranelift corpus): the corpus runs once on the stats runtime, so the cost is building that runtime (69 s on a cache miss) plus about 16 s of slower fixtures (111 s to 127 s on amd64). Cold, a PR that changes runtime sources ran 670 s on amd64 (554 s arm64) and failed `Time budget`; warm is estimated near 475 s but was never measured. A leak that reaches `main` is caught by its full run.
- `ms review` and `ms diagram` list every standard-library entity too, and each asked the lazy effect scan for its callable, which republished the whole library's effects (about 370 times per run, 0.9 s per spawn unoptimized, 26 CLI tests at 6 to 12 s each). `inspect::collect` now scans all effects once, 0.17 s per spawn. When a CLI test is slow, callgrind one spawn first: the cost was a quadratic query loop, not the test count.
- Measured 2026-11-18 on an LLVM pull request (#4453): single `llvm-amd64-corpus` 561 s after 641 s (test phase is 83% of its 1931 s of fixture time, CPU-bound on 4 cores; yaml fixtures 15 to 22 s each), `linux-amd64` 438 s, `linux-arm64` 484 s, `llvm-arm64-gates` 431 s. Causes found: the vendored `cranelift-codegen` embedded the git revision in its `VERSION`, so it recompiled (85 s) on every commit and its 110 MB entry crowded the 1 GiB sccache; the dev-built `ms` spent about 3 s of a 9 s yaml `ms test` in the unoptimized LLVM IR writer (`ms-mir-llvm` is `opt-level = 2` now); the corpus-only `-p ms-cli` build was not in the warmed cache (`warm-caches` builds it). An empty `CONFORM_SHARD` is `0/1`. The corpus job has about 7% margin: before adding LLVM fixtures, cut something else (largest: the five yaml fixtures, each compiling the whole module).
- The corpus runner starts the largest fixtures first (source bytes as the cost): in alphabetical order the five yaml fixtures (12 CPU-s of LLVM each) started last and ran alone at the tail. Each `ms test` binary also compiles the test runner again (about 13k IR lines, 0.15 CPU-s under LLVM); a PR's LLVM job no longer replays lint, check and parse that the Cranelift legs already ran (`CONFORM_BACKEND_ONLY`, about 30 s; Chinmay approved 2026-11-18; main still runs every phase).
- Measured 2026-11-19 (LLVM corpus, same code, two attempts of one run): `llvm-amd64-corpus` took 474 s and 654 s. The corpus step itself was 392 s and 520 s (fixture time 1526 s and 2072 s), so a slow runner alone adds about 35%; a cold-ish sccache added about 40 s of build on top. The job is CPU-bound in LLVM `opt` and `llc` (about 5 s of CPU for a 5 MB unit at `-O3`; greedy register allocation a third of `llc`, `-O2` instead of `-O3`, no vectorizer and `-enable-misched=false` each save under 8%). Read IR size per function before reading flags: every `ms test` binary carries the test runner (about 7,600 IR lines, a quarter of all generated code in the test phase), and its largest piece was `status_error`, the function that maps a runtime status to an `Error` (4,100 lines per table, every program that touches files or the network). It built the whole error in each table row; it now picks the row's strings and builds the error once (about 500 lines), which took a 110-fixture slice of the LLVM corpus from 96 s to 88 s. Find the next offender with `MS_KEEP_LL=1 ms test x.ms --build-type Release` and a per-function line count of `ms-keep*.ll`.
- `cmake -P cmake/BuildRuntime.cmake` builds the gnu, musl and optional archives side by side in separate target directories (cargo locks a shared one, which serialised them).
- Measured 2026-11-19 (#4598, same code, two attempts): `linux-amd64` ran 602 s and 610 s against 443 s of `rust-checks` for the previous Rust PR, yet local timings of the same fixtures (`bigint-number-theory`, `yaml`, `html`, `many-tasks`) matched the baseline binary within 1%. The job log showed every test slower by about 20% (nextest CPU time 457 s to 543 s, including `ms-native` tests the change cannot touch), so before cutting coverage compare an unrelated test's time between the two runs: a uniform slowdown is the runner, not the change.
- Test-phase conformance fixtures are built in batches of up to 12 per `ms test` (`tools/conform/runner.ms` `test_batch`; proposal `proposals/batch-test-fixtures.md`): the runner (about 10,900 IR lines, 0.4 s of LLVM per build) and shared modules compile once per batch, and a fixture whose rebuilt observation differs from its recording is observed alone. Measured 2026-11-19 on 4 jobs: the whole test phase, 244 s to 180 s wall and 891 to 675 CPU-s under LLVM, 730 of 730 passing; fixtures that import `@std/os/`, `@std/net/`, `@std/process` or `@std/time`, or recorded a failure, output or stderr, still run alone. This is not sharding: one job per arch, every fixture still judged on its own.

Apply when: adding or changing a test, a CI step or a workflow.
Evidence: [cicd.yml](../../.github/workflows/cicd.yml), [rust-scope](../../.github/actions/rust-scope/action.yml), [AGENTS.md](../../AGENTS.md).
