# A read-modify-write is one API, not a syntactic pattern

Verified (2026-11-09, #3190): the compiler matched `m.add(k, m.get(k).get(0) + 1)` to one probe, so only that spelling was fast and each new spelling needed its own key-conversion and aliasing rules (#2857, #2858). `Map.update(key, initial, change)` is now a native mutator lowered to one lookup (`map_update` in `crates/ms-lower/src/mapset.rs`); the checker already rejects a `change` that overlaps the receiver, so the slot stays valid across the call. The matcher was deleted: the 2M-count loop runs in 7.6 ms through `update` against 10.1 ms for the matcher and 13.9 ms for `get_or` plus `add`.

The first version of `update` through the general `msrt_map_slot_lent` was slower than `get_or` plus `add` (15.0 ms): the general entry point dispatches on descriptors out of line. Probing first with the inlined word lookup (`msrt_map_get_ptr_w8`/`_sw8` through `word_map_symbol`) and reaching the runtime only for an absent key fixed it. A new fast path must reuse the existing word-specialized probes, not a general entry point.

Verified (2026-11-12): `if not m.contains(k): m[k] = v` then `m[k].f += 1` took two probes a round because the join of the two paths cleared the probe table; `fuse_contains` (#3674) carries the entry across the join (String-key loop 730M to about 400M instructions, equal to `update`). That is a MIR rule on probes, not a syntactic match, so it covers any spelling that reaches those calls. Also: `m.get(k)` bypassed the inlinable `_w8` probes (use `word_map_symbol` at every lowering site). A C twin is only a target if it keeps order, grows and removes like `Map` (`bench/perf/structural-gaps/c/ordmap.h`); the presized unordered twins overstated the gap by 1.6x to 2x.

Apply when: a hot idiom costs two lookups; before adding a syntactic fast path to lowering.
Evidence: `bench/perf/results-2026-11-09.md` (last section), `tests/conformance/fixtures/e2e/stdlib/map-update-differential.ms`.
Verify: `ms test tests/conformance/fixtures/e2e/stdlib/map-update-differential.ms`; compare one program per spelling, minimum of many runs.

Rejected (2026-11-09, #3191): an unordered flat table (entries of `{hash, key, value}` in the probe array itself, no index, backward-shift removal) behind a new `UnorderedMap` type did not beat `Map` enough to ship. Runtime support was small, because every `msrt_map_*` entry point can dispatch on one mode flag (null `index`, nonzero `mask`), but on 1M `Int` keys it measured insert 83 ms against 34, random lookup 83 against 94, remove 28 against 29, and the 2M counter 7.4 against 7.1. The flat C table that measured 2.7x, 1.7x and 5x better was presized (no resize page faults), had 16-byte entries with no control word, and had its key compare as the only probe test; a 24-byte entry crosses a cache line a quarter of the time and a fresh power-of-two table is zero-faulted at every doubling, which `Map`'s realloc avoids. A pure Manuscript version was slower again (insert 73 ms). Before building a faster table, benchmark a presized table, an entry layout without a control word (a separate tag array) and a growing table in the same harness. The prototype is `architecture/unordered-flat-map-prototype.patch` in the project files.
