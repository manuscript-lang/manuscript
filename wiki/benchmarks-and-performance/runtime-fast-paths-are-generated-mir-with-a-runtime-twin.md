# Runtime fast paths are generated MIR with a runtime twin

Verified (2026-11-14, `bench/perf/rt-hot-retired/README.md`): `ms-rt-hot` is deleted. Release programs no longer link helper bitcode; every fast path is MIR that both backends compile, with the `ms-rt` function as the slow twin. Against `main`, map and set lookups, `String.view` and `StringBuilder.append` came out equal or faster, and the engineering suite output is byte-identical.

- Direction (Chinmay): no raw memory or byte primitives in Manuscript; the fast paths are shared MIR operations so Cranelift and LLVM both inline them, with no language change. See `proposals/retire-ms-rt-hot.md`.
- Moving a runtime function out of the hot crate is a perf regression until its fast path is MIR: `parse_int`, one-byte `contains` and `scalar_at` (ASCII and two-to-four-byte decode, 2026-11-15: an offset walk of 11.5 MB non-ASCII text 19 to 12 ms, Rust 11) live in `rtstr.rs`, with the `ms-rt` function as fallback. Find such gaps with a callgrind per-function diff against `main` (a function that is new in the candidate's list was inlined before). The runtime must hash an inline key from its words (`hash_str`), not by repacking its bytes: repacking cost 18 instructions per insert.
- Map and set probes (`Map[Int, word]`, `Map[String, word]`, `Set[Int]`) and `String.view` are generated `inline(always)` MIR functions. Map and set probes come from the C `probe` pass (`compiler/src/opt/opt_probe.c`, speed level, before `inline`): lowering declares the shaped lookups with the role `map_probe_int`, `map_probe_str` or `set_probe_int` and the pass reads the answer (address, contains, get) from the extern's signature, so no symbol name is consulted. `String.view`, `String.slice` and `Bytes.view` come from the C `viewfast` pass (`opt_viewfast.c`) and the fixed-width reads and `index_of_byte` from `bytesfast` (`opt_bytesfast.c`), both run with `inline` after `strfuse`: lowering emits the plain runtime call and the pass tells them apart by role (`string_slice`, `bytes_read_word`, `bytes_index_of_byte`) or, for the two views, by `borrows_argument` and the signature (a string or a bytes receiver, two bounds, an address). Only the string helpers of `rtstr.rs` are still generated in Rust. They read the map through its memory form with `ptr.add`, `ptr.loadu`, `ptr.null` and `umulhi`, so a lookup fuses with the key computation and the use of the value. Calling the runtime twin instead cost 30 to 70% on tight lookup loops; call overhead was the whole loss.
- A `String` key shorter than 16 bytes is two words, so `hash_bytes` for up to 15 bytes is defined on those words (length as seed, two folds). The MIR probe computes the same hash with no branch on length, and a longer key folds 8-byte words in an inline loop (short non-inline keys still call `msrt_string_hash`). Equal-length flat keys of 16 to 32 bytes compare with four overlapping `ptr.loadu` words. Change `hash_bytes` and `pb_string_hash` in `opt_probe.c` together; a mismatch makes lookups miss without a crash.
- A matching hash makes equal words (an inline string, or one block) decide a key; only distinct blocks call `msrt_string_eq`. `string_eq` for user code is decided from the words in each backend (`eq_words` in LLVM, `string_eq_call` in Cranelift) and calls the runtime only for two distinct blocks of one length.
- `StringBuilder.append` is inlined by the LLVM backend (`calls.rs`, as Cranelift already did): capacity check, overlapping moves up to 16 bytes, `memcpy` beyond, runtime call for a full buffer. An inline string is spilled to a slot first; leaving inline strings to the call cost 8% instructions on a report loop.
- A map passed by address (`update`) is not a map value: the probe helper takes a `ptr` map parameter as the map itself (`pb_build`). Storing that pointer into a slot and reading it as a map made `update` miss every key.
- Keep a selects-for-everything form out of hot paths: computing all three length cases of the hash plus a full `eq_words` was 40 more instructions per lookup than branching on the common case.
- Test the ASCII case with the flag or the inline bits, never `[u8]::is_ascii` on a short string (12% loss on `length`). Build a `memmem` searcher only for text of 128 bytes or more (`Needle::for_text`).
- After editing `ms-rt`, run `cmake -P cmake/BuildRuntime.cmake` before any `cargo test` or `clippy --workspace`; the `ms-cli` build script rejects a stale archive. Compare one kernel's instruction counts with `valgrind --tool=callgrind` on a program built by `main` and by the branch.
- `String.view` decides inline text and unflagged flat text (literals, producers that do not scan) in MIR too (2026-11-15): an inline text packs its range from the slot when the bytes are ASCII, and an unflagged flat text checks the bytes at both bounds are scalar starts (every string is NUL-terminated, so the byte at `end` is readable). Only a flagged check failure, bad bounds or a mid-scalar bound calls the runtime. A 15-byte literal piece cost 80 instructions per view through the call, 12 inline.
- Callgrind falls back to glibc for every allocation (the reservation cannot map), which shows small `Map` and builder allocations as `alloc_large`/`malloc_usable_size`. See [callgrind-needs-a-smaller-allocator-reservation](callgrind-needs-a-smaller-allocator-reservation.md) before concluding the small-object path is slow (issue #4021 chased this).


- A String-valued `Map` releases its values without descriptor dispatch, like its keys, and `StrBuilder.freeze` keeps a small block whose size class already fits (`alloc::trim`) instead of calling `realloc` (2026-11-15, issue #4021).
- `Bytes.view` is decided in MIR for a range with `0 <= start < end <= len` (a view `{ptr + start, end - start, 0}` stored with no call; empty, negative or out-of-range goes to the runtime), and `Bytes ==` calls `msrt_bytes_eq` instead of the descriptor-driven `msrt_slot_eq` (2026-11-15, issue #4021). On `replace_each` over HTML-like text (a hit every 8 bytes) that is 8.8% fewer instructions (1.402G to 1.278G over 20,000 runs of ~1KB), 3.9% on sparse text, with wall time inside the noise. A 256-entry first-byte table in `replace_each` was measured and not kept: 15% fewer instructions on dense text but 2x more on sparse text (12 instructions per byte in the loop plus about 10K to build the tables per call at 1KB); an `index_any` scan was worse on both.
- `String.slice` shares `view_fn` with `String.view` (2026-11-18, now `opt_viewfast.c`): a piece of up to fifteen bytes of an in-range, ASCII or scalar-aligned text is packed into an inline string with no call; a longer piece, an out-of-range or negative bound and a mid-scalar bound call `msrt_string_slice`, which copies and clamps. The slice twin writes through a slot and `take`s it, so the result stays owned. c03-csv-group-sum on 400 KB: 71.6M to 65.3M instructions (92,234 slice calls at about 103 instructions each gone). Fixture `e2e/accept/string-slice-fast-path`.
