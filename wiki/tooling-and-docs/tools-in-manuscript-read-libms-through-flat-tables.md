# Tools in Manuscript read libms through flat tables

Decision (C rewrite, 2026-11-20): lint, docs and symbol search are Manuscript programs over `libms`, and the Rust `ms` is the byte-for-byte oracle until the Rust is deleted. A Manuscript program holds no C pointer, so each `libms` entry point in `compiler/include/ms/tool.h` returns a `List[Int]` of fixed-width records (plus `List[String]` where text is needed). The record layout is written twice, in `tool.h` and `tools/ms/syntax.ms`, and the two are one contract.

Verified: a tool links `libmstool.a` (`make target/c-tool/libmstool.a`; `tool.c` includes `libms.c`, so it carries the whole library and needs the runtime's `ms_list_push`) and runs with `ms run tool.ms --link libmstool.a`. The project root is the entry file's directory, so tools sit under `tools/ms/` with its own `ms.toml`.

Verified: `ms_tool_parse` returns an opaque `Tree` held by C; `tools/ms/syntax.ms` decodes its preorder records into parallel columns (`kind`, `first`, `next`, ...), and `tools/ms/dump.ms` prints the canonical dump from them. The text equals `ms_syntax_dump ast` on every `.ms` file in the repository, which is the proof that the table loses nothing.

Apply when: moving a Rust tool rule or report into Manuscript, or adding a table to `tool.h`.
Evidence: [tool.h](../../compiler/include/ms/tool.h), [syntax.ms](../../tools/ms/syntax.ms), [dump](../../tools/ms/dump.ms), [lexical lint](../../tools/ms/lint/text.ms), [differential harness](../../tools/ms/lint_diff.ms).
Verify: `make c-tools-test` compares the dumps over the whole corpus and lints seeded mutations of corpus files with both linters, requiring equal findings.

Verified: copy `String.view_bytes()` of a short view with `as_bytes()` until [#4655](https://github.com/manuscript-lang/manuscript/issues/4655) is fixed; the borrowed bytes change after another view is taken.

Verified: the docs generator (`tools/ms/docgen.ms`) and description inventory (`doc_inventory.ms`) are pure rendering over an API model and reproduce all 103 `ms-docgen` files, `stdlib.json` and the coverage JSON byte for byte. The model is built by the C checker (`ms_tool_api_model`, [api_model.c](../../compiler/src/check/api_model.c)); the temporary Rust example `crates/ms-tooling/examples/api_model.rs` stays only as the oracle for `compiler/tests/api-model-diff.sh` and is deleted with the Rust docs generator.

Search: [search.ms](../../tools/ms/search.ms) ports `ms search_symbol` (pages, fuzzy ranking, `name_rank`, text and JSON output) over the dumped API model and matches the Rust command on every query of `tools/ms/search_queries.txt` in text, `--json` and `--limit 10`. It has library symbols only until the C checker supplies project symbols; the model comes from `ms_tool_api_model`, so run it with `--link target/c-tool/libmstool.a`.

Views: [views.ms](../../tools/ms/views.ms) ports the ten `ms diagram` views (tree, ASCII, Mermaid and JSON renderings) over the fact model that `ms-tooling-dev facts FILE` dumps, and `tools/ms/views-diff.sh` requires equal output with the Rust views (`ms-tooling-dev view`) for every view, format, entity and depth on three fixtures. Fact collection (`collect_facts`, `inspect::collect`) and the API model (`guide/api.rs`) stay in Rust: they read the Rust checker's program, so they move only when the C checker's columns can feed a Manuscript builder. Ownership rule met while porting: a builder record must not hold the model (storing `self` moves it); pass the model to each method instead.

Call graph: [inspect.ms](../../tools/ms/inspect.ms) renders `ms diagram` (text and Mermaid) from the `ms inspect` document, including the standard-library filter, and `tools/ms/inspect-diff.sh` requires the Rust command's output on the same three fixtures. `ms inspect` itself (`inspect::collect`) stays in Rust until the C checker prints that document.

Facts from C: `ms_check_dump STDLIB --facts FILE` ([dump_facts.c](../../compiler/src/check/dump_facts.c)) prints the JSON that `views.ms` reads. Stage 1 is what the syntax tree gives (key, kind, name, line, slots as written, result, `var` receivers, try count); `compiler/tests/facts-diff.sh` with `tools/ms/facts_diff.ms` compares it with `ms-tooling-dev facts` and requires equal entity keys, kinds and lines first. Rules met: the Rust key for an impl is its display name, so impl blocks of one type collide and the last block wins, a block being the inherent impls with the same written receiver (`var` in a function-type parameter counts) and bounds, at its first method's line; `move` versus `borrow` receivers and passing modes need the checker's moving-parameter facts, and `external`, `refs` and flows still come from Rust. The language server's needs list is a separate dump over the same columns.

Expression types: `ms_check_dump STDLIB --nodes FILE` prints `{"nodes": [{"id", "kind"}]}`, the type kind (Optional, Result, List, Map, Set, Bytes, Int, Float, Bool, String, Void, Promise, Other) of each expression the body pass typed, by the node id of `Syntax.id`. Absent means unchecked, as `facts().info(id)` being empty does in the Rust lint. Arm paths and bare arms are syntax, so a rule reads them from the tree. `compiler/tests/nodes-diff.sh` compares kinds with `ms-tooling-dev nodes`; coverage (typed by C over typed by Rust, about 11% of `accept`) grows with the body pass, and the pattern-literal of a match arm is typed only by C.

Effect columns: `--facts` prints `effects`, `reach` (both the declared effects the function reaches, as Rust fills them) and `permits` from `ms_effect_facts` ([effects.h](../../compiler/include/ms/effects.h)) for each function and constant the body pass claims and the scan sees through; every other callable prints empty lists and `"effects_known": false`, and `facts_diff.ms` compares the three only where it is true. A `type` with a field default is unknown too (a default runs code). `calls` lists the project functions a known function calls, as `file#fn#name` keys; a function with a method or interface call or an implicit `close` is partial, so `--facts` runs the ownership walk first (it marks the closing bindings). About a fifth of the corpus functions are known today. `--facts` also prints `ty` (the checked symbol type of a function; other kinds print ""), `error` (the E of its `Result` type, as the Rust `error_type` reads it), `exported` and `imports` (sorted unique paths per file); `first` and `last` are the declaration line and the line before the next declaration (or the last line), as the Rust collector defines them, so no end position is needed; `label` is `Receiver.method` for a method. Ownership columns: for a function the ownership walk kept (`body_checked` after `ms_module_check_ownership`, printed as `"ownership_known": true`) the slot `mode` (`var`, `copy` by `ms_classify`, `move` when declared or in `param_consumed`, else `borrow`), `scopes` (bindings with `MS_BIND_RESOURCE`) and `result_ownership` (`borrow` from `ret_borrowed`, else `owned`) come from the C tables; the walk skips methods, so a method, and a function it declined, print empty modes and `ownership_known: false`. Not printed yet: `refs`, `owned view` and `borrowed ok/error` results, `move` receivers, `external` and `flows`.

Project facts: `ms_tool_facts_project(path)` ([tool.h](../../compiler/include/ms/tool.h), `tool_facts.c`) loads the project of a file with `ms_project_load`, checks every module (`ms_graph_add_modules`, `ms_graph_check`, then the ownership walk) and prints one document through `ms_dump_project_facts`: keys, `file` fields and `imports` rows carry the module names relative to the project root (`src/lib.ms#fn#helper`). `ms_tool_facts(text)` still names its document `main.ms`. A function that calls a function of another project module prints `effects_known: false`: the effect scan lists that call as external and Rust lists it as a call. The scan also leaves such a caller partial today, so the effect thread owns the multi-module scan.

Commands: `tools/ms/main.ms` is the `ms` front; a command moves out of `delegate` (the Rust `ms` named by `$MS_RUST_CLI`) once a module answers it, and `make ms-cli-check` holds the front to the Rust output on `tools/ms/cases.txt`. `init` (`init.ms`) and `profile` (`profile.ms`, data side in `profile_data.ms`) are ported; `profile` builds through `ms build` of the Rust CLI and sets `MS_BUILD_PROFILE_ALLOCS` for `--allocs`. Verified: `profile.pb` equals the Rust bytes except the time field. Known gap: a stop request (SIGINT, SIGTERM) unwinds a waiting task and the program sits in its own process group, so interrupting `ms profile` kills the program before it writes a profile; the Rust CLI forwarded the signal. Tracked in [#5009](https://github.com/manuscript-lang/manuscript/issues/5009): Manuscript code needs a way to hold a stop request back (the runtime has `ms_stop_shield_enter`). `test` (`tools/ms/test/`: `plan.ms` selection and shuffle, `supervise.ms` the process run, `fault.ms` fault records, `run.ms` output and the `--json` document) builds through `ms build` with `MS_BUILD_TARGET=tests` (which also writes `<output>.tests`: source root, project root, test identities). The supervisor waits with `wait_any` over the child's stdout drain, a watcher on the results directory (a record wakes it, no timed polling) and a deadline for the oldest running test; a promise cannot hand a stream back, so each is a one-shot task that owns what it reads. `bench` (`test/bench.ms`) runs each bench in its own process, reads the `MSBENCH` line and holds the work counters to `--baseline`; a workspace root (`workspace.ms` reads the happy path; a bad pattern, a missing directory, a repeated member name or a member lock hands the command to Rust to word the error) runs each member as this command line again (`test/members.ms`), several manifests the same way, and `bench` at a root names the members and exits 2. `bench --ops` builds with `MS_BUILD_COUNT_OPS` and several test files with `MS_BUILD_EXTRA`. Only `--watch` stays with the Rust CLI. `fmt` (`fmt.ms`) formats explicit `.ms` files through `ms_tool_format` (libms, so the front links `libmstool.a`; `make ms-cli-check` passes it) and hands directories, `ms.toml`, `--drop-labels` and unreadable files to Rust before touching anything. `explain` (`explain.ms`) reads `data/codes.tsv`, embedded as `@data`; a Rust test (`explain_table`) fails when the compiler or lint tables change and `MS_BLESS=1 cargo test -p ms-cli explain_table` rewrites it. Verified side by side with the Rust `ms test` on pass, fail, skip, fault, never-waiting timeout, compile error, `--list`, `--shuffle`, `--repeat` and `--json`; one difference: a child ended by a signal reads "was terminated by a signal" (the stdlib gives no signal number). A project import cannot leave the project root, so helpers shared with `tools/conform` are copied (`json_out.ms`).

Analysis: `ms_tool_analyze(text)` ([tool.h](../../compiler/include/ms/tool.h)) checks one document and returns the checker's columns keyed by syntax-node id (resolution, expression types, callee, bindings, the symbols names resolved to), read in Manuscript by [analysis.ms](../../tools/lsp/analysis.ms) for the language server's hover and definition. Verified: a local's type, its uses and a call to a function of the same document resolve; a generic call (`max`) has no row yet because the C checker does not check generics (the generics thread), and `analyze_in(path, text, overlay)` loads the project with the open buffers in place of disk (`ms_project_load_overlay`); a document analysed without a path that imports a project module reports status 2. Joining a row to a position needs the tree of the same text (`ms_tool_parse`), whose ids match.

## Static tool archives are built position-independent

`libmstool.a` and `libms_tools.a` set `POSITION_INDEPENDENT_CODE`. A non-PIC object that references `environ` (install.c) makes the linker copy-relocate it into the executable, so libuv's `uv_os_environ` (via the GOT) reads a copy glibc never fills and `environment()` crashes with a segfault (exit 139). Any new object in these archives must stay PIC.

## The C API model reproduces Rust's quirks

`api_model.c` is byte-identical to the Rust model (923 declarations), so the Rust rules it copies are part of the contract: own methods are the bodiless methods of plain inherent impls (receiver args are the type's own parameters); bodied or bounded methods are implementation rows with a `// Receiver: ...; T: Bound` context, and a type variable's bounds list the declared bounds twice then the impl's; `legacy_contract` is `Name$methods` or `Name$K$methods`, blocks of the same receiver form merge and other forms are numbered by first appearance; shape interfaces (a plain interface whose operations a type has) are added to `implements`; primitives take members from `<Name>Operations` plus the shared integer interfaces with `T` replaced; JSON is HTML-safe (`\u0026`) with two-space indent. A mixed file's `+source` half does not see its native half's names unless `api_share_native_names` copies them, and constants are typed only by running the body pass on their module.

`libms.c` is one translation unit, so a `static` helper name must be unique across every file under `compiler/src` (prefix with the file's topic); a helper another file needs is exported through a header (`ms_prelude_names`, `ms_program_desugar_bundled`, `ms_doc_text_end`) so each file also compiles alone, which `make c-lint` requires. Entry points that need the embedded standard library sit in their own archive member (`tool_search.c`, `tool_check.c`), so programs that do not call them do not carry its 3 MB.
