# Poisoned slots make a stale view fail in every build

Verified 2026-11-16: whether a pointer into a dead stack slot misbehaves depends on what the backend reuses the slot for. The split-in-frame bug (#4284) showed `[:]` only in LLVM Release; Debug and Cranelift passed, and valgrind or ASan cannot see it (the stack memory is valid). `MS_POISON_SLOTS=1` fills each slot with `0xDD` where its use ends (a volatile `memset` before `lifetime.end`, written by `ll_temps_end` in `src/compiler/src/emit/emit_llvm.c`; a plain store would be dead), so the stale read faults or prints garbage deterministically. A corpus pass means no confined slot is read after its end.

Why a build option: the fill changes the code, so it is in `BuildOptions` and the cache key.

Apply when: changing `mir_slot_scope.c` or the slot markers of `emit_llvm.c`, adding a runtime function whose result may point into its argument, or debugging output that differs between Debug and Release.
Evidence: `make poison-check`; `MS_POISON_SLOTS=1 ms test --build-type Release tests/conformance/fixtures/e2e/accept/split-in-frame.ms` fails loudly on a checkout without the #4285 fix.

Valgrind on compiled programs (verified 2026-11-17, release build): a program that never leaves the main task runs clean (`bench/perf/string-lines`); one that switches task stacks (`regex-search`) reports hundreds of invalid writes and uninitialised reads inside `publish_region` and `switch_away`, because the runtime maps and switches its own stacks. A valgrind nightly needs a runtime mode without stack switching first; until then it only covers single-task programs and adds nothing over poison mode.

`tools/view-matrix.ms` (`make view-matrix`, nightly) generates 420 programs: view operation x way of holding the text x temporaries after the view (including branch and loop blocks, which is where slots share storage). Negative control (verified 2026-11-17): with argument-slot pinning switched off it fails 36 programs, all `split` views in Release; unmodified it passes. A new view-returning operation belongs in its `operations()` table.

Temporaries are shared by construction (verified 2026-11-17). Cranelift lowering gives the k-th temporary of each MIR block the same slot and the LLVM spill and result temporaries start their lifetime where they are made and end it at the end of their MIR block, so neither scans for confinement of those; `slotshare` scans only glue and `main`, and which MIR `slot`s are block-confined is a MIR fact (`ms_mir::slot_scope::confined`: every mention in one block, no escaping use, first access a write); the LLVM builder brackets exactly those (`alloca_scoped`, `begin_block`, `end_temps`) and the text scan now classifies only the remaining non-`slot` allocas. Frame bytes over the perf benchmarks equal the scan's to 0.001%. Run `make poison-check` with a fresh debug `ms` (`cargo build -p ms-cli`): a stale one fails 17 unrelated fixtures. The claim that a temporary dies with its MIR block failed once: a call result that a `put` moves into a variable keeps its memory as the variable's (`adopted` in `lower_func`), and 74 fixtures failed in `make drift-check` while a debug-build corpus run of the same change passed. After a change to slot sharing run `make drift-check` and `make poison-check`, not only the Cranelift corpus. Measured: frame bytes over fifteen benchmarks +0.07% (Release) and +0.015% (Debug), Debug build 1.5% fewer instructions on the 1,000-module project, `perf-counts` within 0.6%.
