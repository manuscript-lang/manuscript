# Shared is used like its value

Decision (Chinmay, 2026-11-01): `Shared(value)` has no `share`, `get`, `lock` or guard. The handle is used like the value; a `var` handle changes it and a `let` handle only reads it, under the ordinary ownership rules; calls that read the value run together and a call that changes it runs alone (see read holds below); any payload type works, and the expected type picks handle or value (`names = [9]` replaces the payload, `names = other` rebinds). The lock guard it replaces confused readers about what to use when. Cross-worker sharing is a later stage.

Keep it generic: the checker takes handle behavior from the `Proxy` marker in `@std/core.ms` (`impl Proxy for Shared[T]`), through `proxy_payload` and `Classifier::proxy`, never from the name `Shared`. A value the handle stands for is marked on the expression (`Info.through_shared`, `Info.into_shared`); lowering keys on those facts and on the box layout only. Add a new place where a value fits (an operand, a `for`, a `match`) with `Checker::payload_of`, not a special case.

Failure modes seen: copy-in/copy-out of a `var` argument lost a cancelled call's changes (fixed by the `$mem` instance, which changes the payload in place); holds on the cleanup stack interleaved with the unwind pass's push/discard windows, so holds record their guard depth and `end_abandoned_holds` runs before the cleanups; a park cancelled by a jump skips Rust destructors, so the queue exit is a `with_cleanup` entry; a hold taken before a method's arguments held the box across `slot.append(run())`, so collection changes take no hold.

Decision (Chinmay, 2026-11-01): strict `var`. A method that changes a `Shared` field is `var fn`, with no exception for handles in fields, so `Channel`, `HttpExchange`, log `Transport` and the group handles have `var fn` methods and their entries and handlers are `fn(var ...)` ([var parameters in function types](../../proposals/var-function-parameters.md)). Chinmay's reason: the markers should be able to decide later what may run in parallel.

Decision (Chinmay, 2026-11-01): a copy of a handle on shared state must come from a place that may change it, so `let` means read-only. `Classifier::shares_state` (a `Proxy`, an interface with a `var fn`, or a type holding one) picks the types; copying one out of a `let` or a plain parameter is an error. Under one-owner references (#2199) a record or interface value moves rather than copies, so the copies the rule sees are a `Shared` handle (`let b = a`, `Holder(h.field)`) and `.clone()`. A `let` that owns its value hands it on at its last use instead of copying. Decided (Chinmay, 2026-11-01): a stored closure keeps a writer only for a handle it captured from a `var`: there `fn: run(var ch)` changes the shared state, and the capture counts as a read.

Indirect `var` calls: the unwind pass covers a caller slot passed to `call.ind` only when every function made into a closure of that type borrows it, and it stops following a value at `shared.addr` (the box is outside the value). Without both, a task cancelled inside an entry with a `var` channel leaked its end (`tasks-cancel-channel-wait-memory` grew 8 KiB).

Migrating to the copy rule: a helper that copies its parameter (`var end = target.clone()`) takes it `var` or consumes it (`var end = target`, the caller passes a clone); a task closure that passes a captured handle as `var` needs the binding declared `var`. A fixer that adds `var` mechanically cascades into `var x.clone()` arguments and `var` on parameters that only read; fix each helper by hand.

Open failure mode: in `TaskGroup.results`, `for handle in self.tasks.keys()` (a `Shared` map) with `var found = self.tasks[handle]` and `self.tasks.remove(handle)` in the body made lowering treat `found` as a keyed borrow of the box and fail with "a keyed borrow needs a map"; binding the keys first (`let handles = self.tasks.keys()`) avoids it. Workaround tracked in #2236; delete it once that is fixed.

Read holds (Chinmay, 2026-11-01: "minimize locking"; `proposals/shared-read-holds.md`): a call that borrows through a `Shared` takes a read hold from before its arguments are evaluated until it returns, so a change from another task waits instead of freeing a payload a parked call borrows. That was a use-after-free (`shared-read-holds` fixture). The box's state word counts readers (`-1` while changing); holds are per task in `HOLDERS`; a free box wakes every waiter. `Shared` never leaves its isolate, so there are no atomics or OS locks. A lent result through a handle is copied out (`owned_lends`), and payloads without heap memory take no hold. There is no writer preference: it deadlocked two readers waiting on each other. A position is held for a change only when the callee's body changes its memory (`Cx::changed`); a declared `var fn` that only stops native work (a watcher's `close`) holds for reading, or closing it could not wake a parked `next()`. A reader parked until a writer that changes the payload runs is a deadlock, the same as two `var` calls today.

Nested access (Chinmay, 2026-11-02: "faults are not good like this"): a read from the task inside its own call on the value goes ahead (`msrt_shared_wait` returns 1; a read hold nested in the task's own write leaves the state word alone). A change inside the task's own call is rejected by the checker when a closure literal argument changes shared state through a capture that holds a handle of the same type (`check_reentry`, `Classifier::holds_handle`). Interface values are not followed, so a logger in a callback stays fine. The runtime fault stays only for callbacks the checker cannot see, such as one stored in a record (#2340).

Apply when: adding shared state to the stdlib, or touching `Shared`, holds, scope-end cleanup or cancellation cleanup.
