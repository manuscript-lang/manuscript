# Task stacks are 512 KiB slots in 256 MiB regions

Verified (2026-11-04, sandbox Linux 6.18 x86_64, release build): a task stack starts as a 512 KiB slot carved from a 256 MiB region (`task.rs` `SLOT`, `REGION`; `sys::map_region` reserves it `MAP_NORESERVE` and `MADV_NOHUGEPAGE`, so a touched page costs one page and not a 2 MiB huge page). The main task gets a region of its own; a slot holds about 3,000 frames of ordinary code (141 bytes per frame with LLVM, 390 with Cranelift), and a task that recurses past it grows (below). Generated code finds the running task's `fault::Hdr` through the region's last 16 bytes, a pointer the scheduler writes before every switch (`publish_region`); the block itself lives in the `Task` record, so a stack page holds nothing another thread reads. A parked task costs one stack page plus about 1 KB of page tables plus about 0.9 KB of records (5.0 KB resident at 100k and at 1M tasks, 1 KB of page tables beside it); a task parked for two scheduler idle rounds hibernates: its used stack is copied to the heap with exact-size `malloc` (the runtime's large classes would round 3 KB up to 4 KB and save nothing) and every page of the slot is given back, and the copy goes back to the same addresses before it runs (`hibernate_idle`, `freeze`, `thaw`), so every pointer into the stack stays valid. Hibernation assumes nothing reads a parked task's frames; two things do, and both pin the task (`Task.pinned`, skipped by `hibernate_idle`): a shielded pool job borrows a slice of the caller's frame (`pool::run_shielded`), and a promise's work reads its captures from the frame that started it, so `msrt_promise_start` lends the creator's stack (`task::lend_current`) until the work's task has ended. Missing the second made `fifo_cancel` and `fs-calls-in-tasks` fail on about one CI run in four: the task started by `promise(fn: f(x))` read a zeroed `x` from its hibernated creator (an empty path, `EINVAL`), which only shows under load, when the scheduler idles twice before the promise task starts. A third writer is `promise::ask`, which keeps its reply slot on the asking task's stack and pins the task until the owner's post arrives; without the pin the answer went to a hibernated page and `promise-cross-thread.ms` hung on about one loaded run in sixty (#3342). Any cross-thread write into a parked task's frame needs `pin_current`. Hibernated, a task is 3.8 KB resident whatever its high-water mark was (9.0 KB after a 256-frame call chain, 5.0 KB bare), because what remains is the park depth: 2.9 KB of frames from `Promise.wait` down to `switch_away`. Thinner frames on that path are the next lever, not the slot size. The blocking task itself is never frozen: its saved stack pointer is stale while it runs the scheduler. One idle call walks every slot in chunks of 4,096 and stops when work arrives, so a wake-up waits for at most one chunk.

Growth: the recursion check every cyclic function runs (`DepthEnter`, kept by `strip_depth`) is the first instruction of its entry block (`ms_mir::verify` enforces it; the inliner drops the checks of an inlined body, and passes that prepend to the entry block insert after it with `entry_insert_at`). When the stack pointer is below the limit, the function stores its raw Cranelift parameters in a heap block, calls `msrt_task_grow(shim, block)` and returns the results the shim leaves there; the shim (`Glue::GrowShim`, one per cyclic function) calls the function again. The runtime takes the task's next segment, a slot from the same pool kept until the task ends, so a loop at a boundary pays one call and no allocation (measured 2026-11-04, release LLVM, x86-64 sandbox: 20,000 calls of `depth(3400)` in a task, each crossing the first slot, take 560 to 650 ms, the same as on the main task within run-to-run noise of about 10%, so a crossing costs well under a microsecond; `depth(900000)` in a task takes 23 ms against 22 ms on the main task), writes the segment's chain cell (its top 32 bytes: the bounds and chain of the segment below, `fault::STACK_CHAIN`), sets the limit and bounds (`STACK_LO`/`STACK_HI` always describe the running segment: the depth fault, the overflow signal handler and Windows `__chkstk` rely on it), and switches with `msrt_call_on_stack`, whose frame keeps the frame-pointer chain continuous and carries unwind info (a test panic crosses it on Linux and macOS; Windows SEH cannot unwind across stacks, so the unit test leaves the guard exit from a segment to the e2e fixture). On Windows the assembly installs the segment's thread environment block fields after the stack pointer moves and the caller's after it moves back, and `msrt_guard_jump` takes the fields of the segment they land on (`task::segment_teb`), for the reason under Guards. Frame walkers (`walk_frames`, `profile::record`) follow the chain when a frame leaves the bounds and suspend the "frames go up" check at the crossing. The grow block is a heap allocation the caller frees after the shim returns, but a cancellation or fault inside the shim leaves by a jump, so `msrt_task_grow` registers a cleanup that frees it (leaked one block per segment before #2639; `promise-cancel-grown-stack.ms` under `make leak-check`). A guard frame records the segment it was opened on and `guard_exit` calls `task::restore_segment`, since the jump skips the returns of the grows above it. The cap is the region: 511 segments, then today's stack overflow fault; the main task, which already has a region, never grows. A task parked on a grown segment is not hibernated (`seg != 0`); one parked on its home segment also gives back the pages of its unused segments. Not done: the Windows fault-report walker (`walk_scanned_frames`) stops at the segment boundary, so a report there shows the frames of the faulting segment only. Verified: `tests/conformance/fixtures/e2e/accept/task-stack-growth.ms` (200k frames in a task, a loop at the boundary, a runaway in a task, a guard exit from a segment) on both backends; `cargo test -p ms-rt a_task_grows`.

The running segment's bounds and chain cell (`STACK_LO`, `STACK_HI`, `STACK_CHAIN`) are per-thread (`isolate_static!`), because every scheduler thread switches them in `swap_ctx` and grows its own tasks. They were `Process` statics, one copy shared by all threads: with 32 or more promise tasks recursing 20,000 frames deep and parking on four threads, two threads wrote each other's segment, the chain cells formed a cycle across tasks, and `capture_frames` (run at every promise start) followed it forever with every scheduler thread at 100% CPU (#2644, found by gdb: the cell addresses repeated every five hops). The Windows sampler reads the runtime thread's cells through pointers registered by `start_sampling`; a new per-task global that `swap_ctx` swaps must be a thread-local for the same reason. `GUARD_MESSAGE`, the cell `guard_exit` fills before `guard_jump` and `msrt_guard_call` reads, was a process-wide `static mut` for the same mistake: promises faulting on different threads at once returned empty or foreign reports and segfaulted on a double release (#2650). Any `static mut` or `Process` that runtime code writes while tasks run is suspect; the rule is that user code runs on every scheduler thread, so only write-once values may be process-wide. Verified: `task-stack-growth.ms` "many tasks recurse past their first slot and park on several threads".

Guards: Linux 6.13+ installs a guard region (`MADV_GUARD_INSTALL`), which splits no mapping, so 1M guarded slots cost 25 mappings; older kernels and macOS `mprotect` the bottom of the slot, which splits the region's mapping, and `vm.max_map_count` (65530) then bounds a process near 32k tasks until it is raised (#2483). A slot is never unmapped on its own (that would split its region too); regions go back at teardown. Windows switches contexts with the same assembly, which installs the next stack's thread environment block fields only after the stack pointer has moved, so a register save never touches a guard page while the block describes another stack (the kernel grows a stack only for a fault inside the block's bounds; anything else is an unhandled guard-page violation, exit 0x80000001). It commits a slot's top pages and lets the kernel's guard page commit the rest. Verified 2026-11-04 (probe run on CI, `ms-std-net` `request_bodies_must_match_content_length` died deterministically on both Windows architectures): committing a guard page with `VirtualAlloc` makes the kernel set the calling thread's `StackLimit` to the page above it even when the page is in another task's slot, so `sys::commit_guard` saves and restores the limit; left mixed, the next `__chkstk` probe (a frame over a page) walks from the foreign limit into the foreign guard page and the process exits 0x80000001. A unit test cannot catch this (the probe needs a large frame in the right task at the right time); the Windows CI matrix is the check.

Apply when: changing stack allocation, the scheduler's idle path, context switching, the recursion check or anything that inserts at a function's entry block, or adding another per-operation task.
Evidence: `crates/ms-rt/src/task.rs` `mod stack`, `hibernate_idle`; `crates/ms-rt/src/sys.rs` `map_region`, `guard`; [`bench/perf/tasks/README.md`](../../bench/perf/tasks/README.md).
Verify: `ms run bench/perf/tasks/main.ms -- 1000000 sleep` parks a million tasks in under 5 GB (resident plus page tables); `cargo test -p ms-rt` (`stack` and `hibernat` tests).

Freeing deep data does not grow the stack: the named drop glue of a type that reaches itself (`Module::drop_recurses`) calls `msrt_drop_enter`, and past 256 nested drops parks the value in a heap block on a per-thread worklist (`ms_rt::dropq`) that the outermost drop drains (`msrt_drop_leave`). Before this a 6,000-deep TOML table or 9,000 nested arrays freed in a promise died with "stack overflow", because glue and `drop_map` never ran the recursion check; the main task's 256 MiB region hid it. Only data deeper than the limit is freed out of order. A guard jump resets the counter (`guard_exit`). Verified: `task-deep-drop.ms` on both backends.
