# Task stacks are 512 KiB slots in 256 MiB regions

Verified (2026-11-04, sandbox Linux 6.18 x86_64, release build): a task stack is a 512 KiB slot carved from a 256 MiB region (`task.rs` `SLOT`, `REGION`; `sys::map_region` reserves it `MAP_NORESERVE` and `MADV_NOHUGEPAGE`, so a touched page costs one page and not a 2 MiB huge page). The main task gets a region of its own, so the documented 256 MiB of recursion still holds for the program; a promise task holds about 3,000 frames of ordinary code (141 bytes per frame with LLVM, 390 with Cranelift). Generated code finds the running task's `fault::Hdr` through the region's last 16 bytes, a pointer the scheduler writes before every switch (`publish_region`); the block itself lives in the `Task` record, so a stack page holds nothing another thread reads. A parked task costs one stack page plus about 1 KB of page tables plus about 0.9 KB of records (5.0 KB resident at 100k and at 1M tasks, 1 KB of page tables beside it); a task parked for two scheduler idle rounds hibernates: its used stack is copied to the heap with exact-size `malloc` (the runtime's large classes would round 3 KB up to 4 KB and save nothing) and every page of the slot is given back, and the copy goes back to the same addresses before it runs (`hibernate_idle`, `freeze`, `thaw`), so every pointer into the stack stays valid. Hibernated, a task is 3.8 KB resident whatever its high-water mark was (9.0 KB after a 256-frame call chain, 5.0 KB bare), because what remains is the park depth: 2.9 KB of frames from `Promise.wait` down to `switch_away`. Thinner frames on that path are the next lever, not the slot size. The blocking task itself is never frozen: its saved stack pointer is stale while it runs the scheduler. One idle call walks every slot in chunks of 4,096 and stops when work arrives, so a wake-up waits for at most one chunk.

Guards: Linux 6.13+ installs a guard region (`MADV_GUARD_INSTALL`), which splits no mapping, so 1M guarded slots cost 25 mappings; older kernels and macOS `mprotect` the bottom of the slot, which splits the region's mapping, and `vm.max_map_count` (65530) then bounds a process near 32k tasks until it is raised (#2483). A slot is never unmapped on its own (that would split its region too); regions go back at teardown. Windows switches contexts with the same assembly, moving the thread environment block's stack fields with the stack, commits a slot's top pages and lets the kernel's guard page commit the rest.

Apply when: changing stack allocation, the scheduler's idle path, context switching, or adding another per-operation task.
Evidence: `crates/ms-rt/src/task.rs` `mod stack`, `hibernate_idle`; `crates/ms-rt/src/sys.rs` `map_region`, `guard`; [`bench/perf/tasks/README.md`](../../bench/perf/tasks/README.md).
Verify: `ms run bench/perf/tasks/main.ms -- 1000000 sleep` parks a million tasks in under 5 GB (resident plus page tables); `cargo test -p ms-rt` (`stack` and `hibernat` tests).
