# BigInt, Decimal and time natives are C; zones live in Manuscript

Verified: `src/runtime/std/bignum.c` (a thin layer on OpenSSL `BIGNUM`, already linked for crypto; Chinmay, 2026-11-20: no hand-rolled bignum), `bigint.c`, `decimal.c` and `time*.c` replace the Rust crates. `ms-decimal` is deleted; `ms-lower/src/decimal_literal.rs` only parses a literal into the stored coefficient and exponent. The time natives take an offset and a zone name; zones resolve in `src/stdlib/internal/zone.ms` ([zones](time-zones-are-bundled-tzif-read-by-manuscript.md)), so the C has no zone seam.

- Oracles, not hand checks: `src/runtime/tests/oracle/*_gen.py` write exact Python integers and `decimal` answers, and `time_golden.txt` is Go's `time` (UTC and fixed offsets only; named zones run in conformance). A positive-only fuzz missed a sign bug in the divide-and-conquer `to_string`; the oracle's negative cases caught it.
- BN adds only what BIGNUM lacks: floor shifts, two's complement and/or/xor on negatives, integer sqrt, correctly rounded `to_double`, 128-bit and int64 conversion, text in any radix, and a power-of-two `pow` (BN_exp on 2^(2^24) takes over a minute).
- Decimal speed: add, subtract, multiply and round stay in 128-bit arithmetic (`round_wide`, `combine_wide`, `rounded_magnitude`; a coefficient is below 2^113) and fall to the bignum only when the aligned sum or product exceeds 128 bits, and divide always uses it. That took `decimal.add_round` from 377 to 65 ns/op (2026-11-20, `bench/perf/stdlib/numbers_bench.ms`); before it, pooled BIGNUMs and a shared `BN_CTX` had taken the benchmark from 13.8 s to 4.2 s against Rust's 3.4 s. Profile with `valgrind --tool=callgrind` before adding more.
- Wide products (both operands at least 2^16 bits) use `bignum_ntt.c`, three-prime NTTs with Garner recombination, and `pow` of a wide result squares through it: `3^1000000` takes 24 ms (OpenSSL's Karatsuba took 240 ms; the retired code 30 ms). Still quadratic and slower than the retired code: `to_string` and parse of huge numbers (477k digits, 2 s) and division; a divide-and-conquer conversion needs a reciprocal-based division on the transform multiply. Older note on huge values: `3^1000000` 0.25 s against 0.03 s, a 120k-digit `to_string` 0.21 s against 0.08 s (OpenSSL's `BN_exp` and radix conversion are not asymptotically fast).
- A C fault needs frame pointers for the stack line fixtures expect: `cmake -P cmake/BuildRuntime.cmake` passes `-fno-omit-frame-pointer`.
- Every std test links all of `src/runtime/std/*.c`, so a new cross-file seam needs stubs like `src/runtime/tests/fake_list.h`.

Apply when: changing bignum, Decimal or time natives, or porting the zone database.
Evidence: [bignum.h](../../src/runtime/std/bignum.h), [decimal.c](../../src/runtime/std/decimal.c), [time.c](../../src/runtime/std/time.c), [oracle](../../src/runtime/tests/oracle/).
Verify: `make c-test` passes (about 7,000 oracle cases) and `make conform` is unchanged.
- BN failures: `must` raises an overflow fault for OpenSSL's size cap (`BN_R_BIGNUM_TOO_LONG`, about 2^29 bits) and the out-of-memory fault otherwise. `BN_gcd` is constant-time and slow on wide values, so `ms_big_gcd` runs Euclid with `BN_mod`. Operations that can shrink a wide value (sub, divmod, mod_floor, shift_right, gcd) go through `result_end_shrinking`: when an operand was at least 4096 bits the small result moves to a right-sized BIGNUM and the thread's `BN_CTX` is released, so a thread does not pin the buffers of the widest value it ever saw. Only those ops pay the check; multiply and add measured 12% slower when every op did.
