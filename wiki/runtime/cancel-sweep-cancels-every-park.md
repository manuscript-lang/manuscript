# The cancel sweep cancels each test at every park

Verified: `make cancel-sweep` (`tools/cancel-sweep.ms`) reruns each `tests/conformance/fixtures/e2e/stdlib` test with `MS_CANCEL_AT_PARK=k` for every park k, on the `stats` runtime, and fails when a cancelled run ends with more live `ms-rt` blocks than the uncancelled run. On 2026-11-08 all 191 fixtures were clean at up to 16 parks each.

The counting runtime also counts Rust's own heap (`ms-rt rust heap at exit: blocks=N`; the std heap is the system allocator there), and the sweep fails on a cancelled run that ends with more Rust blocks than every one of five uncancelled runs, reproduced on two re-runs (`heap:`; worker threads leave buffers of timing-dependent size, so one uncancelled run is not a baseline, and a test whose baseline varies is checked on one thread), which is how `Parked`-class leaks in native code show ([guard exits](runtime-guard-exits-skip-native-rust-destructors.md)). It cannot see fd leaks; count `/proc/<pid>/fd` for those. Park counts are per process and include scheduler threads, so a threaded test can vary. The injection skips a scheduler worker's idle root park (`task::sweep::internal`), which is not an await point of the program. A cancel that ends the process (status 143) prints no counts and is not swept.

A park inside a shield (a scope close, a promise's task-end drop) is not cancelled: a real cancel stays pending under a shield, so the injection records the request and the next unshielded park reports it (`task::sweep::cancel_here`). Cancelling shielded parks had made every `close` that parks look like a leak (about 100 of the 145 first-night hits, 2026-11-15, #4052): the shielded close runs with its owner uncovered, which a real cancel never interrupts.

A task started while its spawner is shielded (`Task.born_shielded`) is shielded work too: the sweep does not cancel its parks. A close that writes through a child task (`append_file(..).wait()` in a `close`) otherwise had the child cancelled during a shielded close, the close failed and faulted, and about 90 of the 119 leaks of 2026-11-18 were that artifact; no real cancel reaches such a child.

An implicit close is always shielded, including the close of a discarded statement result (`xs.pop()` as a statement, `drop_unused`) and of a pending temporary (`close_temp`): they were the two that were not, so a cancel arriving during such a close made it fail and then fault (`implicit-close-shielded.ms`).

A thread's promise table owns the closures of deferred promises nobody waited on; `promise::teardown` drops them (a cancelled `promise-cross-thread.ms` run leaked two blocks at every park until it did).

A close that fails at a scope end faults, and the cover for the slot (`cover_shielded_slots`) must still free the collection: the cover skipped a slot whose scope entry was discarded just before the shield, did not see a close inlined as a call on a field address. Do not put `none` in an optional's place while its payload closes: a nested optional (`opt<opt<T>>`, made by a function-value adapter) closes its payload in a temporary slot with no cover, so a fault frees nothing and one block leaks (#4211). A cancel in a child task's park (the file write behind `append_file`) makes such a close fail, which is how the sweep found it (`failed-close-at-scope-end-frees-collection.ms`).

The unwind pass skips every call after a `move.out` that is not filled back (a hole in the owner), so a field read of a temporary (`(f()?).kind`: `move.out` then `type.release` of the rest) made it skip the rest of the function and leak what the frame held when a later park was cancelled (`random-weight-ranges.ms`); a move-out the release follows at once opens no hole.

A cover pushed for a slot in one branch (the early-return exits of a `?` each get one) does not cover another exit's close: `cover_shielded_slots` counts an entry only when it dominates the window (`deque-resource-growth.ms`).

A `var` local with no scope entry that is passed to a callee which parks and rewrites it (take, park, put back) was freed by nobody on a cancel: the callee treated the taken value as the caller's. `slot_owned_params` in the unwind pass now finds a slot parameter every caller fills from a local slot nothing else covers, and the callee covers what it takes (`tree.ms`).

A move-out hole no longer hides the other values: while an owner has a field moved out (`hole_owners` names it), a call still registers every live value except that owner, so a slice held across the parking write in `FailingSink.write` is freed (`iotest-golden.ms`). A hole whose owner has no name (not a `type.get`/`alt.get` projection) still skips everything.

A fault ends a task by a jump that skips Rust destructors, and `fault_vec` never returns, so its locals were never dropped: a run the cancel made fail ended with 12 to 14 extra Rust blocks (the frame list, the last fault record, the guard and cleanup buffers). `fault_vec` now drops the frames and the counting build releases the fault state at exit (`release_fault_state`), leaving one block; the sweep allows that measured difference (a probe test that faults against one that passes, `report` in `tools/cancel-sweep.ms`) for a run that fails, and nothing more.

A native that raises a cancel (`ms_rt::glue::cancelled()`) jumps, so it must drop every Rust value its frame owns first, parameters included: `msstd_process_command_run` kept its argument and environment `Vec<&str>`, leaking 32 bytes whenever `run` was cancelled (`host.ms`).

A `var` that a closure captures by reference, or that is only put, taken and loaded, may hold its value across blocks in the unwind pass (`find_cells`); an early exit of `?` takes it back out in another block. Only captured slots, never-handed fresh values and an owned slot parameter span blocks: a slot holding a field taken out of a captured owner (a websocket's socket) was covered twice and the double close broke `http-websocket` under `--build-type Release` only, so run cancel-related fixtures with `--build-type Release` and the conformance harness, not just `ms test`.

A function that owns a slot parameter (`slot_owned_params`) is owned only through direct calls (a method table entry or a function reached another way never is: `WatchSource.next` got a cover that freed the watcher twice, `fs-watch-cancel.ms`), and a slot parameter spans blocks only when every `put` into it is a fresh value (`ReadStream.next` takes its source out and fills it back, and a callee cover there stopped `net-close-releases-socket.ms` from closing the socket). A function that owns a slot parameter covers what it takes from it; a call that hands a slot to such a callee (direct, or through a function value whose every candidate owns it, `hands_off`) pauses the caller's cover for the call. Creating a closure is not a call: counting `closure.new` as one had made no closure ever own its slot parameter, which left the exchange in `with_access_log` uncovered when the logger parked (`router.ms`). A call result that owns nothing and is no address (a promise handle) is not a borrow of the slot (`borrows_slot_value`); counting it made `Resource.close` unsafe to pass a slot to, so a cancel inside an explicit `close()` leaked the resource (`scalar-lowering.ms`).

A field moved out of a value taken from a slot parameter no caller-free function owns (`self.source` out of a `ReadStream` before the park in `read_bounded`) is still the caller's: covering it in the callee freed the same 16 B interface box twice when a stalled read was cancelled (`live blocks: -1`, `read-stream-timeout.ms`), so `type.get` plus `move.out` of a caller's value joins `caller_values`. A negative live count is a double free: find the block by recording every allocation and free address in the stats allocator.

A promise that holds a value with closeable parts (a promise returned by a promise) must be closed with its type, which only compiled code can do: the runtime's descriptor drop of a `Promise` value frees nothing, so the inner promise kept its two closures when the outer one was dropped by the runtime (`promise-cross-thread.ms`, only with several threads: the inner work had to be queued or stolen at the cancel). `msrt_promise_end` cancels and joins the work and keeps the slot; a cancelled `wait` only ends it, and `Promise.close` takes a value left in the slot (`msrt_promise_take[T]`, so scope end closes it) before `msrt_promise_drop` frees the slot.

Apply when: adding a park, a cleanup, or an `rt::Parked`; run the sweep on the touched fixture (`ms run tools/cancel-sweep.ms -- <file>`).

Found by the first sweep (baseline, not cancellation): `http-hardening.ms` "close cancels a handler parked on a request body" ends with one 16 B block even with no cancellation (a client read after the server closed the connection triggers it); the sweep compares against that baseline, and `make leak-check` owned the fix (#3083, covered by the MIR unwind pass).

## Rust heap counts vary with worker threads, not leaks

- A scheduler thread's isolate statics have no destructor, so a buffer a thread keeps for later is counted as live Rust heap at exit unless `task::teardown` resets it. `Sched.spares` (cleanup and guard buffers for the next spawn) was never reset: about 7 blocks per started worker, and how many workers start depends on timing. That made the heap ceiling noisy (fs-write-backpressure: 24 to 47 blocks for one test); with `spares` reset it is 4 to 8. When the heap count varies between identical runs, look for per-thread state `teardown` skips before widening any ceiling.
- A pool job whose waiter was cancelled is reaped only at the next submit; the stats build reaps it at exit (`pool::reap_at_exit`).
- The stats exit stops the pool threads and the file watcher before counting (their thread-local buffers otherwise varied the count by about 8 blocks).
- The rest, found with a size histogram and a backtrace on 64 KiB allocations: each scheduler thread that served an HTTP connection kept its thread-local `Reactor` (9 blocks, 64 KiB `scratch`) for good, because the detached reactor task parked at the program's end held an `Rc` and its frame was discarded, not unwound. `task::unwind_others` now cancels every other task of a thread and runs it to its end when a scheduler thread ends (always) and when `main` ends in a build that frees at exit (`msrt_exit_frees`: stats, `MS_FREE_AT_EXIT`); http-paths dropped from 70 to 37 blocks, http-websocket from 46 to 24-29. Which threads served is still timing, so the sweep compares the Rust heap only on one thread (`MS_THREADS=1`, `heap_sweep`), where it is exact: five equal uncancelled runs at the default thread count can agree by chance.

A callee owns a slot parameter only when nothing else covers the value it is given. A function that takes a value out of a slot something else covers (a slot parameter its callers cover, or a local with a cleanup entry such as a closeable `conn`) and passes it on through a fresh slot (`ReadStream.next` handing `source` to `read_bounded`; `conn.input.next(timeout:)`) leaves the covering owner reading the slot as the function left it, so an owning callee frees the value a second time (`stream-nested-timeout.ms`, `http-server-half-close-mid-request.ms`: a negative live count, or a closed `Connection` whose `Bound` owner reads as garbage). `refilled_from_covered` excludes those fresh slots from ownership. The result depended on unrelated code: a custom `Source` in the same file made `read_bounded` unsafe for its caller to cover, so it owned its slot and the double free appeared.

A resource temporary passed as a `var` argument (`child.stdout().next()`) is taken out of its owner, which cancelled its close registration; the callee (not a safe borrower, and not an owner while another caller covers its slot) then ran with nothing covering the value, so a cancel inside leaked it (#4555, `descriptor-backpressure.ms`). `var_argument` now keeps the close registered on the argument slot for the call (`var_cover`, disowned in `restore_var_arguments`), the same cover a named `var` has.

Adversarial programs (`cancel-var-fields.ms`, `cancel-var-params.ms`, `cancel-child-lines.ms`) found three more holes in the unwind pass:

- A `var` slot parameter refilled from a covered owner (`fresh_defs` in `find_cells`): a `type.fill` result is a fresh value, so a `var` parameter rebuilt across parks leaked when cancelled; vtable methods never own a slot parameter, and treating every pointer parameter of one as covered (`covered_slot_params`) stops the broader rule from double freeing `lines(child.stdout())`.
- A call inside a hole window (`self.inner.bump(key)` on a `var` method while `inner` is moved out of `self`) left the other fields of `self` uncovered, because dropping the half-emptied owner whole frees the moved field twice. `name_holes` gives each moved-out field a stand-in value live while the hole is open; its cleanup is `unwind.drop_rest`, a `type.release` that skips that field. A value taken from a slot whose close is registered (a `var conn` with a scope close) is dropped whole by that close, so it gets no stand-in: covering it twice crashed `conn.input.next` (SIGSEGV at one park only, found by sweeping `net-adv.ms`).
- The sweep once skipped a run killed by a signal (it prints no counts, like status 143), so that SIGSEGV showed only as a stray leak elsewhere; a run that ends in `terminated by signal` is now a `leak:` hit. Reproduce a park by hand with `MS_CANCEL_AT_PARK=k ms test file --test name`.

A cancelled frame ends the promises it started before its cleanups run, by cleanup-stack height (`started_at` against the frame's base; a promise a caller started registered its close lower, and ending one the frame is itself waiting on or running deadlocked `promise-semantics.ms`) (`promise::end_started_by_current`, called from `msrt_cleanup_unwind_to`, `msrt_cancelled` and the guard's cancel exit). The cleanup stack runs newest first and the unwind pass registers an owner's drop in a window, newer than the promise's close made earlier, so a value a running promise borrows (`derived` in `net.ms` "resolve returns typed DNS records", the promise's `resolve_dns`) was freed while the promise's task still read it: a SIGSEGV in about 1 in 200 sweep runs, with `0xdd` poison in a register (#4574). Found by sweeping with the signal check on, and caught by a core dump of the exact test binary: copy `program` out of `/tmp/manuscript-test-*` while it runs, and set `ulimit -c unlimited` (the core lands in the test's working directory); a rebuilt binary differs from the crashed one only when the inputs differ, so a garbage backtrace means the wrong binary.
