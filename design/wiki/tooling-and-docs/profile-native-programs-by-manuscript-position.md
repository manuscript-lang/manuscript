# Profile native programs by Manuscript position

Decision: teach investigation through a runnable workload, `ms profile`, and native source breakpoints. Explain flat versus cumulative samples and retain the actual debug-information limits beside the debugger workflow. Use file/line breakpoints instead of guessing native symbol names. LLDB/GDB syntax documentation establishes command spelling, not Manuscript-specific runtime behavior; verify the executable's symbols and line mappings and distinguish actual debugger execution from artifact inspection in validation reports. Keep environment-specific addresses, sample counts and timing out of reusable output examples.


Allocation profiles (`ms profile --allocs`) are runtime sampling, not a counter on every call: `MS_PROFILE_ALLOCS` makes the allocator report each request's size, and every `MS_PROFILE_ALLOC_PERIOD`th (default 128) allocation of the main thread walks the frames like a CPU sample (`src/runtime/entry/profile.c`, `on_alloc`). The Rust runtime paid +0.4 to 1.1% instructions on allocation-heavy programs for an always-compiled check, so keep the idle cost to a branch on a flag; measure it with callgrind on an allocation-heavy program. Only the thread that runs `main` is sampled. Attribute a sample to the innermost non-`[runtime]` frame, or every row reads `[runtime]`.

Debug information (`src/compiler/emit/emit_debug.c`): every instruction carries a `!dbg` source place (file, line, a scope per module-wide scope number), written into one LLVM module with a `DICompileUnit` and a `DISubprogram` per function; the function's first line row covers its prologue so a breakpoint lands after the parameters are placed. Types are not described (`MD_NO_TYPES`). Debug info costs compile time: the project's line for it is 1%, so measure before adding variable descriptions (the Rust `dbg.value` parameter variables cost about 4% of compile time and 0.4% of size). On macOS a type nothing refers to is dropped by `dsymutil`.

Reading the report (2026-11-17 review of `ms profile` and `ms diagram`): the start shim before `main` is not a program frame, so folded stacks are rooted at `main`, not `[runtime]` (it made `[runtime]` read as 100% cumulative); `[runtime]` as a leaf means a runtime call from the last Manuscript frame. A report of fewer than 100 samples says so. Inlined callees are not frames, so a hot function inlined into its caller is reported as the caller; frames from DWARF inline records are the remaining gap. The code map's `unknown` effect is shown, never filtered: `unknown` is not "pure".

C build (2026-11-23): the C runtime samples only the thread that runs `main`, through `ms_sched_sample_window` (src/runtime/entry/profile.c; the clock is src/runtime/sys/{posix,windows}/sampler.c). Linux and macOS use `ITIMER_PROF` (CPU time), and every other thread blocks SIGPROF, because the kernel hands a process signal to any thread that does not block it and the idle initial thread would otherwise take them all. Windows has no profiling signal: a sampler thread suspends the target and reads its registers, so its samples are wall-clock and its walk scans for frame records. The kernel delivers the timer on its own tick (250 Hz is common), so the runtime writes `# hz=` as samples over the process CPU time it measured, not the requested rate; without that the report's seconds were four times too short. The C runtime is built without frame pointers, so a sample inside runtime code holds the generated caller's frame register and the walk would drop that caller: the sampler looks for the first source return address above the stack pointer. `MS_PERF_MAP=1` writes `/tmp/perf-<pid>.map` (posix only).

Apply when: changing source maps, line tables, the perf map, or profile output formats.
Evidence: runtime profiling, profile CLI tests, debug artifact tests.
Verify: run a representative profile, inspect the generated bundle and final executable line tables, and run the native debugger where installed and permitted. Keep profile CLI and debug-artifact tests passing.
