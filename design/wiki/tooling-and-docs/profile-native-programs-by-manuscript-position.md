# Profile native programs by Manuscript position

Decision: teach investigation through a runnable workload, `ms profile`, and native source breakpoints. Explain flat versus cumulative samples and retain the actual debug-information limits beside the debugger workflow. Use file/line breakpoints instead of guessing native symbol names. LLDB/GDB syntax documentation establishes command spelling, not Manuscript-specific runtime behavior; verify the executable's symbols and line mappings and distinguish actual debugger execution from artifact inspection in validation reports. Keep environment-specific addresses, sample counts and timing out of reusable output examples.


Allocation profiles (`ms profile --allocs`) are runtime sampling, not a counter on every call: the `alloc-profile` runtime feature adds one per-thread countdown to the allocator entry and every 128th allocation walks the frame pointers like a CPU sample. The check cost +0.4 to 1.1% instructions on allocation-heavy suite programs (objgraph, strings, graph; callgrind) even when idle, so it is compiled only into a second archive, `libms_native_allocs.a` (`cargo xtask runtime --alloc-profile`; release packaging and main/scheduled CI build it, pull requests do not), which `ms profile --allocs` links; linker wrapping cannot catch allocations made inside the runtime. The runtime thread only; other threads' heaps are not sampled. Attribute a sample to the innermost non-`[runtime]` frame, or every row reads `[runtime]`.

Debug types are described once in `ms_mir::debug_types` from the machine layout (`Layouts`) and rendered by both backends: DWARF DIEs in `ms-clif/src/dwarf.rs`, and the global `ms.debug_types` in the first LLVM unit only, a constant whose type is a union with one member per Manuscript type (a type nothing refers to is dropped by macOS `dsymutil`, `retainedTypes` did not survive it, and every unit would repeat the types). A `pointer_type` needs `baseType: null` for void in the bundled LLVM. Values are flattened into registers, so a variable is described per leaf: `Func.names` (set in `lower_callable`, keyed by `Value`, since passes add and drop params) feeds Cranelift value labels, whose ranges become a `DW_OP_piece` location list per parameter (`dwarf.rs::emit_vars`; `DW_AT_frame_base` is the CFA, the CU needs `DW_AT_low_pc` 0 or `--verify` rejects the lists). The function's first line row covers its prologue so a breakpoint lands after the parameters are placed. LLVM release builds describe types only, through the `ms.debug_types` anchor (a `DIGlobalVariable`, kept by `llvm.used`; it works in a line-tables-only unit): `dbg.value` parameter variables there cost about 4% of compile time and 0.4% of size (the 2026-11-15 measurement in `bench/perf/`), over the project's 1% line for debug info, and a variable-free unit must keep `llc -live-debug-variables=false` (with variables on arm64, Machine Copy Propagation segfaulted on unresolved `DBG_VALUE`s). The Cranelift backend has no anchor: a macOS test that wants one of its types in the dSYM needs a non-inlined function whose parameters name it. The Windows image also holds rustc's runtime units, whose ranges `llvm-dwarfdump --verify` rejects: verify only the program's own unit. The allocation sampler walks frames with `fault::visit_frames`, not the raw frame-pointer chain: on Windows frame registers point into frames at per-function offsets, so a raw walk found no generated frame and every allocation read `[runtime]`. Locals and inlined callees follow the same path: `bind_local` names a binding that is never reassigned (a reassigned one holds several values, so its first would read stale); `NamedValue` carries `param` and `scope`; `inline_at` moves a callee's names onto the values it inlines, and a callee parameter, which has no value of its own once inlined, names the call's argument instead (one value can carry several names, and `simplify::apply_subst` moves a name to what replaced its value); `dwarf::emit_inlined` turns each `Loc.scope` into a `DW_TAG_inlined_subroutine` over the code ranges its lines occupy, and a variable sits inside the frame of its scope. Segments of a variable's location list that other leaves cut but that did not change are joined before expressions are built (the list writing was most of the 2.7% debug build cost, with 7% larger executables; measured in `bench/perf/debug-variables-2026-11-15.md`). Printers must tolerate `<optimized out>` parts. The gdb and lldb helpers (`tools/debugger/manuscript_gdb.py`, `manuscript_lldb.py`) share `manuscript_values.py`, which decodes `ms_rt_abi::StrVal`: change both together; `test_values.py` runs in the `ms-cli` tests. LLDB picks formatters by type name, so enums and optionals are registered by shape per loaded module. Windows debuggers that need a PDB cannot read this (no PDB is emitted); gdb and lldb read the DWARF in the `.exe`.

Reading the report (2026-11-17 review of `ms profile` and `ms diagram`): the start shim before `main` is not a program frame, so folded stacks are rooted at `main`, not `[runtime]` (it made `[runtime]` read as 100% cumulative); `[runtime]` as a leaf means a runtime call from the last Manuscript frame. A report of fewer than 100 samples says so. Inlined callees are not frames, so a hot function inlined into its caller is reported as the caller; frames from DWARF inline records are the remaining gap. The code map's `unknown` effect is shown, never filtered: `unknown` is not "pure".

C build (2026-11-23): the C runtime samples only the thread that runs `main`, through `ms_sched_sample_window` (src/runtime/entry/profile.c; the clock is src/runtime/sys/{posix,windows}/sampler.c). Linux and macOS use `ITIMER_PROF` (CPU time), and every other thread blocks SIGPROF, because the kernel hands a process signal to any thread that does not block it and the idle initial thread would otherwise take them all. Windows has no profiling signal: a sampler thread suspends the target and reads its registers, so its samples are wall-clock and its walk scans for frame records. The kernel delivers the timer on its own tick (250 Hz is common), so the runtime writes `# hz=` as samples over the process CPU time it measured, not the requested rate; without that the report's seconds were four times too short. The C runtime is built without frame pointers, so a sample inside runtime code holds the generated caller's frame register and the walk would drop that caller: the sampler looks for the first source return address above the stack pointer. `MS_PERF_MAP=1` writes `/tmp/perf-<pid>.map` (posix only). `--allocs` is not ported to the C build yet.
