# Pull request CI has a ten-minute budget

Decision (Chinmay, 2026-11-14): a pull request's CI must finish in under 10 minutes per job on the current runners (no larger runners), and a new test must fit the budget or something else is cut. Meet it by removing redundant work (one build, shared sessions, work another test already does), not by shrinking test inputs or dropping coverage. See [ci-time](../../../skills/ci-time/SKILL.md).

- Two jobs per PR, one per Linux arch (amd64 and arm64), each building with `cmake --preset ci` and running `ctest`, `lint`, `dist-smoke`, `repo-check`, `docs-check`, `conform` and `count-check` (`.github/workflows/ci.yml`). No sharding (Chinmay, 2026-11-17: no more shards or jobs), no extra runners, and no per-arch or per-platform skipping of a test.
- The `Time budget` job in `ci.yml` fails a PR whose `linux-*` job ran over 600 s, and `Platform checks` requires it. Never raise 600 s. Re-running only a failed `Time budget` job re-reads the slow earlier job: re-run the over-budget job itself.
- Runner noise is large. The same code ran 438 s and 624 s on two runs, every step about 45% slower on the slow runner, so a 10-minute budget needs real headroom, not a re-run. Before cutting coverage, compare an unrelated test's time between the two runs: a uniform slowdown is the runner, not the change.
- Cache freshness decides much of the variance: a pull request cache is visible to that pull request only, and the six-platform run of `main` is hours apart, so the `Warm caches` workflow (`warm-c-caches.yml`) rebuilds the caches after each push to `main` and pull requests restore them.
- A `${{ cond && '' || x }}` expression always yields `x`, because an empty string is falsy. Write `${{ !cond && x || '' }}`.
- A new test is cheap or it replaces another: no test over 2 s without a reason, no per-position loops over a whole file (sample them), no spawning `ms` for a case an in-process call covers, no work the conformance corpus already does. When a CLI test is slow, callgrind one spawn first: a slow `ms map --view review` test was a quadratic query loop (every standard-library entity asked the lazy effect scan, which republished the library's effects about 370 times), not the test count.
- Read IR size per function before reading LLVM flags: every `ms test` binary carries the test runner and `status_error`, which built the whole `Error` in each table row (4,100 IR lines per table) until it picked the row's strings and built the error once. Find the next offender with a per-function line count of the kept IR.

Conformance (2026-11-23, 2026-11-25): `tools/conform-run.ms` runs as many fixtures at once as there are logical CPUs, at most 8. With 8 jobs on a 4-core box `image`, `image-fuzz`, `router` and `builtin-parity` exceeded the 30 s test-phase limit; `--jobs 4` passed 744 of 744 in about the same wall time. Do not read such timeouts as slow fixtures before checking `--jobs`. `tools/conform/batch.ms` proves plain-pass fixtures (single file, no arguments or input, exit 0, quiet stderr, only RUN/PASS lines, no `@std/os`, `net`, `process`, `time` or `concurrency` import) and builds up to 12 per directory with one `ms test a.ms b.ms --json`, cutting each fixture's report out of the combined one. A fixture counts only when its slice equals its recording, and every other fixture is observed alone, so a failure still fails. Local result: 221 s to 148 s wall, 797 to 533 CPU-s. This is not sharding: one job per arch, every fixture judged on its own.

Apply when: adding or changing a test, a CI step or a workflow.
Evidence: `.github/workflows/ci.yml`, [AGENTS.md](../../../AGENTS.md), `tools/conform/batch.ms`.
Verify: the latest pull request run shows both Linux jobs under 600 s and a passing `Time budget` check.
