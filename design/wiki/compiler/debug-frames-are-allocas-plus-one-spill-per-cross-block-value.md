# Debug frames are allocas plus one spill per cross-block value

Verified (2026-11-23, Debug build, x86-64, `llc -O0`): a frame is the emitter's allocas plus one spill slot for every SSA value live across a block or call, because the fast register allocator never colors or reuses spills and StackColoring does not run at -O0. `src/stdlib/toml.ms` `read_value` measured 11.6 KB: 5.1 KB of allocas (slots 2.9, call argument copies 1.0, result areas 0.9) and the rest spills (about 500 cross-block values, 286 of them loads). The 20000-deep TOML nesting test needs at most 13.4 KB per level in the 256 MB stack region.

The emitter shares storage itself, since LLVM will not at -O0: call result areas are one `%R` per function, argument copies are shared for MIR calls whose result is not `ret_borrowed` (a view result can point into an argument copy), and runtime-call argument copies are shared unless the extern returns a view or keeps an argument (`mir_extern_pins_argument`), and `slot`s whose address is only loaded, stored, offset, selected or passed to calls that keep nothing (`mir_slot_ranges`) share `%cellK` allocas when their live ranges (block liveness of the slot's address, in instruction positions) are disjoint. Apply when: adding an alloca to `emit_frame_slots`. Verify: `ms test e2e/stdlib/toml.ms` at -O0. `emit_forward_copies` (`emit_copies.c`) then rewrites each function body: identity copies (`or i64 %s, 0`), constants written as `add i64 5, 0`, `inttoptr` of a `ptrtoint`, and phis with one incoming value are dropped and their users name the source. They were 70% of the cross-block values of `string_value` (frame 15.6 to 7.9 KB, `parse` 15.1 to 8.9 KB, `read_value` 7.2 to 5.9 KB). `opt -passes=instsimplify,dce` gave the same frames, so no LLVM pass is needed. Not done: the values that are really live across blocks still spill one slot each; coloring them is the next lever (#6446). `llc -O1` halves frames but leaves the size to LLVM, so no build selects it.

Decision (Chinmay, 2026-11-23): Debug builds run `opt default<O2>` (no vectorizers) and `llc -O2`, since 7.9 KB frames were still too big. Measured on the TOML parser: `string_value` 7.9 to 2.7 KB, `parse` 8.9 to 2.1 KB, `read_value` 5.9 to 1.4 KB; the accept+stdlib e2e sweep (8 parallel) went from 248 s to 383 s. `opt -O1` and `llc -O1` give the same frames. The emitter work above still matters: it shrinks the IR that opt and llc see. `e2e/stdlib/http-fault-leak.ms` (cancelled-fetch heap growth) fails intermittently at -O0 and -O2 alike (about 1 run in 4 grows 27 to 32 MB), so it is not caused by the optimizer.

Measured after this (2026-11-23, TOML parser, Debug -O2): `string_value` 2.7 to 1.0 KB, `scalar` 1.4 KB to under 0.9 KB. Per-site runtime-call argument copies were 100 of 126 allocas of `string_value` (LLVM cannot merge them: the emitter writes no lifetime markers). What is left is about half allocas (shared `%X`/`%P`/`%R` areas, slots whose address escapes) and half spills.

Wide values (2026-11-23, `design/proposals/wide-values-in-memory.md`): in a Debug build a value of more than 4 leaves (`DEFAULT_WIDE_LEAVES`, `MS_WIDE_LEAVES`) lives in a `%cell<K>` alloca, loaded one leaf at a time with `load volatile` and passed by address; cells that are never live together share storage (`mir_cell_conflicts`; hull ranges gave 9 cells of 520 B in yaml `flow_value`). Largest frames: toml 1144 to 856 B, yaml `flow_value` 3816 to 3240 B (the sum over yaml functions grows 3%, toml shrinks 10%). Not enough for "hundreds of bytes": two 520 B `Flow` cells, a 400 B `Context` copy from `type.get` and a 200 B copy remain. `ms test` defaults to Release; pass `--build-type Debug` to test this path. yaml_suite's overflow is not a frame problem (it also fails in Release).

## Debug build pipeline (2026-11-23)

- Debug runs `function(sroa,early-cse,simplifycfg,instcombine<no-verify-fixpoint>,sroa,simplifycfg)` and `llc -O1 -regalloc=basic -enable-misched=0`: frames within 0.2% of `default<O2>`, LLVM time 8.5 s against 21.6 s on a 30 MB program. SROA alone is +2.7%.
- Not FastISel: it moves the line a fault trace reports (seed-0025 shows 60, not 63).
- `instcombine` without `<no-verify-fixpoint>` aborts LLVM 23 builds that verify the fixpoint ("did not reach a fixpoint after 1 iterations").

Stack check for big frames (2026-11-23, yaml_suite overflowed in Debug and Release): the grow path of `depth.enter` runs inside the function's own frame, so a frame bigger than the reserve above the guard page (64 KB at least) faulted before the check could grow a segment; yaml `quoted` had 110 KB from MIR-inlined `Flow` temporaries. Three fixes: `mir_depth_lower` runs after expand and glue, which add slots, so the frame bound sees them; the bound counts the by-address copies of call arguments and results; a function with a bound above `DP_STUB_FRAME` (16 KB) becomes a small stub that checks and calls `<name>.body`. Slots are zeroed where their `slot` instruction is, after the check, not in the prologue. LLVM lifetime markers on allocas did not shrink such a frame (the slots are the MIR function's own, live from entry to return), so the emitter writes none.

Call temporaries (2026-11-23, `design/proposals/field-views.md` stage 1): `mem.copy` reads its source and writes its destination where it runs (`access_of`), and `str.data` of an inline string is an implicit 16-byte slot that lives as long as its address, so both take part in `mir_cell_conflicts` and share `%cell`s instead of keeping a `%s<n>` or `%y<b>_<i>` alloca each. yaml `quoted.body` Debug frame 2488 to 2184 B. Measure frames with `llc -print-after=prologepilog -filter-print-funcs=<fn>` (the `Frame Objects` list), not `rbp` offsets: a 520 B cell is 65 words.

Build time (2026-11-23): `ms test` of yaml, html, router, native-function-values and html-oracle hit the per-fixture timeout once the size tiers were gone. Cause, from the real IR (`opt` wrapper script on PATH that copies `program.ll`): 459k IR lines for yaml, 8222 of 10812 stores in `flow_value.body` into 520-byte slots (a 66-leaf `Flow` as a leaf bag), `opt` 13 s and `llc` 8 s; in html DSE alone was 6.9 of 12.8 s. Fixes: values of more than 16 leaves are held in cells in Release too (plain loads, `memcpy` copies; `wide_hide` only in Debug), and `opt` gets `-dse-memoryssa-defs-per-block-limit=500 -dse-memoryssa-walklimit=20 -dse-memoryssa-scanlimit=50` (same output, 239361 vs 239362 lines for html). yaml 26 to 23 s, html 24.5 to 16, native-function-values 23.7 to 15, html-oracle 24 to 16, router 16.5 to 14 (debug-built `ms`; opt plus llc for yaml 21 to 11 s). `bench/perf/stdlib` yaml, json, toml and html parse medians are unchanged within noise.

In-place `var` records (2026-11-23, `design/proposals/in-place-var-records.md`): a `var` record parameter stays in the caller's cell (`fn_closing_param`), and a mutable record local that starts as a fresh value lives in a frame cell (`fn_bind_closing_in`). Reads are `ptr.field` and `load`, writes drop the old field and `store`/`put` over it (`fn_store_field_in_place`), lends pass the address. There is no `take`/`type.set`/`put` chain, so the late pass `opt_fieldview` that recovered it is gone. yaml Debug (test build): `block_value` 6.0 to 4.1 KB, `inline_value` 4.2 to 3.6 KB, `quoted` 2.1 KB.

## In-place record pitfalls (found after #6652 broke main)

- A record lays its leaves out in one run, so a multi-leaf field after a bool (`failure Error?` after `finished Bool`) sits off its own alignment, and a `load` through `ptr.field` would read other bytes than the field's own cell holds (json-reader caught it). `field_cell_exact` (`lower_field.c`) accepts a multi-leaf field only after whole-word fields; the rest keep the take/put path until the record layout itself puts each field in its own cell.
- The unwind pass classifies a slot parameter as borrowed in place from how it is used (`uw_bsv_slot_use_ok`). `ptr.field` of the parameter counts as a borrow only when its result is just loaded or scalar-stored (`uw_bsv_field_borrowed`); without that the rewrite made `send.vt` look consuming and http2-cancelled-requests leaked about 930 B per request.
- The sweep lists missed both; run the whole `e2e/stdlib` list in Debug and Release before landing a rewrite of how records are read.
- `mir_field_offset` must keep using each field's own leaves: counting a Map or Set field as one word (as `mir_type_block` does) moved the offsets that `ptr.field` of ordinary `var` record field access uses, and `ms run tools/docgen.ms` crashed in `ms_map_insert` (#6678, reverted). Check `make docs` after touching layout code.

Every `var` record in a cell (2026-11-23, #6750): all mutable record locals (with or without drop glue; plain-data ones get a slot nothing closes) and `move` params that are assigned into (not closer types) live in a cell. `x = f(x)` takes the old value out of the cell before the right side (`fn_cell_gives_up`), reads of `x` there are that value (`fn_cell_old_read`; a move argument takes it, `fn_closing_take`), and the old value is dropped or handed on, then the cell is refilled (`fn_cell_takes_back`), so a dying receiver's `clone` still becomes a move (`consumed-arguments-stay-linear`). A field moved out of a cell leaves a zeroed hole (`field_hole`): zero drops as nothing. A field read the native lends in place (`fn->placing_member`) must not move out. `holds_value` and its prescans (the #6753 workaround) are deleted. Still on the old take/put path: closer methods' `self` and a few `fn_owned_local` bases; it goes with the struct layout and static unwind follow-ups.
