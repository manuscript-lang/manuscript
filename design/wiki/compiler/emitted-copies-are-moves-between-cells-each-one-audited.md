# Emitted copies are moves between cells, and each kind is audited

Verified (2026-11-25 audit): none of the first-party C `memcpy` calls (about 440, in `base`, `runtime`, and the compiler's own data) copies a value a program owns; they build buffers, grow arrays and encode bytes. The copies that matter are the `llvm.memcpy` and `llvm.memmove` the emitter writes into generated code. `ms build --emit ir --opt ` shows them; `opt -O3` removes about half, and `tools/memcpy-check.ms` keeps a per-program budget (`tools/memcpy-budget.txt`).

Justified: a wide value (more leaves than `wide_leaves`) lives in a stack cell, so a move between cells is a block copy: a record into an optional or result (`alt.new`, `opt.some`), a payload out of one (`alt.take`), a block argument on an edge, a return into `%sret`, a list element in or out. Each is the physical form of a language move.

Fixed: `x.f` on a record behind a pointer (a `var` receiver) lowered to `load T p; type.get T.f`, a copy of every leaf of `T` (112 bytes for `Lines`) to read one field. `opt_fieldload.c` turns it into `ptr.field` plus a load of the field alone, when the loaded record is read only by `type.get`, nothing writes memory in between, and the field lies in the record's image as it lies alone.

Fixed (root cause, replaces an earlier held-back-copy cancel that the in-place build made redundant): `alt.take` then `alt.new` of the same payload into a result of another type (`?` forwarding `Result[String, Error]` into `Result[String?, Error]`) wrote two inverse `memmove`s of the payload through one cell, 139 of the 300 copies that survive LLVM in the benchmark programs; and a value built only to become the payload of the `alt.new` after it (an `Error` built by a call, then wrapped in a result) lay at offset 0 of the shared cell and was shifted past the tag by a `memmove`. `emit_wide_alias` now places it at its final offset in that cell (`base`, named `%cellv<n>`), so the move is not written. Code that asks whether two values overlap must ask `emit_wide_shares_cell` (same pool), not `emit_wide_same_cell` (same pool and offset): the first aliasing attempt let a record `new` overwrite a field it still had to copy, and only the Debug build (hidden cells, volatile loads) failed.

The in-place build (`emit_wide_alias`) builds a wrapped payload at its place in the result cell when the payload is made by an instruction in the same pool, has one use and matches the result layout. A returned value is built in the result area: `choose_ret_cell` makes the pooled cell that holds most returned values (of exactly the return size) a view of `%sret`, so `ret` copies nothing. Open: a payload forwarded across a block edge or a call still copies. csv callgrind is +0.4% instructions from the alias (vector memmove becomes scalar stores); wall-clock is within noise.

Apply when: a change adds a block copy to emitted code, or `make memcpy-check` fails.
Evidence: [opt_fieldload.c](../../../src/compiler/opt/opt_fieldload.c), [memcpy-check.ms](../../../tools/memcpy-check.ms), [a new owner takes a move or a written clone](a-new-owner-takes-a-move-or-a-written-clone-never-a-hidden-copy.md) for the language-level copy probe.
Verify: `make memcpy-check`; `ms build --emit ir --opt bench/perf/programs/ms/ms.toml  | grep -c llvm.memcpy`.

Round 3 review (csv, callgrind): libc `memcpy` is 5.7% of instructions and every caller is a data copy: list growth (`realloc`), owned strings from spans (`from_span`, `split` pieces, `append`). No generated-code copy is on a hot path. What remains in the optimised IR is the unwind path, which moves the state cell into a scratch cell and then drops that (`memcpy` then `drop`); dropping in place would save the copy but only code size. `make copy-check` reports the same 21 front-end copies as before this audit.
