# Task stacks are 512 KiB slots in 256 MiB regions

Verified (C runtime, `src/runtime/core/stack.c`, `segment.c`, `src/abi/layout.h`): a task stack starts as a 512 KiB slot (`MS_STACK_SLOT`) carved from a 256 MiB region (`MS_STACK_REGION`) that is reserved without committing pages, so a touched page costs one page, not a huge page. The main task gets a region of its own. A task that recurses past its slot grows. A parked task costs one stack page plus page tables plus its records (Rust-era measurement: 5.0 KB resident at 100k and at 1M tasks). Rust-era hibernation (packing a parked task's stack) did not come to the C runtime.

- Growth: every cyclic function starts with the depth check (`depth.enter`, lowered by `compiler/mir/mir_depth.c` to `stack.low`, a branch and a grow shim). Below the limit the function stores its parameters in a heap block and calls `msrt_task_grow(shim, block)` (`task_abi.c`); the runtime takes the task's next segment, a slot kept in the pool until the task ends, so a loop at a boundary pays one call and no allocation (Rust-era: well under a microsecond per crossing). The segment's top 32 bytes hold its chain cell (the bounds and chain of the segment below). The cap is the region: 511 segments (`MAX_SEGMENTS`), then a stack overflow fault. Frame walkers follow the chain when a frame leaves the bounds.
- The running segment's bounds and chain cell are per thread, because every scheduler thread switches them and grows its own tasks. As process statics, two threads once wrote each other's segment, the chain cells formed a cycle, and the frame capture spun forever with every scheduler thread at 100% CPU (#2644). Any process-wide variable that runtime code writes while tasks run is suspect: user code runs on every scheduler thread, so only write-once values may be process-wide. Fixture: `task-stack-growth.ms`.
- Guards: Linux 6.13+ installs a guard region (`MADV_GUARD_INSTALL`, `sys/posix/mem.c`), which splits no mapping, so 1M guarded slots cost 25 mappings; older kernels and macOS `mprotect` the bottom of the slot, which splits the region's mapping, and `vm.max_map_count` (65530) then bounds a process near 32k tasks until it is raised (#2483). A slot is never unmapped on its own; regions go back at teardown.
- Windows commits a slot's top pages and lets the kernel's guard page commit the rest. Committing a guard page makes the kernel set the calling thread's `StackLimit` to the page above it even when the page is in another task's slot, so `ms_sys_commit_guard` (`sys/windows/mem.c`) saves and restores the limit; left mixed, the next `__chkstk` probe walks into the foreign guard page and the process exits 0x80000001. A unit test cannot catch this: the probe needs a large frame in the right task at the right time. The context switch installs the next stack's thread environment block fields only after the stack pointer has moved.
- Freeing deep data does not grow the stack: the drop glue of a type that reaches itself calls `msrt_drop_enter`, and past 256 nested drops parks the value on a per-thread worklist that the outermost drop drains (`runtime/core/drop_queue.c`). A 6,000-deep TOML table freed in a promise once died with "stack overflow" because glue never ran the recursion check; the main task's region hid it. Fixture: `task-deep-drop.ms`.
- The helpers the compiler writes for a type that contains itself (JSON, equality, format, copy glue) recurse like written functions and need the same check; the copy glue runs on a new segment when short. Fixture: `task-deep-recursion.ms`.
- Windows stack walks (#7011): generated functions carry `uwtable` there, so fault reports and the profiler unwind with `RtlVirtualUnwind` (`ms_sys_unwind`) instead of scanning for frame records; the walk still ends at a segment boundary. Verified by the Windows CI legs, not on Linux.

Apply when: changing stack allocation, the scheduler's idle path, context switching, the recursion check or anything that inserts at a function's entry block, or adding another per-operation task.
Evidence: `src/runtime/core/stack.c`, `segment.c`, `task_abi.c`, `src/runtime/sys/*/mem.c`; [`bench/perf/tasks/README.md`](../../../bench/perf/tasks/README.md).
Verify: `ms run bench/perf/tasks/main.ms -- 1000000 sleep` parks a million tasks in under 5 GB (resident plus page tables); the stack fixtures above.
