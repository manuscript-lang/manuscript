# Timed waits are a deadline with a meaning or armed by an event, never a poll

Rule (Chinmay, 2026-11-16: "i dont like all these random sleeps and waits, they make the software fragile"): a wait is a deadline that means something (user timeout, grace period, retry policy, protocol delay) or one deadline armed by an event. A wait that wakes on a period to see whether something changed is replaced by the event it waits on. `make repo-check` enforces it: `crates/ms-repo-check/src/timed_waits.rs` counts `sleep(`, `park_timeout(`, `recv_timeout(` and `wait_timeout` per file against `timed-waits-allowed.txt` (path, count, reason); a count above the list fails, and a count below it fails too, so the list only shrinks. It is a textual tripwire, not a parser: it also counts `fn sleep(`, `try_task_sleep(` and `sleep(` inside strings and test modules, cuts a line at `//` even inside a string, and does not see other forms (`poll_one(.., Some(slice))`, `wait_ready(.., ms)`, `libc::poll` timeouts, `Gate::park(ns)`), so a new polling wait can pass it; review for those by reading. A new wait needs a reason in the list; a converted one lowers its count.

Done (2026-11-16): the unit-test thread wait in `ms-std-net/src/wait.rs` blocks on the descriptor until ready or the deadline (no 50 ms slice; `sys::poll_one` takes an optional timeout on Unix and Windows); the file watcher's Linux inotify wait and the polling watcher's sleep wake on `close` through `ms_rt::glue::Wakeup` (a token a task parks on and any thread can signal; store the id, re-check `closed`, then park) instead of re-checking every 50 ms; the guard; the accept loop (2026-11-16, the runtime retries per-connection errors at once; any other error backs off 5 ms doubling to 1 s); the h2 reset-stream and pool tests wait on events instead of sleeping. Windows `watch_signals` parks on a `Wakeup` that the console handler and `close` signal (2026-11-16). Child exit (`run`, `Subprocess.wait`) already parks on a pidfd (Linux), an `EVFILT_PROC` kqueue (macOS) or the process handle through the poller (Windows); `POLL_MS` (2 ms) remains only as the fallback when that event cannot be armed (Linux before 5.3, a failed kqueue or wait registration). The Windows reactor parks to the caller's deadline with no cap (2026-11-16; a moved deadline kicks it), and a Windows stream waits for console input on a pool thread that watches a stop event, and reads a pipe with a blocking read on a pool thread that a stop request ends with `CancelIoEx` (a pipe cannot be waited on without consuming; the stop request repeats `CancelIoEx` until a started job is done, since it does nothing before the read is issued). `ms-cli` `wait_supervised` (2026-11-16) waits on one channel for the child's exit (a thread blocked in `waitid` without reaping, or `WaitForSingleObject`), SIGINT and SIGTERM (a self-pipe and relay thread on Unix, the handler's own thread on Windows; the event carries the signal number) and reader output (`Stops::wake`), with the run timeout (and, for `ms test`, the oldest running test's limit) as the only deadlines; the test harness rings a doorbell pipe (`MS_TEST_WAKE`) after each record it appends to the records file, so records wake the wait without a tick; the post-exit `recv_timeout(100 ms)` drains stay as the bounded grace for a grandchild that holds a pipe open. `ms-conform` `exec.rs` waits for the child on a thread and takes the run's deadline from the channel (no 5 ms poll). The terminal's wait for input (2026-11-16) has no slice: it blocks on a pool thread until input, a resize or a close (Unix: `poll` on stdin and a process-wide wake pipe that a SIGWINCH handler and `close` write; Windows: `WaitForMultipleObjects` on the console input handle, which a resize record signals, and a wake event). The Manuscript event loop compares the size only on a wake. Idle: 20 wakes/s and 20 ms CPU per 10 s before, 0 and 0 after (Linux). A pty test needs the pty as the child's controlling terminal, or the resize raises no SIGWINCH. The kqueue (macOS) watcher parks on the kqueue descriptor and `close` triggers an `EVFILT_USER` event; the `ReadDirectoryChangesW` (Windows) watcher parks on the request's manual-reset event through `glue::object`, `close` sets the same event, and the event is reset before each look so no signal is lost (CI-verified on both).

Rejected: replacing the HTTP watcher's periodic look with kernel timers (PR 4238, see [the stealing page](a-computing-handler-holds-its-thread-so-idle-connections-are-taken.md)); it was measured and costs the hot path more than it saves.

## Kept, named

`SPIN_NS` 20 µs (bounded spin before a sleep), `SPIN_BELOW_NS` 1 ms (epoll rounds timers to a millisecond, so a shorter one spins and ends at the timer), `BEAT_NS`, `OWN_HOLD_NS`, `STEAL_*_NS` (one deadline armed by an event), `CLEANUP_GRACE_SECS` 30 s, `CANCEL_FLUSH` 200 ms, the HTTP server's `next_sweep` (earliest deadline), user timeouts in dns, tls, exchange and client, `WAIT_DELAY_NS` 1 s (`exec.Cmd.WaitDelay`), the terminal's 40 ms lone-Escape wait (the terminal sends no end marker), resilience retry and throttle, SSE `retry_ms`, `ms-lsp` debounce and restart windows, and the watcher's own look interval (see the stealing page).

Apply when: adding a wait, a sleep in a test, or a retry loop.
Evidence: timed_waits.rs, allow list, wait.rs, watch.rs, [proposal](../../proposals/event-driven-waits.md).

A native that waits in a loop must call `ms_std_fs::ops::check_wait()` before each park. `ReadStream.next(timeout:)` sets a read limit on the task, and every park past it returns at once as a timeout. A loop that only retries then spins a core and never ends: the native watcher, the polling watcher, the signal stream and the terminal event stream did this. `check_wait` returns `STATUS_TIMEOUT` once the limit has passed, and `watch-and-signal-reads-time-out.ms` and the pseudo-terminal test in `crates/ms-cli/tests/terminal.rs` pin it.
