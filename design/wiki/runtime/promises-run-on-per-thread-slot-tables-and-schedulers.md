# Promises live in per-thread slot tables; threads exchange events

Verified: a promise id is `thread<<56 | generation<<32 | index+1`. The creating thread owns the slot columns (state, token, result, closure, timers); other threads never touch them and send `Started`, `Done`, `Ended` and `Cancel` events through the target thread's mail. I/O promises (sleep, fd readiness, native `io_on_ready` continuations) have no task. A `promise(fn:)` task owns the closure it is handed (the MIR extern parameter is `own`; nothing retains it) until `Ended`, so dropping a promise cancels, joins, then frees.

Function values a native keeps (its runtime header marks the parameter; e.g. `msrt_promise_start`, `msrt_promise_defer`, `msstd_http_serving_new`) are handed over, not borrowed: lowering marks the closure (or `env`) parameter owned in the MIR extern and passes an owned value, and the runtime drops the closure once when the task ends, the deferred work runs, or the serving drops. The runtime never retains such an argument, and a runtime-side creator (`promise::start_native`, the pipe tests) hands its fresh closure over without a release of its own. A retain in the runtime paired with a borrowed MIR parameter was the old refcount pattern; the valgrind signature of getting this wrong is a use-after-free when a task starts its closure. Every runtime function that keeps a callback must have its `extern fn` declare that parameter `move` (the checker and lowering read it), or the closure is freed early and cancelled tasks leak stack values.

Verified (2026-11-07): `promise(fn:)` queues the start on the creator's own thread (`src/runtime/core/sched.c`) and nothing runs until someone needs it. A waiter with no deadline pulls its promise back out of the queue and runs it inline under `msrt_guard_call` (`src/runtime/core/promise.c`), about 0.2 us against 3.9 us for a task; another thread takes only a start older than `BEAT_NS` (20 us), oldest first, and an idle thread sleeps with a timeout until the oldest start ages. Placing starts on other threads at spawn made every fine-grained promise pay a task and a wake; `remove_pending` scanning every thread's queue made 4 threads slower than 1 (5.7M-promise tree: 2.8 s against 0.9 s) until it looked only at its own queue. The first beat (20 us) exposed that the terminal's state (`ffi::Global`) is main-thread-only and faults in a promise on another thread: a thief took the second `events.next()` of the terminal program (debug build) and a raw-terminal test timed out (#2820). `Global::get` on the main thread now sets `MAIN_AFFINE`, so `pinned_here()` keeps later promises started on the main thread on it. A promise created before that first access can still be stolen. Evidence: `bench/perf/promise-tree/README.md`.

Verified (2026-11-08): every promise operation touches the owner thread's table, so a handle used on another thread (captured by a promise that an idle thread stole, or returned by a promise) used to fault `promise: no such promise`, and only when placement happened to cross threads (#3118). `promise::ask` now runs the operation on the owner in a detached task (`Event::Call`) and parks the caller on a remote token; waits register the caller's token in the owner's `watchers` list instead of holding a task there. The same-thread path is unchanged. New promise operations must go through `is_foreign`/`ask`. Tests: `promise::tests` `a_promise_of_another_thread...`, `tests/lang/stdlib/promise-cross-thread.ms`.

Verified (2026-11-10, #3355): mixed-thread `wait_any` must inspect every input before running deferred work, then run deferred inputs on their owners with the waiter's inherited deadline. Passive watcher registration cannot run unstarted work: that could block the whole choice behind one input. A foreign query parks its caller, so a local input checked before that query may finish before its token is installed; recheck local readiness both before deferred callbacks and before parking. Omitting these steps skipped local deferred reads, ran foreign callbacks ahead of existing results, and missed local completions. The `mixed_wait_any_*` tests exercise actual worker threads and bound the failing waits.

Verified: load is a thread's live promise tasks plus queued starts, and only a thread with no live task takes unstarted work. Counting only ready tasks let a thread full of sleepers take a CPU-bound promise, and its sleepers then overshot by the whole spin (about 600 ms against 3 ms). Tests that expect spreading must keep promises busy, because a sleeping promise does not make its thread busy.

Verified: a native that blocks hands its work to the blocking pool itself (`pool::run`, `fs` `offload`, net `wait`) when other tasks share its thread, and this works from scheduler threads. There is no declared blocking marker on externs; a Rust name list or a new keyword was not needed. Terminal natives stay on the main thread (`Global::get`); the system inventory is per thread.

Verified: a task stack is a 512 KiB slot in a 256 MiB region (see [task stacks](task-stacks-are-512-kib-slots-in-256-mib-regions.md)); an idle task costs one resident page, about 5 to 6 KB with its records, and nothing once it hibernates. The promise table's `task` column names the task running the work, so a cancel reaches it directly instead of scanning the scheduler's slots (#2539). A connection that holds no stack needs the work to start on readiness (`ms_promise_io_on_ready`) rather than a task that blocks.

Verified (2026-11-07): `wait_any` scans readiness once before starting deferred work, then again only after a deferred callback actually runs. Eager promise slots are owner-thread-local and advance through events or timers when the waiter parks; a no-op deferred-work probe cannot change their readiness. Rescanning the entire list before every eager input made 40,000 pending inputs do quadratic setup work (#2932). Keep the rescan after a callback: it can complete a different input, so checking only its own slot would run later callbacks unnecessarily. Evidence: the pending-list and deferred-callback conformance fixtures, and [paired measurements](../../../bench/perf/wait-all/README.md).

Apply when: changing `src/runtime/core/promise*.c`, `sched.c`, `pipe.c`, the poller, or adding a native that completes a promise.
Thread-local tables have no destructor, so every one must be released in `task::teardown` (`promise::teardown` frees the promise table). The `stats` leak count and `make leak-check` cannot see it (the table's `Vec`s are plain std allocations); a plain `valgrind --leak-check=full` on any program that starts a promise or reads stdin can (#2472: 14 lost blocks, frames unwindable only with `--trace-malloc` plus the unfreed-address diff, since valgrind cannot unwind task stacks).

A promise has one cancel-signal registration. Applying a replacement must unregister the previous switch before registering the new one, including when the replacement is already fired or freed. Drop and teardown only know the current registration; leaving an older membership behind both retains stale ids and lets an old switch cancel rebound work. The cancel tests assert membership counts after repeated rebind/drop and teardown, as well as which switch actually cancels the promise.

Evidence: the promise fixtures under `tests/lang/stdlib/` (spread, steal, remote cancel, remote fault, pool jobs from scheduler threads); `tools/leak-check.ms` on cancel and fault programs.
Verify: the promise fixtures repeated; leak-check clean after a dropped running promise.

Verified (2026-11-14): 100k tiny promises on 4 threads ran slower than on 1 because thieves paid a task and three events per steal, and spun on the creator's queue (660 ms of CPU for 190 ms). `sched::steal_feedback` makes a thread that stole a promise that ran under 5 us pause stealing, doubling from 50 us to 2 ms (`steal_off_until`; `steal_wait_ns` includes it so an idle thread sleeps instead of spinning). Batch steals (64 per lock) and stealing the newest end did not help. Evidence: `bench/perf/small-promises/README.md`.

Verified (2026-11-15, #4112): four promises that each wait on I/O ran on two or three threads, so a 300 ms round took 0.7 to 1.3 s (Postgres lookups: 0.57 to 1.98 s run to run). Two causes. `next_pending` let the creator start its own queued promises the moment it had nothing ready, before the threads it had just spawned or woken could take them, and a started promise never moves; `submit` also woke one idle thread only when the queue went from empty to non-empty, so the rest of a burst never reached the other idle threads. Now the creator starts its own queue only while more are queued than other threads could take (`own_ready`, bounded by `OWN_HOLD_NS`, 1 ms), every start wakes and claims one idle thread (`wake_idle` clears its idle bit), and `reactor_wait` recomputes its timeout after it sets `sleeping`, since a start queued just before did not kick it and was not old enough to count as work. Test: `waiting_promises_each_get_a_thread` (counts distinct threads, not time; most rounds, because the OS can stall one thread for a few ms). A 20 us spin removal was tried and changed nothing here. Apply when: a fan-out of waiting promises runs slower than its thread count predicts, or `submit`/`next_pending` placement changes.

A promise row holds one wait word. Two tasks can end one promise at once (the task that drops it and the owner's ask to end it), and the later word used to overwrite the earlier, so the end's wake reached one and the other parked forever: the `chat-room` websocket test hung about 1 run in 70 under load (found with gdb on the parked process: the handler sat in `ms_promise_end` on a row that had since been reused). `promise_park_on` now keeps the earlier word and wakes it when it leaves.
