# Sorting records that own data uses the generated sort over bitwise scratch

`sorted` with a known capture-free comparator is compiled with the program (`src/compiler/opt/opt_sortgen.c`) so the comparator inlines; the runtime sort pays an indirect call per comparison and was 2.4x Rust on 1M records with a `String` field. Owning records are now sorted by the same generated code over two `msrt_list_shadow` copies (raw bytes, owning nothing) and the sorted slots are cloned into the result, then `msrt_list_free_raw` frees the scratch. A comparator exit (fault, cancellation) therefore leaks only scratch bytes and never leaves a list with duplicated owners; sorting the real list in place would. Do not drop a shadow as a list. The generated sort is a driftsort (runs, stable quicksort with an equal-ancestor partition, merge sort as the depth-limit fallback); its quicksort partitions with one store to a selected address, not a branch, and every helper is stable and moves slots as bits. A fault test needs a capture-free comparator that faults on data (`fixture sort-driftsort-shapes`), since a capturing comparator takes the runtime path. Evidence: `bench/perf/element-types/README.md`, fixture `e2e/accept/sort-owning-records-by-comparator`.

The merge buffer is freed right after the sort and before the clone, so the result reuses its block: 1M `Int`/`String`/`Float` records peaked at 127 MB with the buffer freed last and 96 MB now (Rust 92).

`String` elements take the same path (`word_elem` accepts `STR`): 1M long strings sorted by `compare` went from 630 to 380 ms against Rust's 341 to 378.

A benchmark with `String::from` per Rust record against Manuscript's static literals is not equal work: borrow the literal (`Cow::Borrowed`) in the Rust twin.

C pipeline: `List.sorted(compare)` is a bodiless stdlib native (`msrt_list_sorted`, role `MR_LIST_SORTED`); lowering gives it a generated `sort.cmp` thunk (`NS_CMP_FN` in the signature table) and `sortgen` rewrites the call when the comparator is a known closure. The shadow extern must not be `fresh`: the copy holds the list's slots, and `lastuse` would otherwise drop the source before the result is cloned (a heap `String` element came back as freed memory inside a test, where promises run on workers). A stdlib sort written in Manuscript over an index list was 4x Rust on 1M records (random reads of the records); a generic call to the comparator costs the same as the runtime sort, so a comparator the module knows must reach `sortgen`. Closure specialization also runs after inlining, so `sorted` inlined into its caller still specializes `sort[T]`.
