# The MIR optimizer's compile time is measured per pass and per round

Verified (2026-11-24): on a 7-line program importing `@std/data/yaml.ms`, `ms emit --opt` cost 4.54G instructions (526 ms); the optimizer was 90% of it. Found by callgrind, then by timing each pass call:

- A pass that allocates per block or per candidate turns linear code into quadratic work: `lift_slot_takes` recomputed `mir_use_counts` per block (19% of the run); `opt_thread` scanned every block per candidate for loop headers. Count once per function; precompute a table.
- Callgrind counts `rep stosb` per byte, so zeroed arrays look worse than they are in wall time. Large scratch arrays that are written before they are read use `MS_ARENA_NEW_ARRAY_UNINIT` with a one-byte flag array.
- The per-function round ran six passes up to three times. By pass and round on that program: `range` 38 ms in round 1 (45 changes), 33 ms in round 2 and 32 ms in round 3 with no change either time; `copyelim` and `twins` the same. The schedule is now a table (`func_pass_enabled_by` in `opt_pipeline.c`): a pass reruns only when a pass that can give it work changed the function. Output was byte-identical on 483 programs (benchmark suite, yaml, fixtures).

- The runtime fast paths (`viewfast`, `bytesfast`, `strfast`, then the inliner) grew yaml's MIR from 15K to 60K instructions in the early steps, and every per-function pass then walked 4x the code. They now expand as the last step, after the final `simplify`: MIR is 25% larger at the end, but emit time fell 38%, Debug build 6%, Release build 14%, and 24 suite programs stayed within 0.4% of before in instructions (LLVM cleans the expansion). Expanding late exposed a template bug the cleanup had hidden: `sf_compare_bytes` defined `iconst 0` in a loop block and used it in a block it does not dominate. Templates must define a constant in the block that uses it. Fusing fold and CSE into one walk saved nothing (2213M vs 2202M): per-instruction work, not walks, was the cost.

Method: `valgrind --tool=callgrind ms emit prog.ms --opt` for instructions; a `clock_gettime` wrapper around each pass call for wall time per pass and round; compare `ms emit --opt` output against a build of the base to prove a schedule or skip is exact. A skip keyed on a function fingerprint saved only 4% (most unchanged calls are small), so it was not kept.

- Passes that no longer fire (2026-11-25): counting per-pass changes over 670 programs (benchmarks, agent suite, every accept fixture, tests mode included) found `loopslot` and `reserve` never changed anything; with each skipped, the emitted LLVM IR was byte-identical on all 670 (lowering sizes a counted loop's list, and the append fast paths superseded loopslot). Both were deleted. `twins` changed 9 programs and stays. Method: a temporary env switch that skips a named pass, then compare `ms emit --opt --ir` output with and without it; a pass with zero diffs is a deletion candidate.

- Where the time goes (2026-11-25, 670 programs, per-pass wall time with a temporary timer): `simplify` is 38% of the optimizer (module and per-function runs change code 63 to 98% of the time, so it is not idle); the step named `fuse` is mostly its prep (`unwind sites`, `unwind thread`, `simplify` change 95% of runs, `fuse` itself 3 of 638), so do not drop the step. Idle work is in passes that change under 1% of runs: per-function `copyelim` took 6% of the time for 0.4% changes (now one clone scan first: 685 to 459 ms, output byte-identical), `copyelim takes`, `thread` and `strfuse` still spend 80 to 120 ms each unchanged. Give such a pass a one-scan precheck for its trigger op before it builds use tables.

- Simplify without a worklist (2026-11-25, yaml import, 1.91G instructions): a worklist or per-subpass dirty bits would save little. Of 569 `simplify` runs, 238 changed nothing, and the last core round of every run is idle by construction (41% of core-round instruction visits), but a subpass that no other subpass changed since it last ran was idle in only 166 of 1011 `cse` runs and 199 of 1011 `dce` runs, under 2% of compile instructions. The pattern passes were the real idle cost: 11 passes, 32 of 569 rounds changed anything, each allocating per-value tables before finding no match. `sm_pattern_round` now scans the function once for the ops and runtime calls each pass needs (`SmPresent`) and runs only the passes whose trigger is present, rescanning after one changes the function: 2.4% fewer instructions, IR byte-identical on 670 programs. A new pattern pass needs a `wanted` predicate that is exactly its necessary condition. What is left: zeroed `MS_ARENA_NEW_ARRAY` tables are 13% of all instructions (`memset`; `lu_family` alone 55M, `mir_func_compact_blocks`, `opt_dead_flags`, `mir_use_counts`, `opt_simplify_phis_func` about 10M each); allocate them uninitialised where the pass writes before it reads. Callgrind inclusive cost is unreliable for `opt_simplify`/`opt_simplify_func` (they sit in a cycle); use per-function exclusive cost and caller edges.

Apply when: a pass is added to `function_round` (give it an entry in `func_pass_enabled_by`), or compile time of a large import (yaml, json) regresses.
