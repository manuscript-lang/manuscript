# Generic list search and the priority queue lose on instructions per element

Verified (2026-11-14, callgrind, release `ms`): `List[String].index_of` (20k searches over 2,000 strings) was 2.3x Rust's `position`: 54 instructions per element against about 17. `List.index_of` and `contains` are generic `.ms` loops (`src/stdlib/collections/collections.ms`); before the fix each element ran the inline word decision (about 25 instructions of selects) and, for two strings of one length with different blocks, a call to `msrt_string_eq` (about 27 more). `contains` over `Int` is not a gap: LLVM vectorizes the loop and it is memory bound (equal to Rust on repeat runs; the 1.58x in the round-2 probe was noise).

Fixed in part (2026-11-14): the decision was a branchless chain of selects run for every element. Branching on the one xor that separates most pairs, then on equal tagged words, in both backends took 1,078M to 793M instructions and the search loop 47 to 35 ms (`bench/perf/index-of`). An early length branch alone gave only 958M. The rest was the `msrt_string_eq` call for same-length pairs with different blocks (about 50 instructions a call: it decodes both kinds and lengths again). Comparing the first and last eight bytes of two same-kind, same-length blocks inline (8 to 16 bytes) took 793M to 503M instructions and 30.3 to 16.3 ms, equal to Rust's `position` (16.0 ms). The same inline compare gained only 4% on the old branchless chain, so the order mattered: decide cheaply first, then compare bytes. A runtime string loop in `msrt_list_index_of` changed nothing: the `.ms` loop is what runs.

`PriorityQueue` (`src/stdlib/collections/queue.ms`) is 1.5x Rust's `BinaryHeap` and 2x its instructions (273M against 135M for 500k enqueue and dequeue): a third is `heap.swap` (about 9 instructions per 16-byte entry; Rust moves a hole, one store per level) and another quarter is the two entry loads per comparison. Comparing in place instead of binding both entries saved 3%. Entries carry a sequence number for FIFO ties, which `BinaryHeap` does not pay for. A hole-based sift needs a move primitive for owned elements (the list has `swap` and `pop` only), so it is a language-library decision, not a rewrite of the loop.

Three heap redesigns lost to the swap-based heap (2026-11-18, Dijkstra 2.2x, pure queue operations 1.4x to 1.7x): a 4-ary heap, a bottom-up 4-ary sift, and a slab of entries with an index heap and a position map. Each added more loads or stores per level than the saved `swap` calls. The gap is the missing hole move: `List` has `swap`, `pop` and `replace` but no way to move an element without a clone, and `copy_within` needs `Clonable`, so a generic heap cannot sift with one store per level. A fourth try with existing operations (entries in `List[Entry?]`, `replace(i, none)` to empty a slot, a hole sift) took 104 ms against 86 ms for 500k enqueues and dequeues: the tag checks and unwraps cost more than the saved swaps. Owner decision (2026-11-18): leave the queue as it is; the gap is a micro-optimization. Revisit only with a move primitive on `List` (or a runtime sift that takes the comparator as a known closure, as `sortgen` does for sorts); measured in `bench/perf/everyday-round5`.

Apply when: someone proposes a micro-fix for `index_of`, `contains` or `PriorityQueue`: start from these counts.
